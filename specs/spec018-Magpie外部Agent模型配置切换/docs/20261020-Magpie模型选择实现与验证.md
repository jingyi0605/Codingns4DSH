# Magpie 模型选择实现与验证

日期：2026-10-20

## 本轮结果

- 在现有模型选择器中增加单独的 Magpie 模型组。只为 Claude Code 和 Codex 显示可持久切换的 Magpie 模型。
- 选择 Magpie 模型后先要求用户确认，再由 Host 重新读取目录、调用 Magpie CLI 写入并回读核验；只有核验成功，Client 才更新当前 DSH 会话。
- Magpie 写入成功但会话更新失败时显示部分成功。重试只更新原会话，不会重复写 Magpie，也不会因为用户已经切换会话而把重试应用到新会话。
- 普通模型仍使用原来的“只改当前 DSH 会话”流程。
- Magpie 模型目录和写入 RPC 都要求传入当前 DSH 会话。Host 校验该会话当前使用的 Agent；PeerHost 按该会话路由到目标 Host，作用域丢失时明确报错，不会回退到本机 Magpie。

## CLI 命令核对

- 本机 Magpie `0.1.1295` 的模型目录输出已只读检查，脱敏格式由 Claude 和 Codex 两个 fixture 覆盖。目录解析要求同时匹配准确 Agent footer 和模型 ID，并只接受回环 Gateway URL。
- 公开 Magpie `v0.1.1295` 源码确认：`magpie <agent> model` 显示 model 字段，输出由 Agent 名称、字段名 `model` 和当前值组成；`magpie <agent> <model>` 是写入命令。
  - https://github.com/yetone/magpie/blob/v0.1.1295/internal/cli/main.go
  - https://github.com/yetone/magpie/blob/v0.1.1295/internal/agent/claude.go
  - https://github.com/yetone/magpie/blob/v0.1.1295/internal/agent/codex.go
- 实现拒绝早于 `0.1.1295` 的 CLI。更高版本还必须通过严格的目录和回读格式解析；目前只有 `0.1.1295` 有目录 fixture，不能把版本门槛理解为所有后续版本都已实测。
- 这轮没有重新运行本机 Magpie CLI。没有打开 Magpie GUI、启动 Gateway、读写真实 Agent 配置或触碰 DSH Desktop。

## 验证

- 六个相关测试文件以源码加载器运行：222 项通过，覆盖 Magpie 服务、选择器、PeerHost 路由、Host RPC，以及 Claude Code/Codex 对 `provider/model` 的 fake-driver 传递。
- 调整 PeerHost 作用域丢失测试后，单独重跑 `tests/peer-host-model-navigation.spec.ts`：18 项通过。
- `pnpm run typecheck`：通过。
- `pnpm run i18n:check`：阻断违规 0；检查器报告 200 条仓库既有中文异常/日志告警。
- `git diff --check`：通过（记录更新后重跑，无空白错误）。

## 尚未验证

- 没有向真实 Magpie Gateway 发请求；用量和路由 API 仍由 fake HTTP 响应测试。
- 尚未确认 CodingNS 的 `providerSessionId` 在真实请求中一定等于 Magpie 记录的 Agent session ID。路由因此只在 Magpie 用量里出现完全匹配的 Agent 和 session ID 后才会请求，并要求路由响应再次回显相同 ID。
- Fake-driver 测试确认模型 ID 原样进入 Claude Code 的 `--model` 和 Codex 的线程模型更新，但没有启动真实 Agent、发起真实推理或验证上游响应。
- 进程启动参数的环境变量和 shell 设置目前由实现中的固定配置保证；本轮没有加入可注入进程启动器的专门断言。
