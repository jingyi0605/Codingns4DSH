# 终端 PTY 启动器调用说明

## 这份文档解决什么问题

Spec003 的“按配置启动终端”不能把命令字符串写进已经打开的交互 Shell。正确做法是由 Host 先读取 Workspace 配置，再调用已有终端服务创建独立运行实例，最后让 DSH 原生终端通过 `terminal.id` 附着。

这项能力已经在 `dsh-codingns` 中实现，Spec003 只调用它，不重新实现 tmux、local-pty 或 ConPTY backend。插件不得调用 CodingNS 父仓库；父仓库实现仅用于核对行为。

## 已有能力

- `TerminalLaunchProfile)：保存 Workspace、命令、参数、相对工作目录、环境变量和 `runtimeMode`。
- `TerminalProcessInstance)：保存一次实际运行状态、进程身份和退出信息。
- `TerminalProcessService)：Host 内部服务，同时兼容导出名称 `ProcessRuntimeService`。
- `terminalProcess/profile/list|create|delete`。
- `terminalProcess/launch`。
- `terminalProcess/runtime/list|get|stop`。
- POSIX tmux/local-pty 和 Windows 独立 ConPTY broker。

当前 Spec003 只使用 `runtimeMode: 'pty'`。不新增非交互 `runtimeMode: 'process'`。

## Workspace 配置到启动器

Host 读取并校验 Workspace 根目录下的 `.codingns/debug.json`，再把配置项映射为已有 Profile：

```ts
const result = await terminalProcesses.launch({
  workspaceId: profile.workspaceId,
  profileId: profile.id,
  dshSessionId: sessionId,
  cols: 120,
  rows: 32,
})
```

`cwdRelative`、命令、参数和终端字段来自 Host 读取的配置。Client 不提交绝对路径，也不能让 Host 把命令追加到已有 Shell。

## 两个标识的用途

| 标识 | 作用 |
| --- | --- |
| `terminal.id` | 打开或恢复 DSH 原生 Terminal，建立或恢复 attach |
| `instance.id` | 运行状态、恢复、端口检查关联、查询和显式停止的主键 |

启动返回后，Client 可以用 `terminal.id` 打开原生终端：

```ts
sidebarRight.openTabIn(sessionId, 'terminal', {
  params: { terminalId: result.terminal.id },
})
```

停止必须使用 `instance.id`：

```ts
await terminalProcesses.stop(result.instance.id)
```

## 生命周期规则

1. `terminal.id` 只是 attach 引用，不是运行实例主键。
2. `instance.id` 才是恢复、查询和停止的主键。
3. Session 切换、侧栏关闭、插件卸载或 generation 切换只释放 attach/subscription，不停止运行实例。
4. 只有用户明确执行停止时，Host 才结束 tmux、local-pty 或 ConPTY 进程。
5. PTY 自然退出后，Host 按 `instance.id` 将实例收敛为退出状态。

## 与 Spec003 三项需求的关系

- 配置启动：Spec003 负责读取 `.codingns/debug.json` 和校验 Workspace；终端服务负责真正创建 PTY。
- 端口处理：Spec003 使用 `instance.id` 关联端口检查结果；端口不能替代运行实例主键。
- 反向代理：Spec003 在端口确认监听后，把 `instance.id` 绑定到插件内部代理；插件通过 DSH Fetch 路由转发 HTTP/SSE，WebSocket Upgrade 当前明确不支持。
