# 外部 Agent 适配器选型矩阵

日期：2026-09-29
范围：对 `codex-host` 已接入的 15 个适配器，加上上一轮调查的 `WorkBuddy`、`ZCode`，逐项给出选型结论、证据、能力缺口与实施批次。本文件是 spec007.1 的选型依据。

## 调查方法

- 以本项目已有的 8 个适配器（`src/host/cli-adapters/feature.ts` 的驱动数组）为基线做差集，避免把已有能力重复计入。
- 一手取证：直接抓取 `codex-host` 的适配器源码、`manifest.json`、`docs/harnesses/*`，以及各产品的官方文档与 npm registry。
- 证据分级：
  - **A 级**：产品官方文档或官方仓库源码。
  - **B 级**：同类宿主（`codex-host`、`multica` 等）的已合并实现与真机验收记录。
  - **C 级**：社区包或第三方逆向结论，只作线索，不作为契约。
- GitHub 页面在本环境不可达（`web_fetch` 报 non-public IP），统一用 `curl` 抓 `raw.githubusercontent.com` 与 `api.github.com`。

### 2.2 同源产品关系（关键）

以下三组是同一 CLI 代码库的不同产品身份，**接第二个时不需要写新驱动**：

| 组 | 产品 | 关系证据 | 差异 |
| --- | --- | --- | --- |
| CodeBuddy / WorkBuddy | 腾讯 | `codex-host`：WorkBuddy 应用内置 CLI 包版本为 CodeBuddy 2.137.1，路径 `WorkBuddy AI.app/Contents/Resources/app.asar.unpacked/cli/bin/codebuddy`，"内部 CLI 入口仍名为 `codebuddy`"（B 级）；`multica` PR #7934 称其为 "the same `@genie/agent-cli` that CodeBuddy Code ships"（B 级） | 配置根（`~/.codebuddy` vs `~/.workbuddy-ai`）、发现方式（PATH vs 应用包）、历史目录编码（小写化 vs 保留大小写与 Unicode）、平台（全平台 vs 仅 macOS/Windows） |
| Qoder / Qoder CN | 阿里 | `codex-host` `qoder-runtime.ts`：两个 SDK 包 `@qoder-ai/qoder-agent-sdk` 与 `@qodercn-ai/qodercn-agent-sdk` 暴露同一套 API，但"own different CLI/auth/history defaults"（B 级）；npm 上两包均存在，latest 均为 `1.0.50`（A 级） | SDK 包名、命令名（`qodercli` vs `qoderclicn`）、访问令牌环境变量 |
| Kimi / Kimi Code | 月之暗面 | `codex-host` `kimi-code` 的命令名为 `kimi`，启动参数为 `acp`（B 级）；本项目已有 `kimi` 适配器的命令名同为 `kimi`/`kimi-cli`，协议为 stream-json（本仓库源码） | 协议路径（stream-json vs ACP），不是产品差异 |

**结论**：`kimi-code` 不应作为新增适配器，而应作为"已有 `kimi` 适配器的 ACP 协议升级"来评估。

## 三、能力缺口（codex-host 一手记录）

以下限制来自 `codex-host` 的适配器文档，属于 B 级证据，实施前需在本机复核。

| 候选 | 已知缺口 |
| --- | --- |
| `antigravity` | **只暴露 Skip permissions（危险）**，且这是新会话默认值——`codex-host` 明确"不添加工具审批、allow/ask/deny 匹配、只读白名单或工作区路径限制"，文档建议"仅在可接受无限制工具执行的环境使用"；headless 不接受双向工具权限回答，需交互批准的操作被 soft-denied；原生在 PrintMode 下**硬编码自动跳过 `ask_question`**，stream-json 里不抛该工具事件；无 `/compact` 或压缩事件（不能伪装成压缩）；需要向 stdin 写 prompt |
| `cursor-cli` | 明确标记 **experimental**；ACP **没有 Usage、Fork、回滚或上下文压缩出口**；Fork 依赖未文档化的 `store.db` 与 PTY（`/usr/bin/script`），Windows 不支持；无人值守入站返回 `unsupported`；`--force` 可能被团队策略静默降级；模型目录每次刷新都要开一个空 ACP 会话 |
| `kiro-cli` | `codex-host` 侧仅 6 次提交、无专属文档、README 矩阵无该列、无端到端真机验收；`_kiro.dev/*` 扩展被官方标注 experimental；配置写超时会 fault 整个会话并关闭 transport；子代理 `readTranscript: false`；会话存储是嵌套目录而非扁平 JSONL，需实测 |
| `qoder` | 官方 ACP 文档未提及 Fork/回滚，需实测；`codex-host` 侧全部测试 mock 掉 SDK，**无真机验收**；斜杠命令仅 `compact`/`compress`/`summarize` 被标记为 headless 已验证；会话存储位置未知 |
| `hermes` | 新会话优先 gateway，缺 gateway 时 ACP 后备；**两种协议不混用同一会话**；压缩历史不产生 checkpoint，派生明确 unsupported；`inline_diff` 是带 ANSI 且可能截断的显示片段，只能标 fragment；Fork 不支持跨工作目录 |
| `omp` | 必须用 `rpc-ui` 而非 `rpc`，否则内置 `ask` 工具不存在；帧协议含 `rpc_chunk` 分片需新写映射器；子代理投影依赖 RPC 的 `set_subagent_subscription`（服务端默认 `off`），旧版优雅降级；上游迭代极快 |
| `workbuddy` | 2.137.1 对标准 ACP `session/fork` 返回 `Method not found`；模型目录依赖应用私有产品快照，缺失时只有 Fast/Balanced/Primary/Deep 四个 tier；仅 macOS/Windows；文档自陈**危险权限、跨 Harness 委派、压缩及子 Agent 的在线行为尚未验收**；"取消→继续→递归 Fork→关闭恢复"组合仍有未定位问题 |
| `codebuddy` | 上下文压缩需原生事件确认；Fork 通过无模型复制 + 原生 `/fork` + rollback 组合实现；取消后可能残留取消态，必须关闭进程并重新 load 同一会话；提问走版本专属 `_codebuddy.ai/resolveInterruption`；许可为专有 |
| `zcode` | `-p` 模式权限**只能拒不能问**（内部 `createDenyPermissionBroker()`）；`-p` 严格单轮；会话存 SQLite 而非 JSONL；无官方 npm；仓库仅存在约 9 天，版本漂移风险高 |
| `deepseek-harness` | `codex-host` 当前只保留 `modern` 代；支持上限为 `0.1.7-rc.1`，与本项目 0.2 基线代际不对齐 |

`pi` 的权限模式缺口（`codex-host` 明确"没有原生会话权限模式目录，不添加 Host 自行实现的权限引擎"）对本项目已有 `pi` 适配器同样适用，属于既有状态。

## 四、分级结论

### 强烈推荐

**1. WorkBuddy（新增）**

- 理由：已有 `codex-host` 的完整实现与真机验收记录（B 级）；官方 ACP 文档齐全，含 `available_commands_update`、`_meta['codebuddy.ai/userinfo']`、`context_window` 档位与 `_meta['codebuddy.ai/teamUpdate']` Team 事件——最后一项直接服务 spec007 的 Team 成员投影。
- 接入路径：ACP stdio，复用本项目 `JsonRpcProcess` 基座（已有 `grok-driver.ts` 的完整会话/权限/取消流程可参照）。
- 不覆盖：仅 macOS/Windows；模型目录依赖应用私有快照；文档自陈的未验收项需本机复核。

**2. oh-my-pi / omp（新增）**

- 理由：**交互语义被 `codex-host` 完整验证过**，是候选里能力密度最高的一个。`omp-interactions.md` 记录了原生提问映射（`select`/`confirm`/`input`/`editor` → 单选/确认/单行/多行，含 `optionDetails[].description` 选项说明）、工具审批只映射为"一次允许"、以及权限模式切换需重启进程并校验会话身份不变。上游 MIT、33.7k stars、`@oh-my-pi/pi-coding-agent` latest 18.4.3。
- 与已有适配器的关系：本项目已有 `pi` 适配器（`--mode rpc`），omp 是 Pi 生态的增强发行版，用户群几乎重合，RPC 经验可直接复用。
- 接入路径：原生 RPC `omp --mode rpc-ui`，可参照本项目 `pi-driver.ts` 与 `json-rpc-process.ts`。
- 不覆盖：**必须用 `rpc-ui`**（普通 `rpc` 不创建内置 `ask` 工具，模型无法调用提问）；帧协议含 `rpc_chunk` 分片需新写映射器；子代理投影依赖服务端 `set_subagent_subscription` 开关（默认 `off`）；上游迭代极快，协议漂移需持续跟进。

**3. CodeBuddy（新增）**

- 理由：有官方 npm 包（`@tencent-ai/codebuddy-code`，latest 2.159.0），全平台可用，中文用户群重叠度高；`codex-host` 的真机验收最扎实（2.148/2.149/2.151，含真实模型 Fork 验证）。与 WorkBuddy 共用驱动，先抽产品身份参数可以一次接两个。
- 接入路径：ACP stdio `codebuddy --acp`，与 WorkBuddy 同一实现。
- 不覆盖：提问走版本专属私有扩展 `_codebuddy.ai/resolveInterruption`；取消后可能残留取消态，必须关闭进程并在新进程重新 load 同一会话；Fork 需要额外临时 CLI 与管理型 ACP 进程（会在随机端口起原生 HTTP server），失败可能残留；许可为专有（`SEE LICENSE IN README.md`）。

### 值得

**4. Kiro CLI（AWS，新增）**：ACP 协议（`kiro-cli acp --agent-engine v3 --auth-method cli`），与本项目 ACP 基座匹配；面向 AWS 企业合规场景（IAM Identity Center、GovCloud、PrivateLink），差异化明确。`codex-host` 有 15 个源文件与 12 个测试文件。
- 注意：`codex-host` 侧只有 6 次提交、无专属文档、**README 能力矩阵里没有 Kiro 列**，且无端到端真机验收（仅在一个 bug 修复上做过原生复现）。
- 会话存储需要实测：官方文档称会话存在 `~/.kiro/` 的本地数据库，而 `codex-host` 的实现是扫描 `~/.kiro/sessions/<workspace>/<sessionId>/` 下的 `session.json` 与 `messages.jsonl`（**嵌套目录，不是扁平的 `<id>.jsonl`**），因此不能直接套用现有 `probeStoredSession`，需要按该结构适配。

**5. Cursor CLI（新增）**：用户群大；走 `cursor-agent acp`，协议与本项目 ACP 基座匹配。但 `codex-host` 明确标记 experimental，且 ACP 缺 Usage、Fork、压缩，能力明显少于其他候选。
- 注意二进制名：新版安装脚本同时建 `agent`（primary）与 `cursor-agent`（legacy）两个软链，发现时应同时探测两个名字。

**6. Qoder（阿里，新增）**：中文用户群有分量。**官方 CLI 直接支持 ACP**（[官方 ACP 文档](https://docs.qoder.com/cli/acp.md)：`qoder --acp`，stdio，复用 CLI 登录态，支持 `QODER_PERSONAL_ACCESS_TOKEN`），因此**不需要引入厂商 SDK**，可直接复用本项目 `JsonRpcProcess` 基座。
- **不要照抄 `codex-host` 的接入路径**：它走的是专有 SDK `@qoder-ai/qoder-agent-sdk`（许可为 `SEE LICENSE IN LICENSE`，且 `postinstall` 会从网络下载 worker runtime）。本项目当前**零厂商 Agent SDK 依赖**，引入它会同时带来专有许可与安装期网络依赖两个问题。
- 另一个反向证据：`codex-host` 的 README 能力矩阵给 Qoder 标了「Agent 间任务协作」与「斜杠命令」，但它自己的 `docs/qoder-capabilities.svg` 把这两项划掉标 `—`，且全仓源码中找不到对应实现。这是"能力过度声明"的实例，正好印证本 Spec 需求 5 的门槛。

**7. Antigravity（Google，新增）**：走 `agy --input-format stream-json --output-format stream-json`，事件信封与本项目 `StandardStreamDriver` 同构，接入成本最低；续接时通过 `--conversation <id>` 恢复原生会话。
- 两个必须处理的问题：① 它需要**向 stdin 写 prompt**（`{"event":"user","message":{"content":"..."}}`），而本项目 `StandardStreamDriver` 当前用 `stdio: ['ignore', 'pipe', 'pipe']` **不写 stdin**，需要扩展一个 spawn 变体；② 权限**只有 Skip permissions 一档且是新会话默认值**，headless 不接受工具权限回答，因此必须不声明 `permission`，且不得在界面暗示存在权限档位。
- 官方文档未见 `--version`，`detect()` 需另找存活探测方式（如 `agy models`）。

**8. ZCode（Z.ai，新增）**：Apache-2.0 全开源、7.1k stars，`-p --output-format stream-json` 可复用 `StandardStreamDriver`。但四个硬限制：`-p` 权限只能拒不能问（须不声明 `permission`）、严格单轮、会话存 SQLite、无官方 npm 且仓库仅 9 天。建议作为第二阶段单轮接入。

### 观望

**9. Hermes（Nous Research，新增）**：产品定位是"住在 VPS 上、从 Telegram 对话"的通用自主 Agent（60+ 内置工具、Messaging Gateway、Bot Mode），**不是编码 CLI**，与本项目现有 8 个适配器的用户群重叠最低。接入成本也最高：新会话优先 Hermes 专属 `tui_gateway` JSON-RPC（用 Hermes 自带 Python 以 `runpy` 启动），没有可复用基座；ACP 只能覆盖兜底路径，且能力弱（压缩历史无法 Fork、`inline_diff` 只能标 fragment、Fork 不支持跨 cwd）。`codex-host` 自陈**尚未进行真实外部模型压缩或 Desktop 端到端验收**。
- 唯一值得借鉴的是它的兼容策略：**不比较版本号，只验证原生能力**（启动时探测 `gateway.capabilities.per_session_exclusive_submit`），比硬编码版本白名单更稳。

**10. Qoder CN（阿里，新增）**：与 `qoder` 同源（同一 CLI 代码库的两个发行身份，差异只在命令名 `qoderclicn`、配置根 `~/.qoder-cn` 与 token 变量）。官方同样支持 ACP（`qodercn --acp`），因此**应与 `qoder` 一起抽产品身份参数复用同一驱动**，而不是写两套。必须先完成 `qoder` 再做。

**11. Kimi Code（同源，非新增）**：与本项目已有 `kimi` 是同一产品。走 ACP 可补齐权限应答与提问能力（本项目 `kimi` 已声明 `permission` 与 `questions`，走的是 wire 协议 + stream-json 回退）。应作为"`kimi` 适配器的协议路径评估"处理，不新增适配器 ID。

### 不推荐

**deepseek-harness（作外部 Agent 驱动）**

结论：**不推荐接入为外部 Agent 驱动**，但它的四个机制值得抄。

本项目自身运行在 DSH 宿主内，且**已经实现 PeerHost（spec006）**：`src/host/modules/peer-host/peer-host-native-protocol.ts` 已登记 `session/create`、`session/fork`、`session/prompt`、`session/control`、`session/follow`、`session/list`、`session/modelCatalog` 等原生方法，`src/host/remote-web-runtime.ts` 已实现本机 DSH Web 的认证与资源白名单。

`codex-host` 的该适配器本质是"用外部进程起第二个 DSH Web，再当客户端连它"（`dsh web --no-open --host 127.0.0.1 --port 0`，随后走 HTTP unary + WebSocket `/api/remote.mux`）。在本项目里这等于用更重、更外挂的方式重做 PeerHost，属于职责重复。

另外两个硬事实（已核实）：

- **代际不对齐**：该适配器支持的上限是 `0.1.7-rc.1`（`profiles/profile.ts` 的 `V4_MINIMUM = parseSemVer("0.1.7-rc.1")`），代码树里**没有任何 0.2 分支**；而本项目 `version.json` 是 `dshCompatibility: ">=0.2.0-rc.1"`、`dshTestedVersion: "0.2.0-rc.1"`。
- **legacy 代已退役**：PR #242「对接 DSH 0.1.5-rc.1 并退役 Legacy」（2026-09-10 已合并）删除了 Legacy 实现、探测回退与旧 SDK。`generation-selector.ts` 的 `DeepSeekProtocolGeneration` 现在只剩 `"modern"` 一个字面量。注意 `codex-host` 自己的 `.agents/skills/.../current-harness-implementations.md` 仍指向 `legacy/host-client.ts`，属**过期文档**，不要照抄。

**仍有价值的三个场景**：

1. **把另一个 DSH 实例当作被编排的下级 Agent**（远程 worker、委派目标）。但本项目已有 `agent-team.native`、`subagent.continuable` 能力（`src/dsh-capabilities/matrix.ts`），做之前先确认原生路径不够用。
2. **旧版本 DSH 兼容**：若产品要驱动用户机器上遗留的 `0.1.2` / `0.1.5` / `0.1.7`，`codex-host` 的 `profiles/v012.ts`、`v015.ts`、`v017.ts` 是唯一现成参考。但本项目路线是"插件跑在 DSH 内 + 版本路由矩阵"，价值有限。
3. **可抄的机制**（与版本无关，实操价值最高）：
   - Fork 继承队列清理：DSH 原生 Fork 会继承下一回合的待办输入，接纳子会话前须用原生队列接口移除并回读确认。
   - `session.export` HEAD flush 屏障：DSH 有批量写入延迟，直接杀进程会丢失已回滚输入，须先等落盘确认。
   - 版本号只决定"尝试哪套 profile"，真正的兼容闸门是原生协议解析。
   - 认证指纹探测：以 `401` + `cache-control: no-store` + 精确响应体判定"端点上有别人的 DSH Web"。

上述第 3 点建议转成对 `docs/调查报告/` 的补充，而不是新增适配器。

## 六、待实测项

以下事实无法从资料确认，必须在实现前真机验证：

1. 各候选 CLI 在本机的实际命令名与版本（`codex-host` 的观测版本可能已过时）。
2. WorkBuddy 的配置根默认值（上游项目分别用 `~/.workbuddy-ai` 与 `~/.workbuddy`，不一致）。
3. WorkBuddy 内嵌 CLI 路径与版本的稳定性（文档自陈"并非对外承诺的稳定接口"）。
4. 独立 ACP 子进程能否复用桌面应用已有登录态，还是必须在同一配置根下单独执行一次 `/login`。
5. CodeBuddy 的 `--disallowedTools` 精确匹配语义（社区反馈逗号拼接匹配不到，CLI help 却称可以）。
6. ZCode 的 `result.usage` 字段形状、`tool.updated` 的 payload 变体、`message.upserted` 与 `model.streaming` 的结构。
7. ZCode `-p` 模式下 `permission.requested` 是否发出、发出后是直接拒绝还是阻塞。
8. ZCode `app-server --stdio` 的握手细节（`initialize` 必需参数、`--stdio` 是否必需）。
9. Qoder 走 ACP 时的会话存储位置与续接方式（`codex-host` 未实现 `probeSession`），以及 ACP 是否支持 Fork。
10. Kiro 会话存储的真实结构（官方称"本地数据库"，`codex-host` 实现为嵌套目录 + `messages.jsonl`），以决定能否复用 `probeStoredSession`。
11. `kiro-cli acp` 在不带 `--agent-engine v3` 时的默认引擎行为。
12. Cursor 在新版安装下 PATH 上到底是 `agent` 还是 `cursor-agent`（安装脚本同时建两个软链）。
13. `agy` 的版本探测方式（官方文档未见 `--version`）。
14. `deepseek-harness` 适配器与本项目 `spec006` PeerHost 能力的职责边界。
