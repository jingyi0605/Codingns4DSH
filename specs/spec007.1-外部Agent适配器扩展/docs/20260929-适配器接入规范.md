# 外部 Agent 适配器接入规范

日期：2026-09-29
范围：新增外部 Agent 适配器时必须遵守的规则。这些规则来自上一轮调查中发现的真实风险，目的是避免配置互相覆盖、误启动同名程序、以及把未验证能力写成已支持。

本文件是规则性内容，与选型结论（`20260929-适配器选型矩阵.md`）分开：选型回答"接哪个"，本文件回答"怎么接才对"。

## 1. 传输基座选择

本项目只允许三种传输基座，不新增第四套框架：

| 基座 | 位置 | 适用 |
| --- | --- | --- |
| `StandardStreamDriver` | `src/host/cli-adapters/standard-stream-driver.ts` | 子进程 `--print` 类单次执行，stdout 逐行 JSON |
| `JsonRpcProcess` | `src/host/cli-adapters/json-rpc-process.ts` | JSON-RPC / ACP over stdio |
| HTTP/SSE 客户端 | `src/host/cli-adapters/http-sse-client.ts` | 网络端点 |

判断顺序：

1. 输出是逐行 JSON，且事件结构与 Claude Code 同族（`system`/`assistant`/`user`/`result`）→ `StandardStreamDriver`，继承并只覆写 `buildArgs()` 与 `parseEvent()`。
2. 需要可应答的权限、提问、会话级配置或精确回滚 → `JsonRpcProcess`（ACP）。
3. 只有网络端点 → HTTP/SSE。
4. 只有厂商 SDK、没有可用 CLI 协议 → 列为独立决策点，先评估依赖成本，不得默认引入。

**每条路径都必须记录它不覆盖的能力。** 典型例子：`stream-json` 路径下权限请求可能只能被拒绝，此时不得声明 `permission`。

### 1.1 stream-json 基座的已知限制

`StandardStreamDriver` 当前以 `stdio: ['ignore', 'pipe', 'pipe']` 启动子进程，**不向 stdin 写数据**。部分 CLI（已知 Antigravity 的 `agy --input-format stream-json`）要求把 prompt 以 JSON 行写入 stdin 才会开始工作。

遇到这类 CLI 时，需要为基座扩展一个"写 stdin"的 spawn 变体，而不是在驱动里各自 fork 一份进程管理逻辑。扩展时必须同时覆盖：

1. 写入失败（子进程提前退出）时不得挂起，必须有超时或退出事件兜底。
2. 取消时先关闭 stdin 再终止进程。
3. 仍然不把 prompt 放进命令行参数（避免参数长度限制与 shell 转义问题）。

## 2. 产品身份与配置根隔离

### 2.1 同源产品清单

以下产品共用 CLI 代码库但属于不同产品身份，必须分别指定配置根：

| 组 | 配置根环境变量 | 默认根 |
| --- | --- | --- |
| CodeBuddy | `CODEBUDDY_CONFIG_DIR` | `~/.codebuddy` |
| WorkBuddy | `WORKBUDDY_CONFIG_DIR` + `CODEBUDDY_CONFIG_DIR` | `~/.workbuddy-ai`（待实测确认） |
| Qoder | `QODER_*` | 见厂商 SDK |
| Qoder CN | `QODERCN_*` | 见厂商 SDK |
| Kimi / Kimi Code | `KIMI_HOME` 等 | 同一产品，不重复隔离 |

### 2.2 强制规则

1. **多个配置根变量必须指向同一个产品根。** WorkBuddy 必须同时设置 `WORKBUDDY_CONFIG_DIR` 与 `CODEBUDDY_CONFIG_DIR`，否则内置 CLI 的内部默认值会回退到 `~/.codebuddy`，导致历史、认证和设置与普通 CodeBuddy 互相泄漏。
2. **不得依赖 CLI 自身的默认配置根。** 内置 CLI 的默认值可能指向另一个产品的目录。
3. **用户显式指定时采用用户值**；未指定时才使用该产品的默认根。
4. **不得复制、推断或代存桌面应用的登录态。** 认证由外部 CLI 自己完成。若独立进程需要登录，提示用户在该产品自己的配置根下完成一次登录，不发明不存在的认证命令。
5. **不得写入凭据。** Host 存储、日志、错误文本、测试产物中都不得出现 token、环境变量、完整命令行、完整本地绝对路径或原始敏感输入。

## 3. 安装发现与平台边界

### 3.1 发现顺序

1. 用户显式指定的安装目录或命令（环境变量覆盖）。
2. 已知安装根目录（仅填写有官方依据的布局）。
3. PATH 上的候选命令名。

### 3.2 强制规则

1. **只随桌面应用分发、不安装到 PATH 的 CLI，不得回退到 PATH 上的同名程序。** WorkBuddy 是典型例子：应用内置的 CLI 入口名仍是 `codebuddy`，若回退到 PATH 会启动另一个产品的安装。
2. **显式指定路径无效时明确失败，不静默回退。**
3. **不混用不同安装的可执行文件与其内置资源。** 例如桌面应用的启动器必须与其同安装目录内的 CLI 配对。
4. **没有官方分发的平台不猜路径。** 官方仅列出 macOS/Windows 的产品（如 WorkBuddy），在 Linux 上必须给出可解释诊断，而不是尝试推测路径。
5. **发现失败只影响该适配器。** 标记为未安装，其他适配器和默认 DSH 会话不受影响。

## 4. 能力声明门槛

1. **没实测过的不声明。** `descriptor.capabilities` 中每一项都必须能指向一次真实交互。
2. **权限只能被拒绝的路径不声明 `permission`。** ZCode 的 `-p` 模式内部使用 deny broker，调用方没有应答通道，因此该路径不得声明 `permission`。
3. **会让运行无限等待的原生交互必须有规避策略。** 已知案例：CodeBuddy 的 `AskUserQuestion` / `ExitPlanMode` 不受 `--permission-mode bypassPermissions` 约束，会等待一个无法给出的确认从而卡住轮次。接入方案必须显式禁用或规避，不得默认放任。
4. **权限能力只有"全放行"时，必须在选型矩阵和设置页如实说明。** 已知案例：Antigravity 的 `agy` 只暴露 Skip permissions，且这是新会话默认值，`codex-host` 因此明确"不添加工具审批、只读白名单或工作区路径限制"。这种情况不得在界面上暗示存在可选权限档位。
5. **能力缺失只影响对应适配器**，并返回结构化的不可用诊断，不静默伪造成功。
6. **不新增能力枚举值。** 现有 `CodingNsCliCapability` 已覆盖 models/stream/resume/continuable/team-proxy/interrupt/tool-events/reasoning/usage/permission/questions/steer。

### 4.1 真实反面案例：能力过度声明

`codex-host` 对 Qoder 的 README 能力矩阵标了「Agent 间任务协作」与「斜杠命令」两项为支持，但它自己的 `docs/qoder-capabilities.svg` 把这两项划掉标 `—`，且全仓源码中找不到对应的 delegation/MCP 桥实现。这就是"文档写了、代码没有"的典型后果。

本项目的做法：能力清单必须能逐项指向实现位置与验证方式，不允许只改文档。当同一项目内出现两份互相矛盾的能力声明时，**以更保守的那份为准**，并把差异记录为待核实项。

## 5. 会话标识与探测

1. **会话标识来源**：从初始化消息或结果事件中取得，绑定到 DSH 会话，只保存在 Host 会话表，不下发客户端。
2. **探测必须只读。** 不得通过 resume/load/prompt 探测会话是否存在，因为这些调用可能修改 Provider 状态或意外创建新会话。
3. **存储格式不是逐会话 JSONL 时，不得套用 JSONL 校验逻辑。** ZCode 把会话存在 SQLite（`~/.zcode/cli/db/db.sqlite`），需要单独的探测方式或降级为 `unknown`/`ephemeral`。
4. **同源产品的历史目录编码规则可能不同，不得互相复用。** CodeBuddy 把小写化并去除特殊字符，WorkBuddy 保留大小写、点号、空格与 Unicode。
5. **会话丢失或损坏时标记为不可恢复并保留诊断**，不自动重放请求。

## 6. 登记清单

新增一个适配器需要触及的位置（顺序即检查顺序）：

| 步骤 | 位置 | 说明 |
| --- | --- | --- |
| 1 | `src/host/cli-adapters/<name>-driver.ts` | 驱动实现 |
| 2 | `src/host/cli-adapters/feature.ts` | 加入驱动数组（当前 8 个） |
| 3 | `src/host/cli-adapters/model-catalog.ts` | 静态回退模型目录 |
| 4 | `src/client/provider-icons.ts` | 显示名与图标映射 |
| 5 | `src/client/provider-icon-assets.ts` | 图标资产（浏览器入口） |
| 6 | `src/host/cli-adapters/legacy-session-adapter.ts` | 旧会话迁移识别（如需） |
| 7 | `src/host/cli-adapters/provider-registry.ts` | 若该产品同时是模型提供商 |
| 8 | `tests/` | 探测、事件映射、能力缺失、资源释放测试 |

`agentAdapters` 设置是 `Record<string, boolean>`，新适配器 ID 天然可用，无需修改设置契约。

## 7. 回归要求

新增适配器必须满足：

1. 现有 8 个适配器的探测、执行、恢复、权限、提问、中断和释放行为不变。
2. 复用现有 `CodingNsCliDriver` 与注册表契约，不修改已有适配器的行为语义。
3. 适配器 ID 冲突时在注册阶段明确报错（现有实现已具备该行为，见 `CodingNsCliAdapterRegistry` 构造函数的重复检查）。
4. 未安装的适配器不阻塞启动。
5. 通过以下验证：

```bash
pnpm run typecheck
pnpm run version:check
pnpm run capability:check
pnpm test
```

## 8. 同源复用的抽象建议

对于 CodeBuddy / WorkBuddy 与 Qoder / Qoder CN 这两组，建议参照 `codex-host` 的 `CodeBuddyRuntimeProfile` 做法：把差异收敛成一组产品参数（显示名、配置根环境变量、默认根目录、历史目录编码规则、命令目录、平台范围），驱动实现只写一份。

需要抽象的最小参数集见 `design.md` §3.2.1。**不要复制粘贴出两份近乎相同的驱动**，否则后续每次协议变更都要改两处，且容易只改一处。
