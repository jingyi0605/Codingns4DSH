## Findings, most important first

### P1 — The current connector is not an HTTP app runtime

`src/client/html-workspace-files.ts:5` accepts only the custom `codingns.html-files.request.v1` message protocol. `src/host/html-workspace-files.ts:68` dispatches file operations, including UTF-8-only reads. Neither file provides static routes, binary resource responses, MIME handling, ES module URLs, root-relative routing or SPA behavior. A standard HTML app using only ordinary URLs and `fetch()` cannot use this connector without custom integration.

**Action:** implement T1–T3. Keep the earlier helper as migration input, not the app server. Verification must open an unchanged multi-file HTML fixture over real HTTP(S).

### P1 — Browser-memory approval is not the proposed Host grant model

`src/client/html-workspace-files.ts:37` stores grants in a WeakMap, and lines 68–70 forward scopes on each RPC. `src/host/html-workspace-files.ts:48` accepts those scopes without looking up a Host-owned app grant or launch. This was built for a trusted authenticated parent controlling a specific preview; it is not evidence of unauthenticated access. It nevertheless cannot be exposed as a general app HTTP endpoint with the same contract.

The current confirmation approves read/save/delete together. There is no Host read-only launch, operation-specific grant, app revision, expiry, or explicit launch revocation check.

**Action:** T2/T4 must make the Host authoritative and test that direct requests cannot expand approved scope or perform writes through a read-only launch.

### P2 — App lifetime is tied to a conversation and native DOM layout

`src/client/html-workspace-files.ts:20` recognizes a specific native iframe and only `dsh-resource://file/session/...` addresses. `src/host/features/file-management.ts:26` requires a session ID and resolves that session's directory. This does not support workspace shortcuts without a conversation and must not determine a long-lived app root from the currently selected session.

`src/client/features/file-management.ts:14` registers no capability requirement for the native-preview DOM contract. The new design needs explicit version/availability detection in the capability layer.

**Action:** T1/T2/T5 must use Host + workspace + app identity, register the footer entry through the slot adapter, and test opening with no active conversation.

### P2 — Existing file safeguards need adaptation before reuse

`src/host/html-workspace-files.ts:86` checks mtime only when the caller supplies it; deletion at line 104 has no version precondition. This does not satisfy the new requirement for mandatory stale-update/delete protection. Canonical-path checks at lines 60–66 precede entry into the mutation queue at line 111; extraction must revalidate grants and paths at actual execution. Plugin serialization does not lock out external editors or turn filesystem path checks into an OS sandbox.

**Action:** preserve the useful atomic-write/create-only/path-check logic, but add API preconditions and execution-time authorization. Add stale-delete and revoked-queued-write tests.

### P2 — Passing existing tests is not acceptance of the latest plan

`tests/html-workspace-files.spec.ts` uses direct handlers and a stubbed parent window. `tests/peer-host-file-management.spec.ts` verifies owning-session routing. These are valid regressions, but they do not establish HTTP asset loading, app-origin isolation, workspace-only launch, or phone-reachable HTTPS.

**Action:** retain these tests where behavior survives and add the acceptance matrix in design §7. Do not relabel the old tests as Quick Apps HTTP coverage.
