# Host-proxied HTML previews and LAN recovery

Date: 2026-10-16. This report records the repository proxy implementation; no installed profile or service was operated. Later authorized membership-page adaptation and repository commits are recorded in `specs/spec016-快捷应用与受控静态HTTP托管/docs/20261015-实现验收矩阵与剩余条件.md`.

## User decision and corrected scope

The user rejected separate app listeners and selected **Sandboxed preview** in the native question panel. The requested route is browser → existing DSH Host → the shortcut's owning workspace. The user reconfirmed workspace read/create/update/delete access and asked not to add permission steps.

The default on supported DSH is now a sandboxed HTTP path on the existing Host. It requires no app domain, app certificate, reserved port pool or extra listener. HTTPS uses the existing DSH ingress. The previous dedicated-origin providers remain compatibility implementations; they are not the default when the native proxy capability is available.

This decision changes the earlier default transport acceptance criteria. A path is still not a separate URL origin: the iframe and response CSP instead give executing HTML an opaque sandbox origin. Browser localStorage/IndexedDB are unavailable, and root-relative paths still address the DSH root. Relative application URLs, scripts/modules, dynamic imports, CSS, images/fonts, binary bytes and fetch are supported. No source rewriting, SDK, Blob packaging, storage emulation or service worker is added. The native viewer explains this compatibility limit. The external membership page/data were not modified or declared compatible.

## LAN regression

The previous change applied Quick Apps admission rules to normal DSH traffic. It compared public Origin/Referer to a Host header that an existing reverse proxy may have rewritten, rejected external top-level navigation, and used app `uiOrigins` as an allowlist for ordinary LAN addresses. These are source-level reproductions of the reported `Cross-origin DSH access is denied` failure; the installed request headers were not inspected.

The recovery accepts ordinary top-level UI navigation, uses browser Fetch Metadata rather than comparing public origins to an internal Host, preserves existing authentication for HTTP clients without those headers, and limits the old port adapter's additional rejection to known app origins. APIs, frame requests and mutations are not covered by the navigation exception. Login, PeerHost authentication, PWA and WebSocket behavior retain their existing paths. Forwarded headers do not become authority or workspace grants.

## Native Host integration

The pinned [DSH WebServer contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/host/webserver/src/index.ts) supplies prefix registration with no trailing slash, response ownership, a disposer, and `getOrigin()` for the configured listener. `quick-app.proxy` probes these methods at the capability boundary; the three required legacy fixtures report unavailable rather than pretending they support the current route.

`quick-app-proxy-adapter.ts` exposes the native interface; the Host-only `quick-app-proxy-provider.ts` registers one reserved prefix on the existing WebServer. An authenticated launch creates an unguessable, temporary subpath bound to its Host-owned handler. A shared 404 handler prevents expired/unknown launch addresses from falling into the DSH SPA. Closing a viewer, revoking access or disabling Quick Apps removes its launch handlers; Host disposal releases the prefix. No conversations are created.

The route reuses `QuickAppService`, the static handler and the existing file API. It strips DSH credentials and supplies only the selected launch credential internally. The LAN proxy preserves sandbox Origin headers and does not inject its DSH cookie on this reserved route. The app sees neither the internal credential nor a general DSH token. The path is a launch-only bearer address: do not share or log it. The viewer displays the workspace file path instead of that address, and responses suppress referrers and caching.

Workspace access remains the saved `fileAccess: 'workspace'` policy. There are no new per-folder approvals or code-review gates. Existing containment, bounded requests, atomic saves and version checks are reused. Static GET/HEAD does not write. Legacy shortcuts and text editing keep their existing policy.

PeerHost resources are also proxied through the **controlling** Host address. Its saved shortcut chooses the owning Host/workspace. A fixed authenticated `quickApps/remote` action carries bounded resource requests to a target-owned launch; it cannot select an arbitrary upstream URL or grant. The owning provider uses its configured WebServer address, never a browser-supplied target, to read the resource. Binary replies are bounded and encoded for the existing carrier. The controlling Host rewrites only directory redirects to its own launch prefix. General PeerHost credentials remain Host-side. Relay-only PeerHost remains unavailable through the existing carrier.

## File API in the sandbox

The existing API is below the launch's base path. For an entry file at the application root, `fetch('./__quickapp/files?path=data/members.json')` works. For nested entry files, derive the root from the launch address:

```js
const basePath = location.pathname.match(/^\/__codingns\/quick-apps\/[^/]+\//)[0];
const endpoint = basePath + '__quickapp/files?path=' + encodeURIComponent('data/members.json');
const loaded = await fetch(endpoint);
const { content, version } = await loaded.json();
const saved = await fetch(endpoint, {
  method: 'PUT',
  headers: { 'Content-Type': 'text/plain; charset=utf-8', 'If-Match': version },
  body: content,
});
```

No cookie, DSH token or request-supplied Host/workspace is needed. Sandbox CORS and OPTIONS support permit ordinary fetch. Create uses `If-None-Match: *`; updates/deletion retain mandatory versions. The existing remote carrier's 4 MiB envelope limit also applies to serialized write requests.
