## What the platform actually supplies

The pinned [DSH alpha.3 WebServer source](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/host/webserver/src/index.ts) exposes pathname-based exact/prefix registration and optional TLS certificate/key configuration for its listener. Those interfaces do not allocate a separate hostname per application, provision DNS or certificates, or establish a browser credential bootstrap for embedded apps. TLS support exists; verified app-origin provisioning is the missing composition.

The pinned [sidebar contract](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/client/ui-sidebar/src/client/contract/slots.ts) declares `sidebar.footer.action` as a root-scoped list with a `wide` owner property. The new adapter waits for this declaration through `slots.inject` and removes its registration with module disposal. Earlier required fixtures report this capability unavailable.

Repository evidence:

- `src/host/rpc.ts`: authenticated `/codingns` and `/api/codingns/*` management routes are on the DSH carrier. They are suitable for shortcut management, not executable app origins.
- `src/shared/peer-host-http-routes.ts`: PeerHost forwards a fixed set of management API paths, now including the exact Quick Apps remote-management endpoint. Executable app origins are deliberately not proxy paths.
- `src/host/modules/peer-host/host-api-proxy-service.ts`: Host-owned access tokens authorize the existing upstream API proxy. Reusing these tokens in application pages would violate R3.5.
- `src/host/index.ts`: loads the operator-owned HTTPS configuration, creates the dedicated provider, contributes capability facts and disposes it with the Host. Missing/invalid configuration keeps HTML unavailable.

## Implemented boundary

`quick-app.origin` is a capability with an internal, explicitly supplied `QuickAppOriginProvider`. A generic `webServer.register` method does not satisfy it. `quick-app-https-provider.ts` now implements a dedicated lazy TLS listener with fresh random app hostnames, certificate/hostname checks, exact SNI/Host dispatch and a distinct cookie site from the DSH UI. Configuration instructions are in `specs/spec016-快捷应用与受控静态HTTP托管/docs/20261015-独立HTTPS配置与前端入口.md`.

An origin lease must supply its owning Host, privileged UI origin, connection reachability class, host-only cookie name, activation channel, and disposer. Validation rejects shared origins, reuse of an active app hostname, the same hostname on a different port (cookies ignore ports), wrong owning Hosts, remote loopback addresses, and HTTPS-to-HTTP downgrades. These checks constrain a provider; they do not prove a provider's DNS, TLS, routing or cookie implementation.

The new provider exchanges a one-use fragment ticket for a Secure/HttpOnly/host-only/Partitioned cookie, verifies cookie delivery, then navigates to the unchanged entry file. A nonce CSP protects the separate landing page. Ordinary app resources use no injected SDK, bridge or Blob packaging. Only app-scoped credentials enter this channel.

The original `appN.localhost` browser test still uses harness-provided cookies and proves HTTP resource behavior only. The additional actual-launcher test runs the production HTTPS provider, actual React/DSH primitives and bootstrap with third-party-cookie phaseout enabled; it does not inject application cookies. Certificates, DNS mappings, management authentication, workspaces and browser profiles remain disposable test fixtures.

The PeerHost continuation uses the actual `PeerHostHttpProxyService` over local HTTP management servers, then the target Host's HTTPS app origin. It verifies target-owned grants and that writes change only the target workspace. The target management fixture authenticates a test token; this does not verify installed DSH/LAN authentication.

## Enforced resource limits

| Resource | Limit |
| --- | --- |
| Text read/write body | 4 MiB UTF-8 |
| Single static resource | 64 MiB, streamed in 64 KiB chunks |
| Concurrent requests per launch | 8 |
| Pending/active launches | 32 per feature instance |
| Origin reservations | 1024 per module lifetime; retired hostnames are never reused |
| Launch lifetime | 30 minutes, checked on access; no expiry polling |
| One-use bootstrap ticket | 60 seconds |
| Code trust check | 4096 entries, 32 directory levels; request-time metadata checks |
| TLS handshake / listener connections / header bytes | 10 seconds / 256 / 16 KiB |
| Remote listing | Four concurrent requests, 15-second overall deadline |
| HTTP request lifetime | 30 seconds |
| Shortcuts / mounts / roots per operation | 200 / 8 / 8 |
| Explicit directory listing | 1000 entries |

Responses use `Cache-Control: no-store`; cached validators never bypass authorization. Downloaded bytes cannot be recalled. Range/media streaming, public sharing, workers and offline behavior are not claimed.
