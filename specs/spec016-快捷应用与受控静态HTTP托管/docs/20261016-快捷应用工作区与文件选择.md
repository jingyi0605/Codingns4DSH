# Quick Apps workspace dropdown and visual file selection

Date: 2026-10-16.

## User-visible behavior

Adding or editing a shortcut uses the built-in DSH `Menu` dropdown for workspaces. Each choice displays its workspace name, owning Host and available path. The list follows the native workspace store; selection keys contain both Host and workspace identity, so reordering the list or duplicate workspace IDs cannot change the selected source. Changing the workspace clears the previous entry, application folder and resource mounts.

After choosing a workspace, **Browse…** opens a visual file selector. It lists folders first, uses the native folder/file icons, supports folder navigation and breadcrumbs, and confirms a selected file with **Use this file**. Cancel/Escape keeps the previous entry and returns focus to Browse. New shortcuts infer their application folder, HTML/text kind and default title from the selected file. The original path field remains available for direct entry and for Hosts lacking the browsing capability.

The inline app grid remains directly above Settings. Browsing neither opens nor creates a conversation and does not change file grants or source files.

## Reused native interfaces and adaptation

The pinned DSH implementation was inspected before integration:

- [Native directory chooser](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/client/ui-directory-picker-browse/src/client/DirectoryBrowser.tsx): selects directories and can create folders; it cannot select a file.
- [Native workspace file panel](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/client/ui-sidebar-files/src/client/FilesBody.tsx): its UI requires a conversation tab and routes file clicks to a viewer.
- [Native Host workspace file service](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.3/packages/api/workspace-files/src/index.ts): `workspaceFiles.list(scope, path, signal)` uses the resolved `workspaceRoot` for directory listing, containment and filesystem permissions. Its list implementation does not consume the scope's session ID.

The plugin reuses that Host listing service through `src/dsh-capabilities/host/workspace-directory-adapter.ts`, together with existing `DshMenu`, `DshModal`, folder and file-icon primitives. It supplies a root resolved by the Host's exact workspace registry, without fabricating a session ID. The selection dialog is a small plugin component over these native services; it is not the native conversation file panel transplanted into a fake conversation. No browser-local upload picker, copied upstream browser implementation, directory creation endpoint or watcher was added.

The new `workspace.directory-list` capability is registered for the inspected `0.2.1-alpha.3` contract. Missing services and the required older fixtures have explicit unavailable diagnostics. Quick Apps declares an optional/degrade dependency: browsing reports a localized unavailable message while direct path entry and existing shortcuts continue working. Capability matrix, route and generated report are updated.

## Host and path boundaries

- `quickApps/browse` is an authenticated management RPC, never an app-origin file API. Selecting a file grants no read/write/delete permission to the application.
- The Host resolves the exact managed workspace. Request-supplied roots and principal fields are not used as authority. Absolute/traversing/ambiguous paths, hidden or secret paths and symlink traversal are rejected before native listing.
- Results contain names, relative paths and kinds, capped at 1000 entries with a truncation notice. Unknown kinds and private entries are omitted. Workspace ownership/root/path and cancellation are checked again before returning results.
- A 15-second bound, connection abort and module disposal cancel native reads. The UI ignores stale replies after changing directories/Hosts or closing the picker.
- PeerHost browsing uses the existing fixed authenticated Quick Apps management carrier. The controller verifies virtual workspace ownership; the gateway checks explicit workspace visibility and pins the target workspace ID. The target resolves its own local registry and uses its own native listing service. No remote path is interpreted on the controlling Host.

## File-loading failure follow-up (2026-10-16)

The reported phone screenshot shows **“The shortcut no longer exists.”** while adding a shortcut. This string originates in `QuickAppRegistry.get`, not in workspace listing. The current `browse` branch precedes shortcut lookup and successfully lists files without any saved shortcut through both registered Fetch RPC routes. An earlier handler that does not recognize `browse` falls through to `registry.get('')` and produces exactly this misleading error. This is evidence consistent with a browser/loaded-Host mismatch, not confirmation of which code the running Host has loaded. No installed profile or running Host was inspected, modified or restarted.

A separate source integration defect was reproduced: direct `ctx.workspaceFiles` access throws `without inject` in a real Cordis plugin context whose injection chain omits that service. Earlier plain-object service fixtures did not exercise this boundary. Before the fix, the new real-Cordis regression reported the capability as unavailable even though its provider was active. The adapter now uses the supported `ctx.get('workspaceFiles')` access and resolves the provider again for each listing, so it cannot retain a disposed provider. Host composition uses a separate optional injection lifecycle for late provider startup and disposal; the other feature modules do not depend on that provider's availability.

Unsupported Quick Apps operations now return `CODINGNS_RPC_NOT_FOUND` before any shortcut lookup. During browsing only, the client translates both that result and the legacy `QUICK_APP_UNAVAILABLE` result into a localized Host update/reload message. Genuine missing-workspace errors retain their own result. The picker never enables file confirmation after a failed listing, and direct path entry remains available.

The regressions failed before the fixes and pass afterward (`data/build/review/spec016-browse-before.log`). Verification for this correction:
