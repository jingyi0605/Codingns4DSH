# Simplified workspace access for HTML Quick Apps

Date: 2026-10-16.

## User decision

The user requested a simpler workspace boundary and selected **read/write/delete by default** in the native question panel. Saving a new HTML shortcut now authorizes reads, creation, updates and deletion of ordinary files in its saved owning workspace. This explicitly supersedes the original per-path approval default in R3/R4. “Workspace” means the shortcut's saved Host/workspace, never whichever conversation is currently selected.

Existing shortcuts are not silently expanded. Their access remains unchanged until the user saves them with the visible **Save and allow workspace access** action. The form names the workspace and describes all four operations. Newly created HTML shortcuts show the same explanation beside their source settings. Text-document edit approval is unchanged.

## Implemented simplification

- Removed the three read/write/delete path fields and separate permission dialog from the current frontend.
- Persisted one optional `fileAccess: 'workspace'` policy in authenticated shortcut metadata. The owning Host derives the three API scopes from that policy; request-supplied Host/workspace/scopes cannot replace it.
- Workspace mode skips application-code scans and code-change reapproval. Ordinary HTML/JS updates do not cancel workspace access. Legacy scoped approvals and their old behavior remain available through the existing RPC for compatibility; no interface was retired.
- Revoke invalidates active launches and removes the persisted workspace policy, including when the entry file is missing. Reopening does not restore it. Old remote Hosts must acknowledge support before the new policy is saved.
- Clicking an unavailable tile now explains its status instead of silently disabling the button. This does not attempt an unsupported launch.

Static URL mapping remains the application folder plus explicit mounts. The optional HTTP file API covers ordinary files throughout the owning workspace. Browser origin isolation, app-only authentication, exact Host routing, path/encoding/symlink checks, hidden/credential-file exclusions, version preconditions, create-only semantics, bounded requests, atomic writes, execution-time checks and lifecycle cleanup remain automatic. These checks prevent access outside the selected workspace and protect against lost writes; users no longer configure individual operation paths.

The API is still explicit: permission to save does not automatically translate an HTML page's download, browser directory picker or legacy bridge into Host writes. No membership HTML or real data was modified.

## Bug found during verification

A new create-then-delete test exposed an existing create-version bug. Create-only writes used a temporary hard link, calculated the returned version, then removed the temporary link. Removing the link changed `ctime`, immediately making the returned version stale. The file service now removes that link before calculating the successful response version. The test confirms that the returned version matches a subsequent read and can immediately authorize deletion.

## Remaining transport prerequisite

The reported `!` was confirmed as **no isolated app address**, which occurs before HTML execution. Workspace permission simplification does not provision the separate HTTPS app endpoint. The current transport still needs valid operator configuration, reachable DNS/TLS and a matching UI origin. Its separate-cookie-domain restriction is an implementation choice of that transport; a workspace filesystem boundary alone does not replace browser isolation from DSH credentials and privileged UI.

T2/T4/T5 repository behavior is updated to the user-selected policy. T1/T6/T7 retain their production transport, installed/mobile/real PeerHost and legacy-consolidation prerequisites. Local fixture success does not close those acceptance items.
