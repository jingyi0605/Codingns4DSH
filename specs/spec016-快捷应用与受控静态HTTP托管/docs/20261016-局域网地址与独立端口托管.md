# Reuse the LAN address with separate app ports

Superseded approach (2026-10-16): the user rejected separate app ports and selected Host-proxied sandboxed previews. This document preserves the earlier provider's implementation history; its certificate and port prerequisites are **not** prerequisites for the current default. The associated normal-LAN regression is corrected and documented in `specs/spec016-快捷应用与受控静态HTTP托管/docs/20261016-主机代理预览与局域网回归修复.md`.

Date: 2026-10-16. Scope: repository source, disposable local fixtures and documentation. No installed Desktop, dsh-web or Stage0 profile was operated. The membership HTML and real membership data were not read or changed in this implementation.

## Decision and visible behavior

Quick Apps now has an optional `lan-ports` transport. It accepts the existing LAN hostname or a literal IP address; a new domain, wildcard DNS and a wildcard certificate are not required. Each launch receives its own HTTPS port and serves its workspace application at `/`. The native Quick Apps grid, text/Markdown viewer, editor and HTML viewer remain in place.

The existing domain-based HTTPS provider remains compatible. Both providers use the same one-use credential landing page, with no modification of application source. New HTML shortcuts retain the user-selected workspace access policy; the transport adds no permission form or per-file approval.

This implements the separate-port plan, not a path-prefix route on the privileged DSH port. An exact shared scheme/host/port would still share the DSH browser origin. The current LAN proxy uses HTTP behind any external TLS ingress; it cannot discover or reuse an external proxy's private key automatically. Certificate paths and reachable app ports remain operator-owned deployment inputs.

## Configuration

Keep using the Host startup variable `CODINGNS_QUICK_APPS_HTTPS_CONFIG`, pointing to an absolute JSON file. A LAN example is:

```json
{
  "transport": "lan-ports",
  "publicHost": "192.168.1.20",
  "uiOrigins": ["https://192.168.1.20:14443"],
  "ports": [15000, 17047],
  "stateDirectory": "/operator/quick-apps/used-ports",
  "certFile": "/operator/tls/fullchain.pem",
  "keyFile": "/operator/tls/private-key.pem"
}
```

For the previously shown `https://dsh-dev.jacksonz.cn:14443` connection, `publicHost` can instead be `dsh-dev.jacksonz.cn`, with that exact UI origin in `uiOrigins`. The certificate must cover that existing hostname. This is an example, not a claim about the running deployment. Literal IP access requires a certificate with the matching IP Subject Alternative Name and browser trust. A certificate covering only a DNS name does not cover its IP address.

- `publicHost` is the browser-facing address of the file-owning Host. IPv6 literals use brackets. Loopback, unspecified addresses, userinfo, URL paths and noncanonical host forms are rejected.
- `uiOrigins` lists exact HTTPS DSH origins whose requests reach this protected LAN proxy. Preserve their original HTTP Host header through the UI's TLS ingress. Native opaque/file origins are unsupported.
- `ports` is an inclusive range reserved for Quick Apps, between 1024 and 65535, with at most 16,384 ports. It must exclude the DSH UI port. Public and listening app ports are identical in this mode.
- The app listeners reuse the active LAN proxy's bind address. They start lazily on app launch, serve only Quick Apps, and never forward requests to DSH. Enabling this configuration without starting LAN access produces a specific unavailable diagnostic.
- The browser must reach every chosen app port on `publicHost`. An existing proxy/NAT forwarding only port 14443 does not expose these additional ports. Use direct LAN routing or separately provisioned TCP/TLS passthrough for the app port range. Generic TLS-terminating HTTP proxy configurations have not been validated.
- This mode supports HTTPS. It does not downgrade an HTTPS DSH page to plain HTTP or install a certificate authority. HTTP-only LAN hosting is not implemented by this change.
- Keep `stateDirectory` in durable Host-owned storage. The Host creates private reservation files there; it does not put credentials or workspace data in them. Do not delete, replace, roll back or relocate this history to recover ports. Extend the range instead.

The source configuration loader does not edit running profiles, obtain certificates, change DNS, expose firewall ports or restart services. Applying this configuration to an installed instance is a separate operation requiring authorization for that target.

## Why separate ports also need a request boundary

Browser origins include the port, but cookies do not. The LAN mode therefore uses:

1. A unique Secure/HttpOnly/Partitioned app cookie name for each launch. Its one-use bootstrap ticket arrives through authenticated management RPC and is exchanged inside that app origin. No general DSH token appears in the bootstrap URL or HTML.
2. Exact Host checking on each app port, plus SNI checking when supplied. IP TLS does not depend on SNI.
3. An origin check on every app resource/API request, before credentials, files or cached responses. Only the credential landing page accepts cross-origin navigation. `Origin` and Fetch Metadata must identify the exact app origin; a same-origin Referer is a fallback when Fetch Metadata is absent. Clients suppressing all three signals fail closed. Referrers are limited to the same origin.
4. Removal of general Cookie and Authorization headers before the request reaches the app file service. Only the current launch's cookie survives. App response headers cannot expose general credentials.
5. A guard on the privileged LAN proxy before its existing Host/Origin rewrite, including WebSocket upgrades and loopback ingress behind a TLS proxy. Browser calls from app ports cannot borrow the DSH session. A typed/bookmarked `/` entry remains available; ordinary same-origin UI requests and verified PeerHost bearer routes retain their existing forwarding behavior. Basic rejection of foreign browser Origin/Referer/Fetch Metadata remains active even without port-mode configuration, so old app pages cannot borrow DSH authentication after configuration removal. Port mode additionally requires positive same-origin evidence and the configured UI address. Existing non-browser carriers retain their authentication path.

The entry URL and static resource bytes stay ordinary HTTP(S). Scripts, ES modules, dynamic imports, root-relative paths, CSS, fonts, images, binary responses and `fetch()` keep the existing static handler. The optional file API retains workspace containment, read/write/delete policy, version preconditions and execution-time revocation checks.

## Ports, revocation and cleanup

Each launch atomically reserves a previously unused port in durable storage. A closed app page can remain open in a browser; reassigning its origin would let that page inherit later cookies. For that reason, reservations survive close, revocation, module disable and Host restart. Busy ports are skipped without being consumed. Independent providers using the same state directory race through exclusive file creation, so only one can reserve a port.

This is a finite pool. Exhaustion is explicit and requires extending the range; it never falls back to a shared origin. Existing limits of 32 simultaneous launches and 1,024 origin allocations per Quick Apps service lifetime remain. A larger configured range allows further fresh ports across service lifetimes, not unbounded concurrent listeners.

Closing a launch closes its listener. Stopping/restarting LAN access closes all app listeners and makes previous launch URLs unavailable. Existing launch metadata remains subject to its original expiry/disposal; it cannot reactivate a closed listener. Port history remains durable. No polling, watcher or port-recycling job is added.

## PeerHost

The authenticated management carrier still selects the owning Host and exact workspace. The target serves its own app ports at its configured `publicHost`; the controlling Host is not substituted as the file owner. For port-mode remote launches, the controlling LAN connection must also have the origin guard. Unprotected controllers report an unsupported connection and close a rejected target launch.

The browser must reach the target's app ports. The existing PeerHost management relay is not a general app proxy. Relay-only transport remains unsupported. Source tests and a real local HTTP management carrier with target HTTPS resources cover the routing; installed PeerHost connectivity remains unverified.
