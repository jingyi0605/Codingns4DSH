# DSH 能力注册与版本路由技术规划

日期：2026-09-25

## 1. 当前基线

| 版本 | 事实 | 处理定位 |
| --- | --- | --- |
| DSH `0.1.5-rc.3` | 当前兼容范围下限；部分 Sidebar/终端扩展能力缺失 | 走旧能力适配器和显式降级 |
| DSH `0.1.6-alpha.2` | 当前插件实际依赖和完整验证基线 | 走当前 SettingsScope/旧 Connection/UI 路由 |
| DSH `0.1.7-rc.2` | 截至 2026-09-25 最新可用 0.1.7 线路版本；没有稳定 `0.1.7` | 目标新能力路由 |

当前插件 `0.1.1` 已临时允许安装到 0.1.7，声明范围为：

```text
>=0.1.5-rc.3 <0.1.8-0
```

当前 0.1.7 仅进入实机测试阶段；`version.json` 的实际测试基线仍是 `0.1.6-alpha.2`，完成真实 0.1.7 回放后再宣称正式兼容。

## 4. 路由优先级规则

同一能力的候选路由按以下顺序选择：

1. DSH 版本范围匹配。
2. 运行时 `detect` 成功。
3. `status: supported` 优先于 `deprecated`。
4. 更高 `priority` 优先。
5. 同优先级仍有多个候选时失败，不随机选择。

版本号只负责初筛，最终选择必须通过实际 Context 能力探测。这样可以处理同一 DSH 版本的不同 Profile 或注入组合。

## 5. 版本与能力的区别

不能把所有版本差异压缩成一个 `isDshVersionAtLeast`：

- DSH 版本表示宿主发行版本。
- 能力 ID 表示某个公开接口是否可用。
- 能力路由表示该接口如何适配。
- Feature 版本表示 CodingNS 自己的业务模块版本。
- Transport/Typert 协议版本表示数据契约版本。

只有能力注册表可以把它们关联起来；业务模块不得把 DSH 版本当作 API 能力本身。

## 6. 旧接口退休账本

每个旧路由都要登记：

| 字段 | 示例 |
| --- | --- |
| 路由 | `settings-scope` |
| 替代路由 | `config-forms` |
| 首次引入 | `0.1.5-rc.3` |
| 弃用版本 | `0.1.7-rc.2` |
| 可移除条件 | 插件最低 DSH 版本 `>=0.1.7`，且三版本矩阵不再要求旧路由 |
| 当前使用者 | `settings.store` adapter |
| 删除证据 | 类型检查、静态引用扫描、三版本测试矩阵 |

删除旧路由前必须更新：

- `version.json`
- `package.json` 的 `engines.dsh` 和 peer dependency
- 所有 DSH 包版本
- 能力矩阵
- Feature 需求声明
- 兼容性报告
- 测试 fixture 和 manifest 测试

```json
  "capability": "settings.store",
  "routeId": "config-forms",
  "status": "ready",
```

```json
  "status": "unavailable",

  "features": ["remotePeerHost"]
}
```

## 8. 开发者扩展标准

新增一个功能模块时，必须按以下顺序：

1. 只选择现有能力 ID；没有对应能力时先新增能力定义和内部接口。
2. 在 Feature descriptor 中写 `requires`，不能写散落的 DSH 版本判断。
3. 通过 `context.services.capabilities.require()` 获取服务。
4. 在能力矩阵中登记支持范围、降级行为和模块使用者。
5. 为至少一个支持版本和一个缺失能力场景增加测试。
6. 更新 Spec 任务和兼容性文档。

禁止事项：

- 在业务 Feature 内新增 `if (dshVersion ...)`。
- 直接导入已经标记 deprecated 的 DSH 类型。
- 通过 `as any` 绕过能力注册表。
- 让一个能力 ID 在不同版本返回不兼容的数据结构。
