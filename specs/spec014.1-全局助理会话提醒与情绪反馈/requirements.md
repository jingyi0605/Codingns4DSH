# 需求文档 - 全局助理会话提醒与情绪反馈

状态：In Progress（源码阶段 0—3 已完成，阶段 4 实机验收待执行）

## 简介

全局智能助理已经提供统一形象、网页悬浮入口和原生伴随窗口，但形象状态主要由实时语音驱动。用户希望不必逐个查看会话，就能从助理的气泡和表情获知本轮完成、运行出错或需要自己回答的问题，并快速返回对应会话。

本功能复用 CodingNS 已管理的会话与形象。StatusLight 的气泡、状态表情及会话导航提供交互参考；通知事实和控制边界由本项目持有。

## 术语表

| 术语 | 含义 |
| --- | --- |
| System | 本项目 Codingns4DSH 的全局智能助理与通知组件 |
| Host（宿主） | 承载会话、事件、认证与通知状态的进程 |
| Client（客户端） | 展示助理、气泡和会话导航的主页面 |
| 受管范围 | 助理配置中明确选择的工作区及其可见会话 |
| 通知 | 由真实运行事件产生、有稳定身份的会话提醒 |
| 本轮完成 | 一次回复或执行轮次正常结束，不等于整个项目目标完成 |
| reaction（情绪反馈） | 成功、担忧、疑问、审批提醒等可选形象反馈，与语音动作独立 |
| PeerHost（远端宿主） | 通过既有聚合与路由能力连接的另一台 Host |
| 伴随窗口 | 原生透明悬浮窗口，只展示形象和受限交互数据 |

## 范围说明

### 本次覆盖

- 本地 DSH、已投影到 DSH 的外部 Agent，以及受管 PeerHost 会话的事件提醒。
- 完成、错误、提问和审批四类气泡，队列、未读标记及关闭提醒。
- 现有形象的可选情绪反馈、网页与原生窗口共用展示，以及通话字幕共存。
- 点击提醒打开正确会话；提问和审批仍由现有原生组件处理。
- 配置、兼容性、生命周期、免构建源码验证及分平台实机验收。

### 本次不覆盖

- 自动回答、自动批准、自动重试、自动续跑、上下文迁移和新建项目会话。
- 安装 StatusLight、复制其角色素材或增加独立宠物管理系统。
- 系统通知推送、主动语音播报、模型生成每条通知文案和长期通知历史存储。
- 自动安装或重启 Desktop、主动构建或启停开发服务器、提交或发布。

## 需求

### 需求 1：通知范围与身份

**用户故事：** 作为管理多个项目的用户，我希望助理只提醒已授权范围内的会话，以便每条提醒都能准确关联项目和设备。

#### 验收标准

1. WHEN 模块已启用、助理已创建且通知已开启 THEN System SHALL 仅接收受管工作区中非归档、非占位会话的通知。
2. WHEN 两台 Host 使用相同会话 ID THEN System SHALL 按 Host 和会话联合身份隔离通知、去重和导航。
3. WHEN 同一个请求被原生会话桥、状态事件或重连再次报告 THEN System SHALL 合并同一逻辑事件，不重复创建通知。
4. WHEN 移除受管工作区、归档会话、移除远端 Host、重置或停用助理 THEN System SHALL 撤销对应通知及在途更新，迟到结果不得恢复旧范围。
5. WHEN 已确认属于受管父会话的子智能体请求需要用户处理 THEN System SHALL 归并到父会话提醒并保留实际请求归属；普通子智能体完成不单独刷屏，无法确认父会话归属时不得猜测展示。

### 需求 2：准确识别完成、错误和待处理请求

**用户故事：** 作为执行任务的用户，我希望提醒来自真实状态，以便不会把停止或失联误认为成功。

#### 验收标准

1. WHEN 运行协议明确证明本轮正常结束 THEN System SHALL 创建本轮完成通知；兼容已确认的外部 Agent 正常结束投影，不宣称整个项目完成。
2. WHEN 轮次报告明确运行失败 THEN System SHALL 创建错误通知，并在有可展示原因时附短摘要。
3. WHEN 用户手动停止、取消执行、工具步骤结束、模型输出截断或连接失联 THEN System SHALL 不生成本轮成功通知；未知终态保持未知。
4. WHEN 收到当前有效的提问或审批请求 THEN System SHALL 按请求身份创建待回答或待审批通知，不从 `running`、历史文本或 LLM 摘要推断等待。
5. WHEN 请求回答、批准、拒绝、取消或失效 THEN System SHALL 只结束对应请求的提醒，不能清除同会话的其他有效请求。

### 需求 3：气泡、未读和队列

**用户故事：** 作为同时运行多个会话的用户，我希望助理清楚地提醒需要关注的事项，以便完成通知不会盖住等待我回答的问题。

#### 验收标准

1. WHEN 产生可展示通知 THEN System SHALL 显示工作区、会话标题、固定模板短文案和「查看会话」入口，远端来源明确标注 Host。
2. WHEN 多条通知竞争展示 THEN System SHALL 按待回答/待审批、错误、完成的优先级选择主要气泡，同级按时间顺序展示，并提供未读数量及列表。
3. WHEN 完成或错误通知超过默认展示时间 THEN System SHALL 收起主气泡并保留未读记录；默认完成 5 秒、错误 8 秒，时间从本次实际展示开始计算。
4. WHEN 待处理请求尚未结束 THEN System SHALL 保留提醒；用户关闭气泡后收起为标记，不能把关闭提醒解释为回答、批准、拒绝或取消。
5. WHEN 主页面刷新或通知快照重复返回 THEN System SHALL 不重播已展示的完成和错误气泡；Host 重建时仅恢复当前有效请求，不回放历史完成记录。
6. WHEN 气泡展开、关闭或翻页 THEN System SHALL 保持形象位置稳定，气泡操作与形象拖动互不误触。

### 需求 4：会话导航与交互边界

**用户故事：** 作为收到提醒的用户，我希望一次点击就返回对应会话，以便继续查看结果或处理问题。

#### 验收标准

1. WHEN 点击气泡的「查看会话」 THEN System SHALL 使用通知绑定的 Host、工作区和会话导航，而不是当前页面选择。
2. WHEN 点击形象本体 THEN System SHALL 沿用打开全局助理的行为；拖动结束不得触发任一打开操作。
3. WHEN 从原生悬浮气泡打开会话 THEN System SHALL 恢复当前 Desktop 主窗口并导航到目标，不额外弹出助理工作台。
4. WHEN 目标不再受管、已归档、远端不可达或请求已失效 THEN System SHALL 显示实际原因，不回落本机、自动恢复归档或发送消息。
5. WHEN 用户处理提问或审批 THEN System SHALL 复用现有原生问题和审批组件，不在气泡中创建第二套回答或批准通道。

### 需求 5：可选情绪反馈与旧形象兼容

**用户故事：** 作为使用自选形象的用户，我希望角色用已有表情表达提醒，以便不换角色也能看懂状态。

#### 验收标准

1. WHEN 会话通知产生情绪反馈 THEN System SHALL 将其与现有六种语音动作分别表示，正常语音状态不被业务终态覆盖。
2. WHEN 形象声明对应图片、精灵图动作、Live2D 动作或可用表情映射 THEN System SHALL 在现有实例上更新反馈，通知变化不重新下载素材或重建模型。
3. WHEN 形象缺少情绪素材、引擎表情接口不可用或旧扩展忽略新属性 THEN System SHALL 继续显示气泡与状态角标，不要求用户更换形象或修改旧包。
4. WHEN 通知收起、请求结束或更换角色 THEN System SHALL 按当前有效通知和语音状态恢复展示，迟到反馈不得作用于新角色。

### 需求 6：网页、原生悬浮与实时通话共存

**用户故事：** 作为使用语音和悬浮助理的用户，我希望提醒始终可读，以便它不会打断通话或挡住字幕。

#### 验收标准

1. WHEN 网页或原生悬浮形象显示通知 THEN System SHALL 复用同一气泡组件、文案和通知身份；原生展示期间不生成第二份网页形象。
2. WHEN 正在实时通话 THEN System SHALL 保留语音动作、计时、静音、设备和租约状态，通知使用独立紧凑区域且不覆盖字幕。
3. WHEN 主窗口隐藏或最小化且原生窗口正常运行 THEN System SHALL 继续在原生形象旁显示收到的提醒，不能因页面不可见而停止原生通知同步。
4. WHEN 开关、气泡尺寸、屏幕位置或 DPI（显示缩放比例）变化 THEN System SHALL 保证形象和气泡可见可点击，展开不推走形象，收起不保留大块透明点击遮挡。
5. WHEN 原生窗口不可用 THEN System SHALL 沿用页面回退和可诊断原因；不同步重复通知、不自动安装系统组件。

### 需求 7：PeerHost 与重连

**用户故事：** 作为跨设备工作的用户，我希望远端提醒与本地一样准确，以便能处理另一台机器的会话。

#### 验收标准

1. WHEN 受管远端提供实时通知与交互协议 THEN System SHALL 按远端身份接入事件并保留连接代次，使用既有认证和虚拟 ID 路由。
2. WHEN 远端只有会话状态摘要 THEN System SHALL 不把 `running=false` 或空闲摘要推断成成功，也不读取整段历史模拟实时提问；明确展示来源能力不足。
3. WHEN 一个远端断线 THEN System SHALL 撤销该连接的交互可操作性，不把断线报成会话失败，其他 Host 和本机通知继续可用。
4. WHEN 远端重连并重新投递同一有效请求 THEN System SHALL 更新其可操作路由并合并逻辑提醒，拒绝旧代次的点击和迟到答案。
5. WHEN 远端明确不支持所需协议 THEN System SHALL 停止重复探测同一不支持错误；连接或能力代次变化后才重新核对。

### 需求 8：配置与生命周期

**用户故事：** 作为希望控制提醒频率的用户，我希望能关闭某类提醒，以便助理符合我的工作习惯。

#### 验收标准

1. WHEN 编辑助理配置 THEN System SHALL 提供通知总开关及完成、错误、提问、审批四类开关，沿用统一草稿、底部保存、取消和写入权限。
2. WHEN 旧设置没有通知字段 THEN System SHALL 使用兼容默认值；只有模块启用、助理创建及悬浮开关条件满足时才展示气泡，不自动开启悬浮或语音。
3. WHEN 关闭通知、对应类型或悬浮显示 THEN System SHALL 收起对应气泡和情绪，原生问题与审批仍保持原行为；重新开启不回放关闭期间的历史完成通知。
4. WHEN 重置、卸载或范围变化发生 THEN System SHALL 清理通知订阅、定时器、主页面动作与所有者状态，不影响会话执行或已有聊天历史。

### 需求 9：性能、验证与证据

**用户故事：** 作为日常使用助理的用户，我希望提醒轻量且可靠，以便多会话和大模型形象不会拖慢工作台。

#### 验收标准

1. WHEN 收到通知事件 THEN System SHALL 在当前事件处理周期更新 Host 通知快照；正常通信下网页展示同步目标不超过 1 秒，原生不超过 2 秒，分别记录源码和实机证据。
2. WHEN 通知刷新 THEN System SHALL 使用修订号和有界元数据，不触发 LLM 索引、不读完整会话正文、不为每个会话增加独立轮询。
3. WHEN 检查最近通知 THEN System SHALL 限制已结束通知数量并分页读取，未处理请求不得因历史容量淘汰而丢失；错误摘要和正文有长度限制。
4. WHEN 用户通过键盘、触摸或减少动态效果设置操作 THEN System SHALL 保留可访问文本、按钮焦点与滚动，不仅依靠颜色表达状态。
5. WHEN 执行源码验证 THEN System SHALL 使用免构建加载和替身回放，覆盖去重、终态、请求身份、跨 Host、迟到回调与旧接口兼容；未做的浏览器和双平台实机验收保持未完成。
6. WHEN 执行实机、构建、启停、安装或发布相关动作 THEN System SHALL 遵守仓库现有授权边界；本 Spec 启动不构成这些动作的授权。

## 成功定义

- 四类事件均可从真实来源准确进入气泡；误报成功、同一事件重复提醒和跨 Host 错跳为零。
- 旧形象、语音动作、字幕、原生交互与设置保存继续可用。
- 需求、设计、任务与验证证据逐项对应；源码完成和实机完成分别记录。
