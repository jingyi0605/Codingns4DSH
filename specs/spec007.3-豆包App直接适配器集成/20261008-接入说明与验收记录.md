# 豆包 App 接入说明与验收记录

## 1. 当前实现

适配器 ID 为 `doubao`，名称为“豆包 App”。通过现有外部 Agent 集成开关和模型选择器接入，产品档位为快速、专家、工作任务（云端）。不需要安装 doubao-cli，不新增 npm 依赖，也不是豆包 API Key 提供商。

已实现：独立会话创建、文本流、专家思考流、联网搜索及来源、网页读取、加载进度、云端操作输出、文件产物元数据、通用工具观察、原会话续聊、只读存在性探测、普通回答停止。工具观察只表示豆包云端工作及进度，不会让 DSH 再执行同一个工具。

产物首版展示名称，并提示在豆包 App 对应的 `CodingNS …` 会话中打开或下载。签名下载 URL 不写入工具记录；本期没有实现产物自动下载到工作区。

## 2. 运行前提与配置

豆包必须已登录，调用期间保持运行，且有可访问的原生后台页与回环调试端口。默认端口为 `9225`，只连接 `127.0.0.1`。

可在 Host 进程环境中配置：

| 变量 | 含义 |
| --- | --- |
| `CODINGNS_DOUBAO_CDP_PORT` | 本机调试端口，默认 9225，允许 1024–65535 |
| `CODINGNS_DOUBAO_APP_PATH` | App 绝对路径；macOS 默认 `/Applications/Doubao.app`，Windows 不猜测安装目录 |

首次安装检测和读取目录不启动 App。实际发送时：

1. 端口已开启：连接豆包原生后台页，不改变当前窗口的显示、焦点或聊天路由。
2. macOS 完全未运行：尝试 `open -g -j` 携调试参数启动，再等待端口。隐藏启动是系统提示，尚未完成完整冷启动不闪窗验收。
3. macOS 已运行但没有端口：返回诊断，不替用户退出或重启。
4. Windows：首版只连接手动开启调试端口的 App；隐藏启动和窗口归属尚未真机验证。

用户自行完整退出豆包后，可按本机路径启动，例如 macOS：

```sh
open -g -j -a /Applications/Doubao.app --args --remote-debugging-address=127.0.0.1 --remote-debugging-port=9225
```

Windows 可由用户在 PowerShell 中对实际 `Doubao.exe` 路径传入同样两个调试参数。不要把 `windowsHide` 或 `CREATE_NO_WINDOW` 当成隐藏豆包 GUI 的保证。

断开 CDP 只释放本轮连接，不关闭 App，也不关闭调试监听。适配器不会隐藏已经运行的窗口，不会创建额外浏览器窗口。用户如果主动进入同一个 `CodingNS …` 会话，仍然是在操作共享的云端会话；隔离不意味着创建了第二个账号或独立数据目录。

## 3. 能力限制

- 目录是已验证产品档位的静态回退，不宣称掌握底层模型、配额或上下文容量。
- 不支持附件上传、计划模式、fork、原生提问代答、Skill 或环境变量注入；明确报错，不静默忽略。
- 不提供完整历史列表/删除/改名/归档接口，不声明完整 `history` 能力。
- 普通停止调用指定会话、指定回复的原生停止接口。工作模式的“停止”只终止本地接收并报出云端可能继续的提示；没有验证可靠终止所有云端工具，需到 App 确认。
- 不提供本机 Shell 或文件操作，不声明 usage、permission、questions、steer 或 Team 能力。
- App 升级导致私有协议特征变化时会明确失败，不回退为前台输入框自动化。
- 发生断线、ACK 会话错配或结果不明时不自动重发任务。

## 6. 新建会话默认档位兼容修复

用户反馈正常新建会话出现“只支持产品档位，不支持独立思考强度、服务档位或运行环境注入”。根因是模型选择器在没有独立思考档位时显式写入 `effortId: "default"`，以清除旧模型选择；豆包驱动按字段是否存在统一拒绝，误拦截了正常默认值。此前直接调用驱动的实测省略了这类界面参数。

修复仅位于豆包输入边界：思考强度、服务档位去除首尾空格后，允许空值与 `default`，不把它们传给 App；其他非默认值与运行环境注入继续分别给出准确错误。保留公共选择器、Registry 和其他适配器的 default 清空语义。

新增两项回归先在旧代码上复现失败，修复后均通过。其中一项经过真实 `session/set → Registry → llm/stream → DoubaoAppDriver → HttpSseClient` 路径，只替换豆包网络端，验证三个产品模式均成功发送，默认档位未进入 App 请求。当前豆包定向测试共 12 项通过；另外 3 项已有服务档位/Fast 回归、类型检查通过。

真实 App 回归现已携带 `effortId: "default"` 和 `serviceTierId: "default"`。首轮实际已成功返回回答，但模型使用了“已记住测试暗号”的措辞，导致旧测试对“连接通过”的固定文案断言失败。测试改为核验正常终态与非空回答，并保留下一轮随机暗号准确回忆、会话 ID 一致等实质断言，不把自然语言措辞变化当作协议故障。

调整断言后的完整实测通过（约 79 秒）：快速新建、立即续聊、专家思考、云端文件产物、指定普通回答取消全部成功，工作模式产生 6 条工具观察事件。本次没有构建、启停服务或改动 Desktop；修复针对源码及已运行的豆包后台协议完成验证。

## 7. 第一轮完成后第二轮被错误拦截

证据来自用户提供的 `dsh-session-session-8fbd692b-4209-4784-9009-573ddda60133.zip`，只读检查其中的 session.v4.jsonl，没有导入、修改或重放用户会话。第一轮 seq 20 记录 completed；约 10 秒后开始第二轮，seq 30 返回“该豆包会话已有运行中的回合”。第二轮仍路由到 doubao/doubao-fast，在本地驱动的并发检查处失败。

根因：Feature 收到 finish 后结束上层迭代，但 Registry 用手动 next 消费内部驱动迭代器，没有把 return 转发下去。豆包生成器因此停在 yield finish，其 finally 未执行，后台桥与 runs/conversations 占用仍保留。此前驱动直连测试会把生成器读到自然结束；上一轮 Host 测试又每次使用不同 sessionId，所以都漏掉了相同会话的续聊路径。

修复位于共同的迭代器持有层：Registry 在 finally 中关闭本轮仍持有的驱动迭代器；自然耗尽或驱动自行分段后撤销本轮句柄；需要跨 step 续读时，将句柄移交续段表。保留豆包真实并发保护，不通过删锁、重发任务或创建新云端会话规避错误。

新增四项回归在修复前均失败，其中 Host 连续对话复现了完全相同的第二轮错误。修复后豆包及生命周期 16 项测试通过，覆盖同一会话三轮、stop/cancel/error 后退出、正文提前放弃及工具续段释放。真实多轮验收改为 `session/set → llm/stream → Registry → 豆包 App`，每轮收到 finish 就退出，并核验绑定、暗号记忆与每轮后台桥关闭。

真实 Host 三轮验收通过（约 12 秒）：仅首轮创建云端会话，后两轮恢复同一个 Provider ID；后续请求不附带随机值，仍能准确返回当前会话首轮的完整校验值，三个后台桥在各轮结束时均已关闭。最初使用“最初的验收暗号”提问时，App 返回了更早独立测试的值，虽绑定、历史索引及资源释放均正确，记忆断言仍失败；随后明确限定“本会话第一条用户消息”，保留完整随机值匹配断言后通过。这个现象不能视作账号级记忆已隔离。

共享适配器核心、RPC、流回归 155 项及 `pnpm run typecheck` 通过，`git diff --check` 通过。验证只连接已运行的豆包原生后台页；没有构建、启动或重启项目服务、修改用户原会话或操作 DSH Desktop。
