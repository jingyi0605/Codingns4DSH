# 外部 Agent 代理成员技术规划（历史版本）

> 本文是 20260928 的 Proxy Teammate 主方案记录。20260929 已改为“`CodingNSAgentTeam` 核心 + `DshCodingNsAgentTeamAdapter` 边界适配”的分层方案，现行规划请阅读 `docs/20260929-CodingNSAgentTeam分层集成规划.md`。本文保留作为历史调查和决策依据，不再作为实施入口。

## 1. 结论先行

推荐“原生 Proxy Teammate + 外部 Agent 执行后端”。这不是把外部 CLI 伪装成 DSH Agent，而是让 DSH 管理一个真实成员，让插件把该成员绑定到外部 adapter。

```text
原生 Team 管理面：DSH Proxy Teammate
外部执行面：CodingNsCliAdapterRegistry -> 外部 CLI
详情观察面：插件 External Agent Detail Panel
```

这个方案的价值在于边界清楚：DSH 的成员、任务、Owner、依赖、write scope、生命周期由 DSH 负责；外部 CLI 的进程、provider session、工具事件、权限、提问、usage 和恢复由插件负责。

## 2. 为什么不做“直接适配成 Team Agent”

外部 CLI 只提供 driver/registry 级能力：执行一轮、恢复、权限、提问、中断和释放。它没有 DSH Agent 对象、continuable child lineage、Session projection、inbox 或 DSH Team 工具上下文。

直接适配需要伪造至少四类状态：

1. Agent/Session 身份和父子 lineage。
2. Team member 状态、mailbox 和投递确认。
3. continuation manager 的 steer、interrupt、dispose 生命周期。
4. Team projection 与 Web UI 读取的事件记录。

这会把插件绑死在 DSH 私有实现上，升级时会直接破坏用户空间。实用方案是引入一个真实 Proxy，将无法表达的外部细节留在插件边界。

## 3. 两层管理模型

### 3.1 DSH 原生层

负责：

- Proxy 成员创建、状态和会话导航。
- 原生任务板、Owner、依赖和 write scope。
- Lead 与 Proxy 的 Team 消息边界。
- Agent dispose、中断和 Team 生命周期。
- 官方 Team Web 面板 roster 和任务展示。

不负责：

- 外部 CLI provider session。
- 外部工具事件的完整细节。
- 外部 CLI 的权限/问题协议差异。

### 3.2 插件外部层

负责：

- adapter 检测、模型和 effort 选择。
- 外部进程或协议运行、恢复、权限、提问、中断和释放。
- `TeamExternalBinding` 和 `ExternalAgentEvent` 的 Host-only 存储。
- 外部事件窗口、背压、cursor 和脱敏。
- 插件详情面板与外部原生会话入口。

## 4. Web 面板回答

在推荐方案中，官方 Team Web 面板能看到 Proxy 成员、成员状态、Team 任务、Owner、依赖、write scope 和会话入口；它不会自动显示外部 CLI 的完整工具时间线、权限详情、问题记录和 usage。

这些内容由插件 External Agent Detail Panel 展示，使用 `memberSessionId` 关联。用户看到的是一个完整工作流：Team 面板管理协作关系，插件面板检查外部执行细节，而不是把两套 UI 的权威状态混在一起。

## 5. 注入和适配边界

### 5.1 候选注入点

插件可以在能力 route 通过后使用：

```ts
ctx.inject([
  'agentTeams',
  'subagents',
  'events',
  'sessionPersistence',
])
```

这段仅是规划形态。真实 DSH 包的字段、类型和生命周期必须由 `src/dsh-capabilities/` 的结构探测确认，不能把字符串路径直接散落在业务模块。

### 5.2 可使用的公开边界

- `ctx.subagents.registerProvider`：只有在验证 provider 能提供 continuable Proxy 时使用。
- `ctx.events.on('llm/stream', ...)`：复用现有外部 CLI 接管链路，避免改写 Agent Loop。
- `agent/created`、`agent/status`、`agent/disposed`：观察 Proxy 生命周期并清理外部 run。
- 现有 CLI registry、message projector、native session bridge：复用既有执行和投影能力。

### 5.3 明确禁止

- 构造假的 DSH Agent 或直接写入 `agentTeam` projection。
- 修改 TeamService 私有字段、Agent prototype 或 continuation manager 内部 map。
- 覆盖官方 Team 工具名称。
- 让外部 CLI 直接调用未适配的 DSH Team 工具。
- 把 providerSessionId 当作 memberSessionId 使用。

## 6. 分阶段实施门禁

### 门禁 A：公开 Proxy 契约

先用真实 `0.1.7-rc.2` 包和 fake Context 验证公开 provider/continuation API。如果不能创建、继续、interrupt 和 dispose 真实 Proxy，停止后续“创建原生外部成员”实现，保留降级路线：由原生 Team 创建普通 Proxy/任务，插件只做外部详情绑定，或者暂不支持外部成员创建。

### 门禁 B：Host 核心闭环

只有绑定唯一性、单活动 run、事件序列、背压、恢复和释放都在 Host 测试中通过，才接 Client 面板。否则 UI 会掩盖生命周期错误。

### 门禁 C：Web 展示边界

必须分别验收官方 Team 面板和插件详情面板：

- 官方面板：Proxy roster、状态、任务、Owner、依赖、write scope、会话入口。
- 插件面板：adapter、model、effort、当前工具、权限、问题、usage、错误、事件和操作。

不能把插件面板的信息写入 DSH 私有 projection 来“伪造原生显示”。

## 7. 能力矩阵建议

规划阶段不直接改能力矩阵实现，但实施时新增稳定能力 ID，例如：

- `agent-team.service`
- `agent-team.tools`
- `agent-team.ui`
- `agent-team.continuable-proxy`
- `agent-team.lifecycle-events`

对于 DSH `0.1.7-rc.2`，只有探测到公开 continuable Proxy 和生命周期事件时，才标记 `supported`；如果只有 Team UI 或 one-shot ACP，则标记 `degraded`，不能让外部成员创建功能误启用。

## 8. 主要风险及处理

| 风险 | 处理 |
| --- | --- |
| 公开 provider 只返回 seed | 阶段 1 门禁阻塞，禁止私有 API 绕过 |
| 外部 CLI 事件不统一 | adapter 声明能力，统一事件允许缺省和扩展 payload |
| Team 与外部状态双写 | DSH projection 只归 DSH；插件 binding store 只归插件 |
| 同一 cwd 并发写文件 | 在任务/write scope 中提示，暂不承诺隔离 |
| Web UI 看不到外部细节 | 插件详情面板作为必需组件，不依赖官方 UI 扩展 |
| 中断后重复执行 | runId、eventSeq、resumeCursor 和幂等状态迁移 |
| 凭据泄露 | Host-only store、脱敏 DTO、日志扫描和安全测试 |

## 9. 交付判定

只有同时满足以下条件，才能称为“Agent Team 外部适配器集成完成”：

1. 真实 DSH Proxy Teammate 出现在官方 Team roster 中，而不是插件自绘假成员。
2. 原生任务板继续是 Owner、依赖和 write scope 的唯一权威。
3. 外部 CLI 运行、恢复、权限、提问、中断和释放都有绑定和测试。
4. 插件详情面板可以查看外部操作明细，官方 Team 面板的能力边界已明确展示。
5. Team Profile 关闭、旧 DSH 版本、adapter 崩溃和 provider session 丢失都有安全降级。
6. 全部实现通过能力、类型、回归、安全和资源清理验证，且没有 DSH Host 源码改动。
