## Root cause and bounded correction

Grok's driver handled all ACP tool permission requests through generic native approval. It lacked admission for the already-bound CodingNS Team tool, which the Command Code transport already treats as coordination within existing write authority. A child with noninteractive approval policy could therefore launch, discover its Team tool, and still fail on its first coordination call.

`src/host/cli-adapters/grok-driver.ts` now recognizes only the exact injected `codingns__agent_team` permission request when all of the following hold:

- The live session has the same Team launch credential as the Grok process.
- The current turn has `workspace-write` or `danger-full-access` scope and is outside plan mode.
- The request has no explicit risk marker.
- Grok offers a real `allow_once` option.

The existing request record retains that decision. The ACP server-request handler returns the offered one-time option, and the stream omits a redundant native approval request. Ordinary native tool call/result records remain visible. The bridge still checks exact caller identity, current membership, role, and task revision on the actual Team operation.

Unrelated CodingNS tools, other MCP servers, unqualified tool names, dynamic wrappers, ordinary/unbound sessions, revoked identities, read-only/unknown scope, plan mode, explicit risk requests, and requests offering only permanent approval retain native approval handling. Each reused turn rechecks current scope. The change does not enable Grok's blanket `--always-approve` flag or change saved sandbox/approval policy.
