### 2.3 `listSessions` 的返回结构（重要修正）

```js
async listSessions(signal) {
  const persisted = persistence === void 0 ? [] : await listPersisted(persistence, signal);
  const records = new Map();
  for (const header of persisted) records.set(header.id, {
    header: structuredClone(header), live: false, persisted: true
  });
  for (const session of this._ctx.sessions.list()) {
    ...
    records.set(session.id, { header: structuredClone(session.header), live: true, persisted: durable !== void 0 });
  }
  return [...records.values()].sort(compareSessions);
}
```

**它返回的是 `{ header, live, persisted }` 包装对象，不是扁平会话记录。**

🔴 **对 spec013 的影响**：`design.md` §3.2 的索引结构假设能直接从 `listSessions()` 拿到 `title` 与 `workspaceId`。**实际都拿不到**，见 §3。

### 2.4 `readSurface` 的返回结构

```js
async readSurface(sessionId) {
  const loaded = await this._corpus.load(sessionId);
  return {
    session: structuredClone(loaded.header),
    inheritedEventCount: loaded.inheritedEventCount,
    capturedThroughSeq: loaded.events.at(-1)?.seq ?? null,
    events: currentSurfaceEvents(sessionId, loaded.events)
  };
}
```

返回**当前模型表层事件**（不是完整日志），含 `session`（header 克隆）、`inheritedEventCount`、`capturedThroughSeq`、`events`。

## 3.5 归档会话机制（性能与语义的关键）

### 3.5.1 归档状态的权威来源

`ctx.workspaceRegistry` 拥有归档集合。从 `dsh-workspace/lib/index.js:232-246` 核实：

```js
/**
 * `workspaceIds` is the authoritative display order. `archivedSessionIds` is
 * the registry-global archive set layered over workspace accounting: an
 * archived session keeps its `sessionIds` slot (unarchiving must restore the
 * ...
 */
archivedSessionIds: z.array(sessionId).default([]),
```

**关键语义**（源码注释原文）：

- `archivedSessionIds` 是**注册表全局**的归档集合，叠加在工作区记账之上。
- **归档的会话仍保留其 `sessionIds` 槽位** —— 取消归档必须能恢复到原位。
- 归档与置顶**互斥**：归档会丢弃该会话的置顶状态。

持久化形态（`~/.dsh/storages/workspace.json` 的 `global` 段）：

```json
{
  "initialized": true,
  "workspaceIds": [...13 个...],
  "archivedSessionIds": [...454 个...],
  "pinnedSessionIds": [...1 个...]
}
```

### 3.5.2 本机实测数据

> **快照说明**：以下数字取自 **2026-10-04 15:51** 的一次快照。会话与归档状态**在持续变化** —— 调查过程中 10 分钟内观测到归档数从 458 增至 460、磁盘会话从 542 增至 543。因此本文所有数量级结论（比例、耗时、提速倍数）是稳定的，但**绝对数字会随时间漂移**，实现时不应硬编码。

| 项 | 数量 |
| --- | --- |
| 磁盘唯一会话 | 543 |
| 注册表会话 | 483 |
| **归档会话** | **454** |
| 置顶会话 | 1 |
| **未归档（活跃）会话** | **89** |

**84.5% 的会话是已归档的。**

### 3.5.3 性能影响（决定性数据）

| 场景 | 文件数 | 磁盘占用 | 耗时 |
| --- | --- | --- | --- |
| 全量扫描（含归档） | 594 | 334.8 MB | **6.56 秒** |
| **仅活跃会话** | 108 | 30.2 MB | **1.03 秒** |
| 归档会话占用 | 484 | 284.5 MB（**90.4%**） | — |

**仅索引未归档会话：提速 6.4 倍，减少 86% 读取量。**

### 3.5.4 `filterSessions()` 不支持归档过滤（重要限制）

从 `dsh-session-query/lib/index.js:675-702` 的 `materializeSessionResultFilters` 读出**全部可用谓词**：

| 谓词 | 说明 |
| --- | --- |
| `id` | 按会话 ID |
| `cwd` | 按工作目录 |
| `created-at` | 按创建时间范围 |
| `parent` | 按父会话 |
| `availability` | `live` / `persisted` |

🔴 **没有 archived 谓词。** 归档过滤**必须在索引层自行完成**，不能指望 `sessionQuery` 代劳。

这是本调查中最容易踩的坑：如果开发者假设 `filterSessions` 能过滤归档，就会把 454 个已归档会话全部读进索引 —— 性能退化 6 倍，且摘要里会混入几个月前就结束的工作。

### 3.5.5 归档约束

从 `dsh-workspace/lib/index.js:315-329` 核实两条约束：

```js
/** An archiveSession request named a session that at least one
 * `workspace/session-activity` listener reported active. */
var WorkspaceActiveSessionError = class extends Error {
  constructor(sessionId, activity) {
    super(`cannot archive session '${sessionId}': the session is active (...)`);
  }
};
/** A pinSession request named a session currently in the archive set. */
var WorkspaceArchivedSessionPinError = class extends Error { ... };
```

1. **不能归档活跃会话** —— 有 `workspace/session-activity` 监听器报告活动时拒绝。
2. **不能置顶已归档会话** —— 二者互斥。

**对 spec013 的意义**：因为归档时必然不活跃，所以「已归档会话」与「正在运行的会话」是互斥集合。索引里不可能出现一个既归档又 running 的会话，这简化了状态合并逻辑。

## 4. 会话投递能力（派发的核心）

### 4.1 接口（实际 zod schema）

`ctx.sessionController` 由 `@deepseek-ai/dsh-api-session-controller` 拥有。从 `lib/typert.remote-client.js:784-810` 读出：

```js
session.prompt({
  requestId: string,
  sessionId: string,                    // 任意会话
  mode: "queue" | "steer",              // steer = 注入正在运行的轮次
  content: [
    { type: "text",  text: string }
  | { type: "image", mediaType: "image/png"|"image/jpeg"|"image/webp"|"image/gif", data: string, name?: string }
  | { type: "file",  receiptId: string }
  ],
  clientTimeZone?: string,
}) → { accepted: true }
```

Host 侧绑定（`lib/typert.host.js:1231`）：

```json
{ "id": ".../session/prompt", "service": "sessionController",
  "namespace": "session", "method": "prompt", "invocation": { "kind": "direct" } }
```

### 4.2 完整 Remote 命名空间

```
session.create   session.fork    session.list    session.page
session.prompt   session.cancel  session.rename  session.search
session.follow   session.attachment  session.updateQueue
```

### 4.3 关键语义（来自包 README）

- 提示词会拒绝**既没有非空白文本也没有附件**的 content。
- `requestId` 已进入 queue 或日志时，重试直接返回原接受结果，**不重复插入**（幂等）。
- prompt 与 queue 变更可以**解析或恢复普通 Session**。
- 取消要求 live 状态。

**结论：需求 6 在核心层已完整解决，spec013 只需正确调用。**

## 6. 会话存储格式（影响读取成本）

### 6.1 三种格式版本并存

实测 `~/.dsh/sessions/`：

| 文件名 | 文件数 | header `version` |
| --- | --- | --- |
| `session.v4.jsonl.zstd` | **364** | 4 |
| `session.v3.jsonl.zstd` | **212** | 3 |
| `session.jsonl.zstd`（无版本） | **74** | 0 |
| **文件合计** | **594** | — |

当前格式版本常量为 `SESSION_FORMAT_VERSION = 4`（`dsh-session/lib/types/types.js:54`）。

🔴 **关键陷阱：文件数 ≠ 会话数。**

实测发现 **47 个会话同时存在多个格式文件**，例如：

```
session-ce0eaf9e-... → ['session.jsonl.zstd', 'session.v4.jsonl.zstd', 'session.v3.jsonl.zstd']
session-70a6afcb-... → ['session.v4.jsonl.zstd', 'session.v3.jsonl.zstd']
```

这是格式迁移（v0 → v3 → v4）留下的历史残留，**同一会话在不同版本下各留一份**。

| 指标 | 值 |
| --- | --- |
| 格式文件总数 | **594** |
| **唯一会话 ID 数** | **543** |
| 多格式并存的会话 | **47** |

**对 spec013 的影响**：任何"按文件枚举会话"的做法都会**重复计数**（594 vs 543）。**这是必须使用 `sessionQuery` 而非自行读盘的第二个强理由** —— 核心的持久化层已封装格式迁移与去重。

### 6.2 存储规模与读取成本（实测）

| 指标 | 值 |

| 格式文件数 | 594 |

| 操作 | 耗时 |

✅ **结论：全量读取成本远低于预期。** 4.6 秒是全量扫描的代价；实际摘要只需读少量会话，成本可忽略。`design.md` §9 中"`sessionQuery` 在冷会话上的读取成本未知"这一风险**可以关闭**。

⚠️ 但仍需注意：`readSurface()` 返回的是**表层事件**，其体量取决于会话长度。最大会话的表层可能有数 MB，需要实测后决定是否进一步截断。

### 6.3 并发安全

磁盘上有 **451 个 `session.lock`** 文件，说明会话写入使用文件锁。`sessionQuery` 的读取路径（`load`）**优先使用实时会话**，避免与写入竞争。

## 7. 语音能力

### 7.1 核心语音转写（可用）

`@deepseek-ai/dsh-experimental-speech-to-text` 提供 `ctx.speechToText`（`lib/index.js:7-21`）：

```js
var SpeechToText = class extends Service {
  constructor(ctx, config) {
    super(ctx, "speechToText");
  }
  register(provider) { ... }   // lib/index.js:37
}
```

Provider 接口：

```ts
register(provider: SpeechProvider): () => Promise<void>

interface SpeechProvider {
  readonly info: SpeechProviderInfo
  readonly preparation?: SpeechPreparation
  transcribe(input: SpeechInput, signal: AbortSignal): Promise<Transcript>
}

interface SpeechProviderInfo {
  id: string
  name: string
  location: 'host-local' | 'cloud'
  languages: readonly string[]
}
```

**第三方可注册自己的 provider**（含云端）。本机有两个实现佐证：`sensevoice-local`（`host-local`）与 `dsh-experimental-api-speech-to-text`（`cloud`）。

### 7.2 本地模型已就绪

```

~/.dsh/speech-to-text/sensevoice/models/sensevoice-onnx/tokens.txt

```

### 7.3 官方语音输入的启用状态（已确认）

`~/.dsh/profiles/desktop/package.json` 的 bundles 列表：

```
@deepseek-ai/dsh-base
@deepseek-ai/dsh-web-app
@deepseek-ai/dsh-experimental-agent-team-profile
@deepseek-ai/dsh-experimental-auto-review
@deepseek-ai/dsh-experimental-schedule-bundle
@deepseek-ai/dsh-experimental-voice-input-bundle    ← 已列入
@jingyi0605/codingns4dsh
```

但 `cordis.patch.yml` 中**没有任何 voice/speech 条目**（`grep -i "voice\|speech"` 为空）。

**结论：bundle 已列入 profile 的 bundles 列表，但其插件行尚未在 patch 中启用。** 需要在 GUI 侧边栏「插件」页启用「语音输入」才会挂载 `speechToText` 服务与麦克风按钮。

⚠️ 这意味着**需求 4 依赖的服务当前可能尚未挂载**。任务 4.1 必须先确认或显式启用。

### 7.4 核心没有 TTS（缺口确认）

核对方式：

1. 枚举 asar 内全部 `@deepseek-ai/*` 包（**290 个**），按 `tts|text-to-speech|synthes` 匹配 → **无结果**。
2. 按 `speech` 匹配 → 仅 5 个包，全部为 STT。
3. 核心语音服务只有 `speechToText` 与客户端 `speechController`，**均无合成方法**。

**结论：语音播报必须由 spec013 自己选型。**

## 8. 等待处理状态的来源（易错点）

`SessionSummary` **只带 `running` 与 `completed`，没有「等待审批」**。

如果直接用 `running` 判断，会把「等用户点审批」的会话误报成「运行中」—— 需求 7 直接失效。

| --- | --- |
| Host | `approval/request`、`user-questions/request` 事件（日志中对应 `approval/asked`） |
| Client | `ctx.uiSession.pendingInteractions` |

## 11. 对 spec013 的修正（已回写）

本次调查后回写到 `design.md` / `requirements.md` / `tasks.md`：

1. **索引结构**：`title` 来源改为"日志最后一条 `session/title`"。
2. **摘要读取**：必须用 `readSurface()` 或只读语义事件，**禁止**遍历原始日志（流式 chunk 占绝大多数）。
3. **不得自行读盘**：三种格式并存 + 47 个会话多格式重复，自行读盘会重复计数。
4. **索引范围限定为「受管工作区 ∩ 未归档」**：新增需求 8（手动选定范围）与需求 9（仅索引未归档会话）。
5. **性能章节**：新增 `design.md` §3.5，回答"是否影响 DSH 性能"，给出实测数据与设计要求。
6. **归档过滤自行实现**：因 `filterSessions` 无 archived 谓词，必须在索引层用 `workspaceRegistry.archivedSessionIds` 过滤，并有专项测试。
7. **语音前置条件**：任务 4.1 需先确认 `voice-input-bundle` 是否已启用。
