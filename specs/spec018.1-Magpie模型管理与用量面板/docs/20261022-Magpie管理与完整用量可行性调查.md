# Magpie Management and Complete Usage Feasibility Report

Date: 2026-10-22

## Conclusion

The full usage dashboard and useful provider/group/account management are feasible with the installed Magpie `0.1.1318` interfaces. The CLI documents provider name/endpoint/model configuration, provider on/off, and routing-group setters. Isolated real-CLI tests confirmed provider and group writes plus read-back, including ordered model IDs and pattern preservation. Provider accounts can be managed through Magpie's authenticated Web API when `magpie web` is available on a loopback URL and the Host has the matching `MAGPIE_WEB_KEY`.

The account CLI itself exposes `active`/`on` status but no per-account setter. However, Magpie `v0.1.1318` source confirms the Web UI API's authenticated `POST /api/login/on|off` route calls `provider.SetLoginOn`. The DSH panel nests the signed-in account as primary and other saved accounts as secondary under matching providers, then uses that Web API for reviewed routing toggles and verifies the result using a fresh CLI read. This write can reseat affected Agents and sync their model catalog. Account switching remains distinct and is not exposed.

## Live-device method and boundary

- Installed CLI version: `magpie 0.1.1318`.
- CLI checks: `magpie --version`, `magpie --help`, `magpie provider --help`, `magpie providers`, `magpie groups`, `magpie accounts --json`, and `magpie group help`.
- Read-only Gateway checks used the existing local loopback listener at `http://127.0.0.1:3425/v1`; requests used GET and the local Magpie bearer convention.
- Write/read-back testing used a new temporary `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, and `XDG_CACHE_HOME`, with `MAGPIE_NO_ACCOUNTS=1`, proxy variables cleared, and only synthetic loopback endpoints. It created and removed synthetic provider/group records using the Magpie CLI; the isolated inventory was empty afterward.
- The installed Web UI endpoint `127.0.0.1:3430` was not listening during this investigation. The account API handshake and `on`/`off` requests were verified with a mocked HTTP transport and CLI read-back tests, not a live authenticated account mutation.
- No active Magpie configuration, account sign-in, live model route, or running Magpie Web/Gateway process was modified. The Magpie CLI was only used for read-only checks against active data and isolated synthetic writes under temporary HOME/XDG paths. No DSH process, Stage0, or Desktop profile/process was operated.
- CLI list output can include account identities and masked key fragments. This report intentionally records field names and shapes only, not live values.

## Exact fields observed

### `GET /v1/models`

The response is an OpenAI-compatible envelope with `object`, `data`, `first_id`, `last_id`, and `has_more`. Model records exposed:

`id`, `object`, `created`, `created_at`, `display_name`, `magpie_label`, `owned_by`, `type`, `context_length`, `context_window`, `max_input_tokens`, `max_output_tokens`, `modalities.input`, `reasoning`, `reasoning_levels`, and `supported_reasoning_levels`.

### `GET /v1/magpie/usage?period=today|week|month|all`

The live endpoint returned HTTP 200 for `today`, `week`, `month`, and `all`. The root exposes:

`period`, `since`, `path`, `bucket`, `calls`, `errors`, `retried`, `input`, `output`, `cache_read`, `cache_write`, `reasoning`, `cost`, `unpriced`, `credits`, `credited`, `timed`, `ttft_ms`, `decode_ms`, `decode_out`, `decode_n`, `sessionCount`, `series`, `agents`, `models`, `accounts`, `providerKeys`, `callerKeys`, and `sessions`.

Series rows expose `time`, `label`, and the same applicable usage/timing metrics. Group rows expose identifiers and labels appropriate to their dimension plus calls/errors/retries, token/cache/cost/pricing, and timing metrics. Session rows expose `id` and `agent` plus metrics. Not every field is present in every period or row.

### `GET /v1/magpie/usage/requests`

The live endpoint returned HTTP 200 with `period`, `bucket`, `total`, `offset`, `rows`, `series`, `by`, `agents`, `providers`, `accounts`, `purposes`, `callerKeys`, `calls`, `errors`, `retried`, `input`, `output`, `cache_read`, `cache_write`, `reasoning`, `cost`, `credits`, `credited`, `unpriced`, `timed`, `ttft_ms`, `decode_ms`, `decode_n`, `decode_out`, `through`, `direct`, `reported`, and `by` subgroups `agent`, `callerKey`, `model`, `modelAt`, and `provider`.

Live request rows exposed:

`route_id`, `t`, `agent`, `agentName`, `provider`, `providerName`, `host`, `providerAccount`, `model`, `req`, `served`, `in`, `out`, `cache_read`, `cache_write`, `reasoning`, `ms`, `ttft_ms`, `first_text_ms`, `first_reasoning_ms`, `flow_ms`, `status`, `rid`, `response_id`, `ep`, `stop`, `credits`, `cost`, `priced`, `icon`, and `access`.

With a session search, additional rows can contain `session`, `native_session`, `effort`, `err`, `err_type`, `own_ms`, `providerKeyId`, `reasoning_hidden`, `retried_ms`, `sent_ms`, `tier_served`, and `tries`. CodingNS must omit raw error text, endpoint/response identifiers, prompt/reply fields, and arbitrary unknown fields. A search query is not an identity guarantee; the Host must exact-match `session` or `native_session`.

### Quota reads

`GET /v1/magpie/quotas` and `/v1/magpie/quotas/cards` returned `{ object, data }`.

Quota cards exposed `provider`, `name`, `kind`, `user`, `plan`, `alias`, `balance`, `readAt`, `icon`, `windows`, and, on cards, `daily`. Window fields observed include `name`, `used`, `remaining`, `resetsAt`, `holdsWhy`, `display`, `amount`, `limit`, `unit`, `runsOutAt`, and `runsOut`. Daily records contain `since` and `days[]` with `day` and `used`.

`GET /v1/magpie/quotas/history?days=30` returned `{ object, data[] }`; records contain `provider`, `user`, and `lines[]`, each line has `name` and `points[]`, and points expose `at`, `left`, `start`, and `resetsAt` where available.

### `GET /v1/magpie/route?session=...`

The live response envelope was `{ session, seq, route }`; the test identity had `route: null`. A complete populated-route shape was not observed during this test. The existing request ledger is the better verified source for provider, requested/served model, account, cost, and status history.

## CLI management surfaces

### Providers

`magpie providers` and `magpie provider <id>` are human-readable. The installed CLI documents:

- `magpie provider set <id> k=v…` for existing provider settings, using the same key/value fields as custom-provider addition. Reported fields include `id`, `name`, `url`, `anthropic`, `responses`, `gemini`, `decide`, `key`, `models`, `catalog`, `icon`, `header.*`, `balance`, `balance.path`, `balance.method`, `balance.token`, `models.url`, `search`, `user-agent`, `access.key`, and `access.secret`; documented provider-specific settings also include context, family, codex, compaction, and tool behavior.
- `magpie provider models <id> [ids…]` to replace exposed models, with `+id`, `-id`, `all`, and `none` forms.
- `magpie provider on|off <id>` to include/exclude an existing provider from routing.
- Additional provider commands for key/fallback, listed visibility, account-model mapping/caps, concurrency, queue, RPM, quota/rest caps, refresh, testing, and removal.

The panel deliberately writes only provider display name, already-present plain endpoints, exposed model IDs, and `on`/`off`. It does not surface key/header/balance/credential settings, provider ID changes, creation, or removal. The live reader presented `url=` as `chat`; it returned endpoint details for `chat`, `responses`, `anthropic`, and `gemini`, but not `decide`, so `decide` is not editable. Endpoints with userinfo, query, or fragment are sanitized and read-only. Magpie canonicalizes an Anthropic endpoint ending in `/v1` to the base URL, so the Host normalizes this before writing.

An isolated CLI round-trip confirmed `provider set` changes name and endpoint, `provider models` accepts provider-local model names (for example `model-a`) and returns canonical `provider/model-a` IDs, and `provider off`/`provider on` change the provider-list state. The model argument normalization is covered by automated regression tests. No private Magpie config-file write or app RPC is used.

### Accounts

The live `magpie accounts --json` result was an array. Each observed account record exposed:

`agent`, `user`, `plan`, `active`, `on`, `windows`, `asOf`, and `readAt` (some keys are absent from some rows). Quota windows expose `name`, `used`, `remaining`, and `resetsAt` where available.

The CLI documents `magpie accounts switch <agent> <email>`, which changes an Agent sign-in. It does not document a per-account `on` setter. `magpie accounts discovery on|off` controls discovery of sign-ins globally and is not account routing eligibility. `magpie accounts switch-only codex on|off` is also not the per-account `on` field.

Magpie's `internal/gui/providers.go` at tag `v0.1.1318` registers `POST /api/login/{action}`; actions `on` and `off` accept JSON `{ "Agent": ..., "User": ... }`. The handler calls `provider.SetLoginOn`, runs the change through `agent.Reseat`, then calls `agent.SyncCatalog`. In `internal/provider/logins_on.go`, the signed-in account is always the Agent's primary login, other saved accounts can be switched into or out of use, and Magpie refuses to turn off the final account in use. Turning off the currently signed-in primary pauses its routing use but does not switch its sign-in. These are routing mutations with potential Agent/model-catalog effects, not harmless display toggles.

Magpie `internal/gui/web.go` protects the Web API with a key-to-cookie handshake: the `?k=` login link creates a port-scoped `magpie_web_<port>` cookie; subsequent API requests require that cookie. The DSH Host reproduces that handshake, requires a Host-side key, restricts the destination to HTTP(S) loopback origins, rejects redirects and unexpected auth redirects, and never returns the key over RPC. The account remains disabled in the UI unless this authentication check succeeds. API success is followed by `magpie accounts --json` read-back.

This account action is an internal Web UI API discovered in Magpie `v0.1.1318`, not a published stable API guarantee. The current Host reports a change only for HTTP 200 plus matching CLI read-back; an upstream route or behavior change therefore fails visibly rather than claiming success. Re-audit the handler when upgrading Magpie.

The Host reads `MAGPIE_WEB_KEY` and optional `MAGPIE_WEB_API_URL` from its process environment (default URL: `http://127.0.0.1:3430`). Magpie Web and DSH Host must use the same key; both processes must be started with the configured environment. The key is not stored in CodingNS settings or passed through the Client.

The UI matches accounts to providers only on an exact `account.agent === provider.id`; unmatched account Agents remain in an explicitly separate section. Within each provider, `active === true` is primary and the other saved logins are secondary. Account API enablement is unavailable if the Web key is absent, authentication fails, or the target is not loopback. The Host also blocks attempts to turn off the last account it sees as in rotation.

### Routing groups

`magpie groups` and `magpie group <id>` provide human-readable list/detail output. No stable JSON read schema was observed, so the DSH parser is gated at `0.1.1318` and fails closed if the expected list/detail rows cannot be parsed. The list includes group ID/name, policy and stickiness, ordered members/patterns, and (where present) Agent usage. Details expose group ID/name, routing, stays, members, and pattern counts.

`magpie group help` documents `magpie group set <id> k=v…`; setting names include `name`, `models`, `models+=`, `models-=`, `routing`, `stays`, `context`, `levels`, `family`, `id`, `effort`, `classifier`, `pick`, `fast`, `weight`, and `listed`. Rule add/remove/move is also documented. Route modes are `smart`, `order`, `rotate`, `usage`, `pace`, `weight`, and `manual`; stickiness values are `auto`, `session`, `turn`, `off`, and `strict`.

An isolated real-CLI round-trip changed group name, ordered members, route policy, and stickiness, then confirmed the settings by rereading the group. A separate rename of a pattern-backed group preserved both its wildcard pattern and expanded members. The DSH panel exposes only `name`, ordered `models` (including patterns), `routing`, and `stays`; other CLI-settable fields lack a dependable reader or sufficient isolated success-isolation evidence and remain out of scope. Provider state and other groups remained unchanged in the automated mutation-isolation tests.

## Usage display decision

| Need | Feasibility | Evidence / boundary |
| --- | --- | --- |
| Period totals and charts | Feasible | `usage` returns totals and series for all four tested periods. |
| Provider/model/account cost breakdown | Feasible | Usage breakdowns and request rows include provider/account/model plus numeric cost. |
| Session list and per-session request costs | Feasible | Summary includes sessions; request ledger supports query and pagination; exact Host-side ID match is mandatory. |
| Automatic binding to the currently open DSH conversation | Not provided by this settings-panel context | Users choose a Magpie session row; detail queries require its exact Magpie session ID and Agent. |
| Subscription allowance/history | Feasible | Quota cards and history endpoints return windows, daily points, and timestamped remaining values. |
| Provider name/endpoint/exposed-model editing | Feasible with a narrow allowlist | `provider set` and `provider models` are documented and passed isolated write/read-back checks; credentials and unverified fields are excluded. |
| Provider on/off | Feasible | `provider on|off <id>` is documented and passed an isolated real-CLI check. |
| Per-account enable/disable | Feasible through authenticated Magpie Web, not the CLI | `POST /api/login/on|off` calls `SetLoginOn`; requires `MAGPIE_WEB_KEY` on the Host and running Magpie Web on loopback. Read-back is performed by the CLI. Mocked protocol tests pass; no live account mutation was performed because the default Web listener was not active. |
| Provider/account hierarchy | Feasible with verified identities | `accounts.active` identifies the signed-in primary; other account rows are secondary. Only exact Agent/provider-ID matches are nested; unmatched accounts remain visible without inferred parentage. |
| Account sign-in switching | Technically available, not included | `accounts switch` is a consequential Agent sign-in operation, separate from routing eligibility. |
| Routing group name/models/patterns/routing/stays | Feasible with a version-gated parser | Documented `group set` and human-readable list/detail output passed isolated read/write/read-back tests; only confirmed fields are exposed. |
| Other routing-group settings | Not included | CLI can set context/levels/family/classifier/pick/fast/weight/listed/rules, but this panel excludes fields not covered by its verified read-back contract. |
| Complete current routing-group list | Feasible for the installed CLI; not a structured contract | Current `magpie groups` and per-group detail output parse under the tested version gate; an unknown output shape returns unavailable instead of guessing. |

## Cost caveat

The live API returns numeric `cost` and pricing indicators such as `priced`/`unpriced`; no currency field was observed. The new dashboard must show this as Magpie-reported cost and must not add `$`, USD, or another currency claim based only on the number. The existing compact subscription UI is unchanged.
