# 语音上传积压与诊断文件选择修复记录

用户反馈「语音上传积压过多，请检查网络后重新开始实时对话」，随后通话自动结束；汇总脚本只读到一条记录，提示没有完整样本。本次检查现有日志并修复上传与日志选择逻辑，没有构建或启停服务。

## 实际证据

真实通话已写入 `data/logs/voice-performance-2026-10-07T14-41-43-554Z-65353-7fc65bd5.0.jsonl`，共有 170 条记录。原脚本按文件名中的初始化时间选择运行，误选了随后生成的单条 `diagnostics.self_test` 文件；真实运行虽更早初始化，却在之后持续写入通话记录。

| 指标 | 本次样本 |
| --- | --- |
| 成功上传 | 40 次；往返 P50 103.8 ms、P95 734.9 ms、最大 847.7 ms |
| 上传排队 | P50 138.9 ms、P95 619.7 ms、最大 835.0 ms |
| Host 上传处理 | P50 14.3 ms、P95 67.7 ms、最大 100.3 ms |
| Host 事件循环 | 最长阻塞 1203.8 ms，8 次采样中有 6 次超过 100 ms |
| 识别实时系数 | 0.047～0.126；处理速度尚能赶上音频，最长单帧解码 73.7 ms |

| 上传中止 | UTC 14:48:32.149，旧队列积压 130788 字节 |

RTF（实时系数）为处理耗时除以音频时长。当前识别 RTF 低于 1，并不能排除识别中的短时阻塞；上传往返也包含 Host 排队与处理，不能直接等同于网络耗时。

MOSS（语音合成模型）冷启动开始后约 4.4 秒因通话结束而取消，尚未输出音频；该样本不能用于评价实际合成速度。Host 负载与事件循环阻塞值得继续调查，但当前不能把根因确定为网络、识别器或 MOSS。旧日志没有未完成上传的起始与收到事件，末次请求停在哪一层仍缺少证据。

## 修复内容

### 按真实音频计算积压

原队列保存每个小帧的 JSON 首部和 PCM（脉冲编码调制）音频，将两者一起计入 128 KiB 限制。实际采集每帧约 8 ms、每秒 125 帧，小帧首部明显消耗容错预算，约三秒音频就可能触发退出。

队列现在只保存待传 PCM 与帧元数据，按实际音频时长计算压力，最多允许五秒音频，同时保留 160000 字节 PCM 上限。连续且同代次、同采样率的小帧合并到约 40 ms 后再封装，保留全部样本与顺序，不跨序号间隙合并。每组使用最后一个原帧序号，兼容现有协议。

上传继续保持单请求串行。请求完成后，已经等待超过 60 ms 的队列立即续传，不再额外等待一次固定间隔。五秒没有响应、音频积压超限或请求失败仍会停止通话，避免无限缓冲；提示改为 Host 或连接处理过慢，不再直接归因于网络。

### 让积压识别批次释放事件循环

原 Host 在每帧后等待协调器；同步识别只产生微任务切换，批量处理期间其他 HTTP、RPC（远程过程调用）和租约定时器仍可能等不到执行机会。

现在帧处理累计超过约 10 ms 时，通过 `setImmediate()` 在帧间让出事件循环。每帧仍校验当前代次，保留打断后的旧帧过滤与租约语义；单次同步识别的内部耗时不会因此消失，后续仍需实测。

### 补全断开前的诊断证据

- 客户端发起请求前写入 `client.upload.start`，Host 入口写入 `host.upload.received`；即使请求未返回，也能按 `diagnosticId` 关联。
- 上传记录补充 PCM 字节、首部字节、音频时长；压力和错误记录补充待传时长、在途批次与等待时间。
- 中止原因分别记录为 `upload_backlog`、`upload_timeout`、`upload_transport_error` 或 `upload_batch_limit`。
- 汇总脚本按记录中的最新接收时间选择真实指标运行，自动跳过仅自检或启动的运行，包含同一运行的全部轮转文件。
- 即使通话在模型回复前结束，脚本也输出上传中止和未完成请求；原有旧日志仍可分析。

日志仍直接保存到 `/Users/jackson/Code/CodingNS/data/dsh-codingns/data/logs`，不新增音频或对话正文记录。
