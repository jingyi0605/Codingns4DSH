# Stage0 热重载设置读取时序修复记录

## 问题与原因

用户在启用源码监听后发现，每次 Host 热重载都会打印两次“ConfigForms 未找到设置
namespace，使用默认值”，部分已经启用的功能只有彻底重启 Stage0 才能恢复。

通过真实 Cordis（插件生命周期框架）和 SettingsForms（原生配置表单服务）复现：
当设置等依赖已经就绪时，插件的注入回调会在入口 Fiber（插件生命周期实例）仍处于
加载态时执行。SettingsForms 只投影激活态的配置条目，因此此时 `describe()` 返回空列表。
原配置及新 Fiber 已解析的配置仍然存在，但原实现回退到默认设置。

终端 controller（控制器）在装配时只读取一次开关；其他重启生效模块也会捕获启动快照。
即使稍后表单恢复可见，这些启动状态也不会自动纠正。问题是读取时序，不是配置文件被删除。

## 修复

- Host 入口把当前入口 Fiber 的配置读取函数交给设置作用域。注入回调的子 Fiber
  没有插件 Config，不能把它当成配置来源。
- 原生表单可见时继续读取表单；加载态下直接读取本轮 Fiber 已经校验的配置。
  根 Config 是 volatile（实时配置引用），每次读取都解引用并返回独立快照，避免
  重复校验深冻结的值，也避免缓存旧一代插件或其他 Profile 的配置。
- 写入继续交给原生 SettingsForms。表单尚未激活时明确拒绝写入，避免误用旧版
  `codingns` namespace（设置命名空间）。旧版 `register()` 路径保持不变。
- 不引入第二份配置文件，不改功能开关的重启语义，不修改上游运行时。

- 覆盖原生设置编辑、监听通知、表单暂时不可见时读取最新实时配置、拒绝写入错误
  命名空间，以及现代无入口配置调用和旧版注册兼容。
- Host 入口测试确认配置读取来自入口 Fiber，而不是注入子 Fiber。
