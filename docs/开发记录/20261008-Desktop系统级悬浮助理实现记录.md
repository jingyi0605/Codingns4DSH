# Desktop 系统级悬浮助理实现记录

## 问题与判断

截图中的形象是 `shell.overlay` 插槽里的网页元素，`FloatingAssistantFrame` 使用 `position: fixed`，拖动位置按 `window.innerWidth/innerHeight` 限制。它只能在主窗口中显示，提高 z-index 无法把它变成系统窗口。

核对仓库内官方源码归档 `deepseek-harness-4878cdabd87d4041bdaff61d04c966883b9fd07a.zip`：`apps/desktop/src/host-process.ts` 在 Electron Node 模式子进程中启动插件 Host，`preload-app.ts` 不提供创建原生窗口的公开接口，不能在插件 Host 直接使用 Electron BrowserWindow。`web-document.ts` 的 Desktop 请求转发会移除 Origin，并向回环 Host 添加认证 Cookie。

本轮用户选择扩展现有 spec014 并实现系统原生窗口，需求 6、设计 §21 和阶段 22 已更新。

## 实现

| 部分 | 实现与职责 |
| --- | --- |
| Host 入口 | `src/host/desktop-assistant/feature.ts`，同时核对操作系统、Electron Node 模式和官方 Desktop Host 入口；从正式设置取角色和尺寸 |
| 生命周期 | `controller.ts`，每个 Host 一个伴随进程，维护页面 owner、更新序号、窗口 generation 和打开事件；关闭时回收进程与端口 |
| macOS | `mac-agent.ts`，透明、置顶、不随应用失焦隐藏的 NSPanel＋WKWebView，跨 Spaces 与全屏辅助窗口属性 |
| Windows | `win-agent.ts`，透明置顶 WPF＋WebView2CompositionControl，不显示任务栏条目；鼠标位移按 WPF DPI 比例换算，多屏边界通过 Win32 工作区校正 |
| 形象展示 | `desktop-entry.ts`、`desktop-view.ts`，独立 React 页面复用内置、图片、图集和 Live2D 渲染器，不创建语音或助理会话 |
| 主页面选路 | `desktop-bridge.ts`，串行同步展示状态、读取打开事件；Desktop 首帧保留原生展示位置，明确不可用或持续故障才恢复页面并展示降级提示 |

原生窗口没有绑定 Desktop 主窗口为父窗口，主窗口最小化或隐藏不会直接隐藏它。点击形象由原生进程激活创建 Host 的 Desktop 主进程，再由主页面打开现有工作台。拖动达到阈值才移动窗口，拖动释放不打开工作台；保存位置与网页位置分开。主程序完全退出、模块停用或关闭悬浮开关时清理伴随进程。它依赖 DSH 正在运行，不是独立后台助理服务。

正式配置沿用原字段，无需迁移。Web 页面、非官方 Desktop Host、未创建助理及不支持的第三方自定义渲染器继续使用原有页面路径。只同步展示状态与最近最多 8000 字符的通话字幕，不申请麦克风、不创建第二套语音运行时。

## 资源、权限与兼容处理

- 控制路由必须通过 DSH 登录校验、物理回环地址和回环 Host 检查，并拒绝 Origin 与反代来源头；不加入 PeerHost 远程代理通道。
- 伴随页使用另一个随机回环端口，以每个实例独立的随机令牌换取 HttpOnly、SameSite Cookie；只提供固定 HTML、bundle、展示快照及既有形象资源处理器，没有通用代理、文件读取或 DSH RPC。
- 原生窗口导航限定到该实例的回环地址，不能跳转到外部网站；页面正文由 React 转义。
- l2d 2.1.1 会插入内联 Cubism 脚本，因此独立页面的 CSP（内容安全策略）允许固定同源引擎的内联脚本和 WebAssembly，仍禁止外部脚本、frame 与表单提交。
- 页面就绪先显示加载占位，模型在可见后再初始化；避免隐藏窗口与 Live2D 可见性门禁互相等待。资源失败、超时和异常退出均使主页面恢复显示。
- PowerShell 5.1 脚本使用带 BOM 的 UTF-8，标准输入输出显式使用 UTF-8；SDK 路径用 PowerShell 字面量引用，支持中文与单引号路径。
- Windows 随包携带固定 WebView2 SDK 1.0.3595.46，约 1.1 MiB，含 x64、ARM64、x86 加载器及微软许可。系统需已有 WebView2 Runtime，缺失时回退，不自动安装系统组件。
- `bundle:client` 增加独立伴随页的构建配置，发布文件清单纳入 SDK；本轮只修改配置，没有执行构建。

## Windows 回退与 macOS 初始化修复

用户安装打包 npm 后，Windows 显示页面内回退，浏览器报告 `POST dsh-app://app/codingns-desktop-assistant/attach` 返回 405。用户彻底退出并重启后确认 Windows 系统悬浮正常，因此本轮没有修改 Windows 原生窗口代码。该反馈与旧 Host 未重新加载新路由的情况一致，不将它误判为 Windows 原生窗口创建失败。

macOS 则在仓库独立 JXA 测试中确认存在不同问题：

1. `ObjC.registerSubclass()` 返回 `undefined`，不能把返回值作为类调用 `.alloc`；现改为注册后通过 `$.CodingNsAssistantBridge` 等名称实例化。
2. 当前系统的 JXA 无法解析 WebKit 代理协议元数据，显式声明 `protocols` 会在启动时抛出 `protocol does not exist`；改为显式声明方法签名，保留 WebKit 所需选择器。
3. 导航完成回调是原生 block，直接作为 JavaScript 函数调用会失败并导致 WebKit 报告未完成导航判定。改为 NSInvocation（原生调用对象）按 `void (^)(NSInteger)` 签名调用，参数 0 是 block 自身、参数 1 是策略值，不设置方法选择器。导航仍只允许当前实例的同源地址。

同时修复管道在中文 UTF-8 字节中间分块时丢失命令的问题，完整字符到达前保留原始数据；WKWebView 改用非持久存储。原生进程退出时保留有上限的 stderr 诊断并隐藏启动令牌，避免 EPIPE 提前掩盖真正异常。页面回退文案可点击展开错误原因，不再只依赖鼠标悬停。

新增 `tests/desktop-assistant-mac.spec.ts`，在 macOS 26.5 ARM64 直接执行仓库生成的 osascript，使用隐藏窗口和空白测试页：

- 完成原生类注册、分块中文命令接收、令牌认证、回环页面加载和页面就绪回传。
- 页面尝试跳转到不同回环端口时，目标服务实际收到 0 次请求，原页面仍能回传就绪。
- 不发送显示或激活命令，不连接用户 Desktop，结束后清理自有进程、服务及临时目录。

## 点击悬浮助理恢复 Desktop 主窗口

用户补充要求：Windows 与 macOS 点击系统悬浮助理后，应恢复前台显示 DSH Desktop，不能仅打开后台页面中的对话框。

旧路径有两处缺陷：macOS 只调用 NSRunningApplication 激活应用，无法可靠取消窗口最小化；Windows 枚举父进程中带标题栏样式的窗口，可能漏掉自绘窗口或选中辅助窗口，且没有处理前台权限交接。页面的打开事件与上述操作独立，即使主窗口没有恢复，对话框仍会打开。

核对仓库内官方源码归档和 0.2.0-rc.2 对应源码：Desktop 的 `focusPrimaryWindow` 已负责 `restore → show → focus`，macOS 的 `dsh://open` 和 Windows 的单实例事件均通向该入口。改为复用它：

- macOS 从父进程 PID 取得当前应用包，通过 NSWorkspace（应用启动服务）定向发送固定 `dsh://open`。禁止创建新实例、替换为其他应用或自动弹出启动提示；请求成功交接后才发送页面打开事件。应用不存在、已退出或请求失败时保留具体原因。
- Windows 从父进程取得当前 Desktop 可执行文件，以固定打开参数触发单实例入口。启动环境移除 Host 继承的 `ELECTRON_RUN_AS_NODE` 和 `NODE_OPTIONS`，避免把桌面程序当 Node CLI 启动；通过 AllowSetForegroundWindow 仅向当前父进程交接前台权限。移除标题栏枚举和异步 ShowWindow 猜测。
- macOS 合并进行中的重复请求，Windows 一秒内重复点击合并。原有助理工作台打开、键盘操作、拖动互斥及窗口生命周期保持原路径；主窗口唤回请求由原生点击直接触发，不等待后台页面轮询。

新增唤回专项验证当前应用归属、请求合并、成功后通知页面、失败不伪报成功、退出保护和 Windows 启动环境契约。macOS 额外在自有临时目录中使用不存在的 `.app` 路径真实调用 NSWorkspace，验证方法签名和 NSError（原生错误）回调桥接；禁止激活和提示，不打开任何实际应用。

## 原生形象常驻与内部形象闪现修复

用户反馈原生悬浮已经显示时，内部形象仍频繁出现约一秒再消失；同时要求原生窗口在 Desktop 前台和助理工作台打开期间保持显示。

根因是两个状态被混用：Client 用原生 `visible` 决定是否画页面形象，初始值和显示确认前的答复均为 false，因此直到下一轮轮询才能收起内部形象；原生 `presentation.visible` 又复用了页面避让工作台的条件，Host 的打开事件也主动隐藏原生窗口。单纯缩短轮询无法消除这些中间状态。

改动：

- 将展示位置与显示确认拆开。Desktop 首帧和原生初始化期间不渲染内部形象，组件重挂载、重新启用及尚未收到 shown 也保持该选择；普通 Web 不变。
- 原生是否显示只跟随助理创建状态和悬浮开关，打开/关闭工作台、Desktop 回到前台不会再隐藏它。Host 打开事件只通知现有工作台，形象与通话运行时不重建。
- 状态变化立即提交，迟到响应不能覆盖已变化的开关。首次、第二次通信失败继续保留原生位置，连续三次失败才进入回退；原生明确错误和不支持当前形象则直接放行页面回退。
- 断连后重新附着而不吞掉期间点击；Host 在两次正常轮询之间重建时，用可选的无人持有标记恢复附着，其他页面已经持有时不争抢。卸载清理等待在途请求结束后发送一次。

覆盖首帧、等待显示、重复状态答复、工作台开关、用户开关、迟到响应、短暂断连、持续故障、Host 重建和不支持形象的回退。测试使用仓库内控制器替身与实际 React Hook 状态，不操作已安装 Desktop，也不启动可见原生窗口。
