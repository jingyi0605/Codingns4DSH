# PeerHost 会话反馈状态路由修复记录

## 问题与原因

通过 PeerHost 打开远程工作区会话后，会话尾部出现“反馈状态加载失败”。

原生 Remote（远程调用）白名单遗漏了 `messageFeedback/list`、`messageFeedback/put`、`messageFeedback/delete` 和 `sessionFeedback/record`。远程消息反馈请求因此没有进入 PeerHost 转发链路，落到本机反馈服务；本机服务无法用虚拟会话 ID 找到远端会话。

上游 `@deepseek-ai/dsh-api-remotes` 的本地 `0.2.0-rc.2` 和 `0.2.1-alpha.1` 产物均提供这些反馈命名空间。请求使用 `args.request.sessionId`，消息 ID、版本号与反馈文字属于业务数据。

## 实现

1. 在唯一原生方法白名单中登记四个反馈方法，页面传输与原生连接分流共用这份名单，代理 Host 与目标 Host 也按同一名单校验。
2. 客户端只根据反馈请求的 `request.sessionId` 选择 Host，避免消息 ID、反馈文字或版本号中的字符串干扰路由。
3. 复用既有虚拟 ID 双向转换与 Gateway（网关）派发，将会话 ID 还原成目标真实 ID，保留消息 ID、反馈文字、版本号和业务响应。

## 验证

新增 `tests/peer-host-feedback.spec.ts`，在内存中串起页面分流、代理 Host、两台目标 Host 和各自 Gateway。HTTP（超文本传输协议）请求和监听入口使用夹具，状态文件只落在本次创建的仓库临时测试目录并在退出时清理。

- 改动前，新测试失败：远程查询直接返回本机反馈结果，证明没有进入目标 Host。
- 改动后，验证读取、保存、删除、版本冲突及会话级反馈转发；两台目标使用相同真实会话 ID，反馈状态仍互相隔离。
- 消息 ID 与反馈文字故意携带另一台 Host 的虚拟会话 ID，验证不会改写这些字段或错误选择 Host。本机反馈文字引用远端会话时仍交给本机服务。
- 目标存储失败保留原始错误码与提示，不伪造空反馈或成功结果。
- 相关 36 项回归通过，涵盖反馈、原生协议、派发、传输、交互事件、子会话、标题同步与原生连接夹具。
- `pnpm run typecheck`、`pnpm run version:check`、`pnpm run capability:check` 和 `git diff --check` 通过。

## 生效边界

本次完成仓库源码修复和模拟链路验证。聚合端与目标 Host 均需加载包含本修复的插件代码；旧版目标白名单仍会拒绝反馈方法。

没有执行构建、服务启动重启、安装或发布，没有操作 Desktop 的配置、插件、进程或界面。实际运行环境的反馈界面尚未实测。
