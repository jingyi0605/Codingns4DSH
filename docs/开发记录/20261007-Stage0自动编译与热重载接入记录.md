# Stage0 自动编译与热重载接入记录

## 问题与边界

原来的 `pnpm run dev:watch` 只运行 `tsc --watch` 和 `tsdown --watch`，不会让运行中的
Host 自动采用新代码。Stage0 又因终端 keyed Slot（带键的界面注册槽）重复注册问题，
显式关闭了官方 Client HMR（客户端热模块替换）；每次修改后都要手工重启和刷新。

用户选择单命令启动：`dsh-stage0` 托管编译监听，退出时一并关闭。本次只修改本仓库，
不启动、重启真实 Stage0，不操作 Web 或 Desktop 的 Profile、插件和进程。

## 实现

- `scripts/run-dsh-stage0.sh` 保留原有独立 DSH_HOME、启动参数和退出诊断，交由
  `scripts/stage0-runtime.mjs` 管理本次创建的 DSH 与编译监听进程。
- `scripts/dev-watch.mjs` 仍使用原来的两路编译器；被托管时通过 IPC（进程间通信）
  通知首次编译成功，独立执行时继续向当前终端输出。TypeScript 强制英文、无颜色的
  watch 状态，结合当前 tsdown 的成功日志判断两路就绪，避免首次启动载入旧产物。
  托管器等待上限为 90 秒，超时或监听进程失败会退出并打印原因。
- 编译器在独立进程组中运行，退出时回收 pnpm 及其派生进程。编译监听意外退出也会
  停止本次 DSH；只管理本次子进程，不扫描或结束已有监听和其他应用。
- `dsh-stage0.patch.yml` 为原生 `@deepseek-ai/dsh-hmr` 指定仓库绝对 base，监听
  `data/build/dist`，覆盖上游忽略 `data` 的默认规则；忽略 Client、声明和 source map，
  使用 800 毫秒防抖合并 Host 编译写入。
- Host 的 Fiber（插件生命周期实例）退出时取消设置监听并关闭已激活功能，防止重载后
  旧网络与适配器资源残留。会话读取修复包装也按所有权撤销，避免重载后逐层叠加包装。
- 官方 `client-hmr` 行继续禁用。`src/host/stage0-dev-hmr.ts` 只在 Stage0 启动器
  注入专用环境变量时，载入 `scripts/stage0-client-hmr.mjs`。该脚本从本次 Stage0
  启动器所在运行时解析官方 Host transport（传输实现），复用其 500 毫秒产物轮询、
  缓存失效和 SSE（服务器发送事件），不启用官方浏览器局部替换代码。
- 页面监听文档相对的 `plugins/events`，仅对 CodingNS 的新产物版本自动整页刷新，
  一秒内连续通知合并。初次图、重复版本和其他包不刷新；事件流重连后通过新图补齐
  错过的变化，离开页面时取消计时器和连接。这样不会复用上一代终端注册。

## 使用

首次源码安装与 `dev:link stage0` 步骤不变。之后只需：

```bash
dsh-stage0
# 等价入口
pnpm run dsh:stage0
```

如果已有手动启动的监听，保留原终端并关闭 Stage0 的托管监听：

```bash
DSH_STAGE0_WATCH=0 dsh-stage0
```

此开关只关闭自动编译，Host 和页面重载仍启用。`--dump-config`、
`--dump-config-schema`、`--dump-default-config`、帮助、版本与 `plugin` 命令不启动监听。
正在运行的旧 Stage0 需要用户自行在合适时机退出并使用新入口启动，才能应用新配置。
前端重载采用整页刷新，页面内临时状态会重新初始化。
