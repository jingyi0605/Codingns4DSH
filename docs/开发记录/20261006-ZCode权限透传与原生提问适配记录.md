# ZCode 权限透传与原生提问适配记录

## 核心判断

✅ 值得做。旧驱动没有权限和问题应答接口，真实交互请求被统一回复为空对象，无法完成 ZCode 的交互协议。本次将这两类请求接入现有 DSH 原生审批和问题入口。

## 会话包证据与实机范围

用户提供的 `dsh-session-session-2190087f-44c5-473a-a38e-8db441c19b44.zip` 只有一份 `session.v4.jsonl`，共 20 行。会话使用 `workspace-write` 文件策略、`ask` 审批策略，用户要求通过提问组件提出计算题。最后记录了 `zcode / deepseek/deepseek-flash` 路由，未记录助手正文、问题、审批、失败或回合结束。因此不能仅凭会话包判断最终错误。

实机使用本机 ZCode 3.14.4 的 `/Applications/ZCode.app/Contents/resources/glm/zcode.cjs app-server`，通过标准输入输出协议驱动独立进程。测试工作目录位于本仓库 `data/testing/zcode-interactions/workspace`，使用 DeepSeek Flash 模型。不连接或操作 DSH Desktop，不修改其 Profile，不启动、重启或构建 Stage0。

协议字段依据本机分发代码中的严格校验结构和实际返回事件核对。模式与提问自动继续行为另核对了 [ZCode 官方安全确认文档](https://zcode.z.ai/en/docs/safety-confirm)。

## 关键洞察

- 数据结构：业务 `params.requestId`、线协议 RPC `id`、工具 `toolCallId` 分别标识交互、应答信封和工具历史，不能混用。
- 复杂度：同一交互重发时，共用一个应答 Promise（异步结果），只投影一次面板；已经回答的 Promise 保留到回合结束，晚到的重发可以直接复用结果。
- 风险点：恢复会话可能保留旧权限模式；`ExitPlanMode` 与普通问题共用 RPC 方法，却会授权实施计划。模式必须逐轮覆盖，计划批准必须走审批入口，DSH 只读状态不能被批准提升。

## 原有实现的审查

【品味评分】🔴 交互部分缺少实现。

【致命问题】

1. `interaction/requestPermission`、`interaction/requestUserInput` 被回复 `{}`，不符合严格结果结构。
2. 没有实现 `respondPermission`、`respondQuestion`，也没有声明对应能力。
3. 没有下发当前 DSH 权限模式，恢复会话和连续回合会沿用 Provider 状态。
4. 先等待 `session/send` 应答再消费通知，若 Provider 等待交互决定后才回复 send，会形成双向等待。
5. 默认允许 ZCode 五分钟后自动继续未回答问题，与 DSH 阻塞式问题组件的行为不一致。

【改进方向】统一维护每轮交互表，协议转换留在 ZCode 驱动边界，复用现有 DSH 消息投影，不增加 Client 专用组件。

## Linus 式方案与实现

### 逐轮同步权限

在 `session/create|resume` 后、发送消息前执行 `session/setMode`，参数为 `{ sessionId, mode }`。

| DSH 有效状态 | ZCode 模式 |
| --- | --- |
| `read-only`，任意审批策略 | `plan` |
| 显式 `plan: true` | `plan` |
| `workspace-write + ask` | `build` |
| `workspace-write + never` | `edit` |
| `danger-full-access + ask` | `build` |
| `danger-full-access + never` | `yolo` |
| 权限缺省或只读到部分状态 | `build` |

缺省状态覆盖恢复会话可能残留的宽松模式。模式同步失败直接终止发送，不静默沿用未经确认的模式。

**边界：ZCode 执行模式不等同于 DSH 的操作系统级文件沙箱。** `edit` 允许自动编辑，但命令仍可能要求审批；它并不提供工作区路径的系统级隔离。本次适配实现原生模式和审批决定映射，没有为整个外部 CLI 增加文件系统隔离机制。

### 权限请求

真实方法是 `interaction/requestPermission`。公共事件保留工具名、调用 ID、请求原因和完整工具输入，进入 DSH 原生 `requestApproval`。

批准返回 `{ "decision": "allow" }`，拒绝返回 `{ "decision": "deny", "reason": "..." }`。不下发 `permissionUpdates`，避免把 DSH 的单次授权变成 ZCode 的项目永久授权。

### 普通提问与计划批准

普通 `AskUserQuestion` 调用产生 `interaction/requestUserInput`，其 `questions` 没有稳定问题 ID，选项含 `label`、`value`、`description` 和可选 `multiSelect`。转成 DSH `question-request` 后，经已有原生 `askQuestions` 入口显示，工具历史沿用 `toolCallId`。

ZCode 的答案键是**原始问题正文**，不能回传 DSH 的 `question-1`：

```json
{
  "action": "accept",
  "content": {
    "answers": {
      "17 + 25 等于多少？": ["42"]
    }
  }
}
```

多选按选项 `value` 回传，自由文本作为附加答案传入，问题原始正文的空白也保留。空回答数组回传 `{ "action": "cancel" }`。

`schema.interaction === "plan_approval"` 时走原生审批并显示完整计划。批准必须回传 `{ "action": "accept", "content": { "answer": "approve" } }`，拒绝回传 `decline`；DSH 只读会话即使收到上层批准，也强制拒绝。

运行时偏好设置 `askUserQuestionAutoResolutionEnabled: false`，让用户回答、取消或停止决定后续动作。

### 生命周期与附带修复

- send 应答前立即消费交互通知；监听器在恢复和订阅完成后注册，避免混入历史重放。
- 同一业务请求即使使用不同 RPC id 重发，也只生成一份原生面板，每个 RPC 应答继续使用其原始 id。
- 取消、打断、进程退出、驱动释放和消费者退出时，未完成权限返回 deny，未完成问题返回 cancel，并清理等待。
- 没有活动回合消费者时，历史或迟到交互直接拒绝，不留下无人应答的 Promise。
- 实机还发现：切换 DeepSeek 时缺少思考档位会返回 `Reasoning level is required for deepseek/deepseek-flash`。驱动现在从 Provider 目录保留 `reasoning.defaultLevel`，未显式选择档位时使用该默认值。这与会话包停止位置相符，但包中没有异常记录，不能据此断言原会话只有这一项原因。
