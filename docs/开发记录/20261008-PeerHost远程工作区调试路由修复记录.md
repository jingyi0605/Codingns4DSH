# PeerHost 远程工作区调试路由修复记录

## 问题与根因

通过 PeerHost 打开远程工作区的调试页时，标题显示虚拟工作区 ID，页面报错“Workspace 根目录不可用”。

终端环境查询已通过 DSH 原生远程调用取得虚拟工作区 ID，但插件自身的 `debug/*` RPC（远程过程调用）没有进入 PeerHost 分流，仍交给当前 Host 的 `DebugWorkspaceService`。本机无法用远端虚拟 ID 解析根目录，因此配置读取失败。Host HTTP 代理白名单也缺少调试路由。

此外，调试页原先用空参数查询 `terminal/status`，得到的是本机 Shell 和平台信息，无法反映远端启动环境。

随后用户反馈“远端 Host 插件 RPC 失败: HTTP 401”。检查发现首轮修复遗漏了目标 Host 的 LAN（局域网）登录保护白名单：发送端允许调试路由，接收端却未把它识别为可用 Bearer（持有者票据）认证的请求，转入浏览器 Cookie 校验后返回 401。首轮测试没有执行目标 LAN 鉴权，这是验证缺口。

## 核心判断与方案

值得修复。工作区归属决定执行 Host，真实目录只能由目标 Host 解析；不能通过补本机路径映射绕过错误。

- 页面 Transport 与原生 Connection 共用插件端点识别函数，补齐 `debug/*` 与带资源作用域的 `terminal/status` 分流。
- 复用已有 `peerHost/request` 代理、凭据与 RPC 信封，不增加另一套连接通道。
- 仅还原调试请求顶层的 `workspaceId`、`sessionId` 和 `dshSessionId`；配置中的命令、参数、环境变量保持原文。
- 调试只按顶层资源选择 Host；聚合暂时缺失时返回明确作用域错误。跨 Host 参数拒绝转发，远端业务错误保持失败，不回退本机。
- 调试页取得工作区后再查询目标 Shell 状态，启动时携带所属 DSH 会话 ID；切换会话时清空旧配置、实例、代理绑定和 Shell 状态。
- HTTP 白名单只新增调试命名空间与终端状态的 POST 请求，未开放其他终端管理接口。
- 后续补修把两端重复的 HTTP 白名单合并到 `src/shared/peer-host-http-routes.ts`，发送端代理与目标 LAN 入口共用路由匹配函数；原导出路径保持兼容。
- 客户端保留代理返回的认证错误码和脱敏原因，避免把 `PEER_HOST_SESSION_REQUIRED` 再次覆盖为笼统的 HTTP 401。

本次沿用现有调试接口，不迁移 `.codingns/debug.json`，不修改根目录检查。本机工作区调用继续使用原路径。

## 验证边界

网络、终端和端口观察均使用测试夹具，未启动实际调试进程，未做真实远端界面联调。本轮未构建、安装、发布或重启服务，也未操作 Desktop Profile；已有 OpenCode 与并行 Git 工作区修改保留。

修复生效需要当前聚合 Host 加载包含此修复的插件及前端资源，**目标 Host 也必须加载更新后的 LAN 鉴权白名单**；仅更新发送端无法消除目标旧白名单引起的 401。目标端调试业务接口本身保持不变。此次验证不涉及调试服务代理 URL 的跨 Host 访问。
