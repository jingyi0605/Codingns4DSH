# Codex 插话协议参数与回合状态修复记录

## 问题与依据

Codex 适配器已经声明 `steer`（运行中插话）能力，但 `turn/steer` 请求传入了 `turnId`。Codex app-server（应用服务器）的[官方协议](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)要求使用 `expectedTurnId`，并校验它与当前运行中的回合一致。原实现缺少必填参数，会收到 `missing field expectedTurnId`。

插话响应返回 `{ turnId }`，原实现却使用只解析线程 ID 和通用 ID 的 `readId()`，没有读取协议中的回合 ID。

## 修改

- `src/host/cli-adapters/codex-driver.ts` 的插话请求改用 `expectedTurnId`，保持线程和文本输入的结构不变。
- 响应复用现有 `readTurnId()`，不扩展通用线程解析函数。
- 发起请求时保存目标回合，只有等待响应后本地回合仍然匹配时才更新状态，避免迟到响应恢复已经结束或被替换的回合。
- `turn/interrupt`（回合中断）仍使用 `turnId`，插话失败继续透传原始协议错误。

## 回归验证

新增 `tests/cli-adapters-codex-steer.spec.ts`，在内存中模拟严格校验参数的 app-server，不启动真实 CLI 或调用模型。

普通回合和分段回合分别覆盖：

1. 连续插话使用 `expectedTurnId`，复用当前回合，中断请求保持原协议。
2. 回合失配透传原始错误，不重试或覆盖本地状态。
3. 已结束回合拒绝插话，不发送额外 RPC（远程过程调用）。
4. 回合结束后迟到的成功响应不会恢复旧回合。

另覆盖未启动的会话拒绝插话，共 9 项。修改驱动前，两项正常插话测试均复现 `-32600 / missing field expectedTurnId`；修复后全部通过。
