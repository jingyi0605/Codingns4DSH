# ZCode 用量、上下文与提供商识别修复记录

## 核心判断

✅ 值得做。截图中的百万级 token 来自全局账单污染；提供商发现没有理解原生配置里的模板继承、`api` 和 `access`，当前模型也没有参与来源选择。这些都是实际数据错误。

【品味评分】原有统计和来源发现为 🔴；修复后使用独立的本轮统计和提供商配置解析，复用已有 DSH 投影及上游读取器。

【致命问题】全局账单、会话去重累计、单次模型请求和当前上下文被当成同一种数字；来源发现则假设地址和密钥必定放在同一个对象。

【改进方向】先明确数据所属范围，再在 ZCode 协议边界转换，不为它增加独立的余额界面或上下文界面。

## 会话包与实机证据

第二份附件 `dsh-session-session-84b9fcac-13f3-4d1e-b922-0d81ba5d6659.zip` 包含 27 行事件。问题正常回传 `408`，但两个用量记录分别为 16,392 和 1,627,138 token，最后一份覆盖前一份。缺少 `description` 的首次调用没有作为原始工具失败保存，只有模型重试说明。

使用本机 ZCode 3.14.4 的独立 `zcode.cjs app-server`，在仓库测试目录连续执行两轮计算题，发现：

- `usage/stats` 的 `range: all` 是全局账单，修复前第一轮被覆盖为 1,788,484 token。
- 新版 `session/usage` 会按 `inputBaselineBySource` 扣除历史输入基线，不是请求账单；主对话的缓存分桶还被归零，不能简单改成前后累计值相减。
- 同一请求先发送带 `type: model_request_completed` 的网络通知，再发送带 `stopReason` 的模型完成通知，两者都有 `usage`。不能各算一次。
- 实际主请求报告 `contextWindow: 1000000`，目录和快照却报告 `200000`。实际请求的窗口优先于目录默认值。
- 当前个人 DeepSeek 配置只有 `config.access.apiKey`，地址继承内置 `templateRules` 的 `config.api.baseUrl`：`https://api.deepseek.com/anthropic`。

## 实现

### 本轮用量与上下文

新增 `zcode-telemetry.ts`，每轮创建一份状态，分别维护请求用量、最后一次主请求上下文、工具输入及事件去重表。

1. 只累加带 `stopReason` 的模型完成通知，忽略网络镜像；按 `eventId` 或 `seq` 去重，排除其它会话。
2. 保留输入、输出、缓存读取和缓存写入桶，未缓存输入经现有 `usageChunk` 转换。
3. 总消耗累加本轮各次请求；上下文只采用最后一次主请求的占用和窗口，子代理不会覆盖它。
4. 移除全局 `usage/stats` 查询。新版基线去重累计没有真实请求事件时不冒充账单；旧版原始累计桶仍支持前后求差及计数重置。
5. 没有原生请求窗口时才补读 `session/read`；快照不得覆盖已经得到的真实窗口。
6. 查询超时使用 `killOnAbort: false`，在 `finally` 清理定时器，避免账单查询超时杀掉可复用 CLI。
7. 完成用量继续走 DSH 原生 `appendUsageSample` 和 `appendRequestContext`，不新增 Client 特例。

### 提供商与余额

新增 `zcode-provider-config.ts`，按模板、内置规则、个人覆盖顺序解析原生配置，读取 `config.api` 的地址和 `config.access` 的密钥。账号凭据按 Provider 前缀选择，并兼容本机 AES-GCM（认证加密）格式；解密失败不发送密文。

`ProviderSubscriptionService` 使用 `modelId` 中的原生 Provider 前缀选择来源：

- 官方 DeepSeek 调用已有官方余额读取器，并将 `/anthropic` 地址归一化成 `/user/balance` 的 API 根地址。
- 其它已支持的官方厂商复用原有官方读取器，官方地址识别允许个人 Provider 使用自定义名称。
- 自定义地址只传入当前来源，交给已有 New-API／Sub2API 统一分类器，分类缓存和失败行为保持不变。
- 未识别、缺少凭据或读取失败时不借用其它账号的余额；Start Plan 模型仍读取原有 ZCode 套餐。
- 显式注入的来源继续优先；New-API 自动发现兼容旧规则格式，同时按当前 Provider 筛选。

### 提问与工具历史

发送前附加简短宿主能力说明，明确 `AskUserQuestion` 必填 `question`、`header`、`multiSelect`，每项选项必填 `label`、`description`，并说明题目／选项数量、唯一性、自由文本和取消行为。校验发生在交互 RPC 发出前，不能靠修改答案转换器补救缺失参数。

原生 `tool_input_*` 片段按 `toolCallId` 组装，`tool.updated` 的运行、结果和错误转成公共工具观察事件。`AskUserQuestion` 统一为 `question`，与交互请求共享调用 ID，避免重复卡片；失败重试保留不同调用 ID。

实机允许写入测试遇到原生“写入前必须先读取文件”的限制，记录了失败的 Write、成功的 Read 和再次成功的 Write，证明真实失败与成功重试均能透传。

## 兼容与边界

- 保留已有权限应答、问题答案文本回传、多选、自定义文本、取消及附件路径适配。
- ZCode 的 `plan` 可能内部表示为 `mode: build` 加计划状态；写入行为以真实只读测试为准，不能仅看快照 mode 字段。
- 开发验证阶段仅更新仓库源码、测试和文档；没有构建、启动或重启 Stage0，也没有操作 DSH Desktop／Web、安装插件、提交或发布。后续 Git 提交按照用户明确授权分批执行。
- 运行界面仍需在用户安排的加载时机采用源码改动；已有会话中落盘的错误累计没有回写修改。
