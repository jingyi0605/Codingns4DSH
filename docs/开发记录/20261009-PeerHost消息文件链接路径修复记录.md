# PeerHost 消息文件链接路径修复记录

日期：2026-10-09

## 核心判断

✅ 值得修复。远端文件树可以读取同一文件，消息链接却提示文件不存在，是文件位置表达没有转换成目标 Host 文件路径的问题。

## 关键洞察与代码审查

- 品味评分：🟡 凑合。原生消息与文件树共用资源协议，但消息路径中的 Windows 盘符前缀和行号没有统一处理。
- 数据结构：文件位置包含会话身份、路径和行号；行号属于导航参数，不能继续留在文件名中。目标平台从所属远端工作区的真实路径识别。
- 致命问题：截图中的 `/C:/Code/zhiweijz/docs/20261009-后端全面审查与重构清理清单.md:170` 原样到达 Windows 文件定位接口。
- 复杂度：在原生资源入口和已有文件转发边界复用同一个位置解析函数，无需新增文件代理协议或扫描正文。
- 风险点：POSIX 文件名允许冒号，本机平台也不能代表远端平台。修正只作用于已知 Windows 远端工作区，保留 POSIX、本机和未知平台的路径。

## 根因证据

核对 DSH 0.2.1-alpha.1 的本地原生源码：

1. `dsh-client-ui-primitives` 的 `parseFileLink` 支持 `#L170` 行号片段，没有拆分 `:170`。截图中的按钮标题就是原始路径。
2. `dsh-client-ui-chat` 的 `openFile` 使用 `fileAddressFor(sessionId, cwd, path)` 构造会话文件资源，保留会话身份，但没有纠正 `/C:/` 或位置后缀。
3. `dsh-api-workspace-files` 文件资源调用 `workspaceFiles/stat`；预览调用 `read`、`readBytes`；变化通知调用 `changes`。这些方法均已在 PeerHost 原生协议白名单中，转发会把 `workspaceFileScopeId` 还原为目标会话 ID。
4. 文件树返回正常的路径，构造同一种会话资源后可以读取。

使用 Node 的 `path.win32.resolve` 回放 Windows 解析：

```text
工作区：C:/Code/zhiweijz
消息路径：/C:/Code/zhiweijz/docs/清理清单.md:170
错误解析：C:\C:\Code\zhiweijz\docs\清理清单.md:170
正确解析：C:\Code\zhiweijz\docs\清理清单.md
```

因此，本次没有发现消息链接缺少独立远程协议；实际遗漏在路径与导航参数的转换。

## 修复方案

1. 新增共享位置解析：已知 Windows 工作区下，把 `/C:/` 纠正为 `C:/`，拆出 `:行` 或 `:行:列`，仅将有效行号提供给原生预览导航。
2. PeerHost 随 `sidebarRight` 服务生命周期包装原生 `openResource` 和 `openResourceIn`。从资源地址中的虚拟会话查所属工作区，不读取前台选择；保留原有放置参数、查询片段和显式行号；停用时释放包装。
3. Host 原生请求改写器从当前作用域对应的工作区读取真实路径，统一纠正 `workspaceFiles/*` 的路径及 `readBytes` 的 `baseFile`。已持久化的旧标签也可读取，变化订阅与读取使用同一目标路径。
4. 未改动原生协议白名单、目标局域网白名单或远端文件正文。
