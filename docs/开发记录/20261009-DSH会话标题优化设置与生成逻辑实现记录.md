# DSH 会话标题优化设置与生成逻辑实现记录

## 行为

在「设置 → Codingns4DSH → 工作区会话增强」新增「优化DSH会话标题生成逻辑」，配置键为 `workspaceSessionEnhancement.optimizeSessionTitles`，默认关闭。旧设置会补齐默认值。工作区会话增强主开关和这个子开关同时开启才生效；设置更新直接驱动 Host（宿主）处理，不依赖设置页是否打开。

开启后，原生自动标题请求使用新提示词：概括完整动作与对象，保留必要技术名称和版本号，去掉开场语，不添加原消息没有的事实。中文通常为 12～24 字，简单主题可以更短；英文通常为 5～10 词；输出最多 64 个 Unicode 字符、24 个中日韩文字，且不超过 80 UTF-8 字节。

模型先生成一次。结果超长、多行或以省略号、分隔标点结尾时，最多再请求一次重新概括，不直接裁剪模型标题。两次合计采用 30 秒取消期限，并保留原生上游取消信号。

不批量重命名历史会话，不改变标题生成时机和原生手动命名规则。原生 API 标题路由保持不变；CLI 虚拟提供方没有辅助文本调用能力，标题请求落到这类提供方时，使用已配置的 DSH 默认原生模型。主对话、上下文压缩和未知第三方标题帧保持原样。关闭设置会中止本功能正在处理的请求，后续请求恢复原生行为。

## 实现

- 设置契约、Host schema（配置结构校验）和工作区面板共用同一个布尔配置，补齐中英文文案。
- Host 模块登记在 FeatureRegistry（功能注册表），声明 `llm.text` 和新增 `session.title` 能力要求；缺少能力时仅停用此模块。
- DSH 版本相关接口封装在 `src/dsh-capabilities/host/session-title-adapter.ts`，版本门禁集中在能力路由。
- 使用 `AsyncLocalStorage`（异步作用域存储）隔离嵌套调用。真正的优化请求仍走原生 LLM（大语言模型）服务与其他中间件，自身不递归；并发会话互不串扰。
- 每次真正优化调用追加 `session/title-llm-request`，记录实际提示词、消息、提供方、模型和输出限制。原生请求日志保留，优化调用使用 `codingns-title-optimization` 标识。
- 成功输出完整原生文本流，由 DSH 负责接纳和保存。失败终态、工具请求、输出未正常结束均保留失败，不把半截模型输出当成成功。

## 失败与兼容保护

模型失败时，仅当请求前后仍是同一个兜底标题事件、消息来源一致且没有取消，才追加更可读的兜底标题，来源仍明确标为 `fallback`（兜底），不伪造模型身份。

兜底优先保留能装下的完整断句；没有可靠断句时，在可读长度与字节预算内保留文本并明确显示省略号。按字素边界处理 Unicode，避免截断 emoji 或组合字符。人工标题、已有模型标题、新标题修订及不同来源消息不会被迟到的失败覆盖。

原生 API 标题请求保留现有路由。CLI 标题请求只允许改用用户已配置的 DSH 默认原生模型，不从模型目录随意挑选。默认模型缺失或仍指向 CLI 时，以 `CODINGNS_SESSION_TITLE_NATIVE_MODEL_REQUIRED` 明确失败并改善兜底；实际 API 调用失败时保留原始错误，不再尝试其他模型。80 字节限制匹配已核对的 DSH 默认接纳上限；宿主自行配置更小上限时，其接纳规则仍由宿主决定。

接口调查见 `docs/调查报告/20261009-DSH会话标题生成扩展接口调查.md`。

## 设置写入拒绝的补充修复

用户实际点击开关时，Host 返回 `CODINGNS_SETTINGS_FIELD_FORBIDDEN`。原因是最初只补了设置 schema 和界面，遗漏 `src/host/rpc.ts` 的嵌套字段白名单；已有测试覆盖设置渲染与后台 watch（配置更新监听），没有走真正的 `settings/set` 写入边界，因此没有发现这个缺口。

修复仅将 `workspaceSessionEnhancement.optimizeSessionTitles` 加入已有白名单，不放宽其他字段或嵌套路径。新增回归先在修复前复现完全相同的错误，再接通真实客户端设置桥、Host RPC 主处理器、设置处理器与标题优化模块，验证开关开启和关闭均能保存、回读并改变生成行为；未知字段、更深的嵌套路径和只读提供器依然拒绝写入。修复后上述 93 项回归与类型检查通过。

该错误来自 Host 写入边界，运行实例需要加载修复后的 Host 代码；仅更新或刷新客户端不能改变旧 Host 的白名单。

## 2026-10-22：Windows 路径兜底与 CLI 标题路由修复

实际会话日志显示：首条输入以 Windows PPTX 文件路径开头，原生先保存路径前缀作为兜底；标题请求经优化后仍使用 `codingns-cli-claude-code / claude-opus-5.5`，随后优化的失败兜底把标题写成了 `"C`。用原始输入调用兜底函数得到相同结果。该会话没有保存生成异常文本；CLI 标题请求旁路到只支持 Agent 回合的虚拟 Provider，是源码中能够确认的失败路径。

修复分支为 `fix/session-title-generation`，基于本地 `main`。变化如下：

- 兜底识别开头的 Windows 文件路径（含引号、空格和 `@` 引用）；有任务描述时使用描述，只有路径时保留文件名。ASCII 冒号不再作为断句边界，避免切断盘符、URL 和时间。
- 仅当原生标题请求指向 `codingns-cli-*` 时，读取 `agentDefaultModel.currentSelection()`，改用用户配置的原生模型；按目标模型能力选择最低思考档位，与原生标题生成器一致，避免传递 CLI 专属档位或用高思考消耗短标题预算。旧服务无能力查询接口时保留原生默认档位。每次调用重新读取配置，重概括和实际请求日志保持同一路由。
- 未配置原生默认模型时明确失败并保留可读兜底；认证失败、取消、已有人工标题和标题修订保护仍保留。未修改现有会话文件。
