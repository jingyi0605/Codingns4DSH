# Desktop 订阅用量实时上游刷新修复记录

## 问题

订阅用量入口读取的是会话的 `adapterId`、`providerId` 和 `modelId`。此前 Client 侧存在两个会让结果滞后的状态窗口：

1. 会话配置共享快照默认保留 5 秒。模型或 Provider 切换后，订阅 Slot 仍可能拿到切换前的配置。
2. 选择器只在适配器 ID 变化时通知会话适配器缓存。同一适配器内部切换模型或 Provider 时，订阅 Slot 不会重新挂载，因此同类适配器会一直显示上一次的上游用量。

此外，较早发出的 `session/get` 返回后会覆盖刚由 `session/set` 写入的共享快照，导致快速切换时旧 Provider 重新成为后续读取结果。

## 修复

- 增加 `publishSessionSelection`，同一适配器的模型或 Provider 变化也会通知订阅和其它会话级 Client 组件。
- 订阅 Slot 刷新当前用量前强制读取最新会话配置，避免继续使用短期配置快照；共享配置读取不接受订阅组件的专属取消信号，防止卸载一个组件时误取消其它组件共用的请求。
- 让较早的在途 `session/get` 只有在仍是当前缓存请求时才能写回结果，不能覆盖新选择。
- 保留普通会话配置读取的 5 秒合并缓存，只有订阅用量的实时刷新绕过该快照，避免无关组件增加 RPC。

## 影响范围

修改只落在仓库的 Client 共享状态、订阅用量 Slot 和回归测试；没有操作 Desktop Profile、Desktop 进程或安装目录。Web 与 Desktop 共用这条 Client 逻辑，因此两端的会话选择变化都按当前 `providerId` 和 `modelId` 重新分流用量读取。
