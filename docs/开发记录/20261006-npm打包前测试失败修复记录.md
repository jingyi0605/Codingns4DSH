# npm 打包前测试失败修复记录

## 问题与原因

本地打包脚本 `scripts/publish-npm-package.sh` 在生成 tarball（压缩包）前执行类型检查与完整测试。用户日志中的两个断言失败导致流程提前退出，尚未进入 `npm pack` 阶段。

1. `tests/subagent-bridge.spec.ts` 仍期待 Claude Code 的 `--permission-prompts host` 参数。驱动已经改用 `--permission-prompt-tool stdio`，用于原生权限与结构化提问；测试没有同步这项协议修复。该失败在定向测试和完整测试中均能复现。
2. `tests/profile-install-check.spec.ts` 通过临时 Shell 文件模拟 PATH 中的旧版 dsh，并断言必须打印旧版提示。生产探测设有 2 秒超时；用户日志中的约 2105 毫秒耗时与探测超时后的「未检测到当前 DSH 运行时」分支吻合。本轮定向测试与首次完整测试都未复现这一失败，因此将其判断为依赖临时进程启动耗时的偶发问题，而非版本兼容性判定错误。

## 修改

- Claude 子代理托管测试改用当前 stdio 权限协议参数，同时检查托管开启后基础参数仍被保留。
- 安装检查测试继续将 Profile 脚本复制到独立临时目录运行，只在隔离子进程内模拟 `spawnSync` 的版本命令结果；版本解析、来源优先级、兼容性判定和提示输出仍由真实脚本执行。
- 子进程环境清空 PATH，避免探测开发机的真实 dsh；动态导入使用文件 URL，兼容 Windows 路径。
- 补充 PATH 兼容版本仍只提示、版本命令超时仍允许安装并保留运行期校验提示的用例。

生产安装脚本与 Claude 驱动未作修改；保留真实运行时不兼容时拒绝安装的规则。

## 验证

- 定向测试：`tests/profile-install-check.spec.ts`、`tests/subagent-bridge.spec.ts`、`tests/cli-adapters-stream.spec.ts`，34 个用例全部通过。
- 本地打包流程：指定独立 `NPM_PACKAGE_OUTPUT_DIR`，执行 `bash scripts/publish-npm-package.sh --mode pack`，版本同步、类型检查、构建和完整测试通过。
- 完整测试：1529 个用例，1528 通过、0 失败、1 跳过。
- 生成 `jingyi0605-codingns4dsh-0.2.1-beta.3.tgz`，共 1396 个打包条目；1366 个构建文件的 SHA-256（内容摘要）与本地 `data/build/dist` 逐文件一致。

产物保存在仓库的 `data/build/npm/` 独立验证目录，已有 tarball 保留。修复验证阶段仅作本地打包，没有发布 npm，没有操作 Desktop 或启停 Stage0。随后按用户要求，将 Profile 安装检查测试、Claude 托管参数测试和本记录分为三批提交；没有推送。
