# 全局助理 Windows 兼容修复记录

日期：2026-10-07。范围：全局助理未提交代码中已经确认的语音运行环境兼容问题。

## 修复结果

| 模块 | 原问题 | 修复 |
| --- | --- | --- |
| Python 进程环境 | Windows 管道编码可能是 ANSI；混合大小写的 PythonHome／PythonPath 未清除 | 共用环境生成器，删除受控变量的大小写变体，固定 UTF-8，保留代理、证书和 PATH |
| MOSS 工作进程 | 中文正文、路径及错误可能乱码；取消后立刻重试时旧进程仍在关闭 | 显式启用 Python UTF-8 模式；取消、释放和重试等待 close；流式解码 stderr |
| 独立 Python 安装 | PATH 优先命中 Git GNU tar 时，Windows 盘符被误当远程主机 | 从 SystemRoot／WINDIR 选择 System32/tar.exe，保持参数数组调用，不经过 shell |
| CPU 推理初始化 | pip 安装成功不代表 ONNX Runtime 等库能加载，缺失 DLL 到模型下载后才暴露 | 安装依赖后、下载模型前实际导入全部推理库；Windows 提示检查 VC++ x64 运行库，保留原始错误和取消原因 |
| TTS 服务生命周期 | 重新初始化、重置和服务释放未等待旧工作进程结束 | 等待进程关闭及旧配置操作结算，再修改模型、环境或开放新请求 |
| 工作进程测试 | 固定调用 python3，Windows 通常仅提供 python 入口 | Windows 默认使用 python，其他平台使用 python3；支持 CODINGNS4DSH_TTS_PYTHON 指定解释器 |

环境准备命令同时使用 `-I -X utf8`：隔离模式会忽略 Python 环境变量，必须由命令行明确打开 UTF-8。工作进程保留原有脚本导入方式，使用 `-X utf8` 和受控环境。

依赖预检不自动安装系统运行库，也不把所有 DLL 错误都判定为 VC++ 缺失。模型下载后的 ONNX 图验证继续保留，预检不能替代模型可用性验证。

## Windows 实机验收

由用户在 Windows x64 的开发环境执行，结果继续归入 spec013 的 TTS.4：

1. 让 Git for Windows 的 usr/bin 排在 PATH 前面，在含中文、空格的 DSH_HOME 下首次准备语音资源；确认独立 Python 解压成功，没有“连接 C／D 主机”错误。
2. 在宿主存在 PythonHome、PythonPath、PythonIOEncoding 等混合大小写变量时运行，确认托管解释器不读取宿主库；中文与表情播报、参考音色导入和中文路径均正常。
3. 验证依赖加载失败在“检查 CPU 推理依赖”阶段停止，保留 DLL 原文；修复系统依赖后重试，确认模型下载和图验证正常完成，失败期间旧输出后端与参数保留。
4. 连续执行开始播报、打断、立即重试、重置和重新初始化，确认旧推理进程退出，没有模型占用或重命名失败。
5. 验证真实中文音质、参考克隆、麦克风／扬声器、首音延迟和内存；这些指标不能由模拟模型测试确认。

Windows 本地 MOSS 支持范围仍为 x64，未增加原生 ARM64／ia32 支持。运行工作进程协议测试需要测试机有可用 Python，或通过 CODINGNS4DSH_TTS_PYTHON 指定；产品首次初始化仍自动准备独立解释器。
