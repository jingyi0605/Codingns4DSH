# Codex 原生权限申请工具接入修复记录

## 问题与证据

用户在本插件的 Codex 会话中，用自然语言要求触发权限申请并验证选择。Agent 在 `/private/tmp` 创建文件后直接结束，DSH 没有显示审批面板。

导出会话的工作区是 `/Users/jackson/Code/TEST`，权限状态是 `workspace-write` 和 `approval: ask`；对应 Codex 运行记录是 `workspace-write` 和 `on-request`。测试命令没有申请额外权限，写入成功，导出中没有审批请求或审批决定事件。DSH 的运行时说明本身也允许部分平台临时目录写入，因此不能靠取消临时目录权限来制造审批弹窗。

继续检查插件接入后，发现了独立的能力缺口：

- 安装的 Codex `0.160.0` 将 `request_permissions_tool` 默认设为关闭。
- 适配器只启用了原生提问工具，没有启用原生权限申请工具；原会话的工具上下文也没有 `request_permissions`。
- 驱动已有 `item/permissions/requestApproval` 的转换和 `{ permissions, scope }` 应答，但旧测试直接注入协议请求，无法发现模型侧工具没有启用的问题。

用户不应每次编写提权参数和测试路径。工具可用性和宿主交互指令应由插件统一提供。

## 修改

### 插件进程启用权限工具

在 Codex app-server（应用服务器）的启动参数中增加：

```text
-c features.request_permissions_tool=true
```

覆盖参数放在 `app-server` 子命令前，只影响插件启动的子进程，不写入全局配置。模型目录读取和会话运行使用同一组启动参数。

使用配置覆盖而不是 `--enable`，避免后者对未知 feature（功能开关）的严格校验影响旧版启动。本机验证了该配置能够启用工具，同时接受未知 feature 配置；没有逐一回放所有历史 Codex 版本。旧版没有该工具时仍保留原生命令提权通道。

### 宿主权限指令

为 `thread/start` 和 `thread/resume` 统一追加权限交互指令，保留已有提问和子代理桥接指令：

- 权限边界和审批策略读取当前回合上下文，不把线程创建时的权限档位写死在指令中。
- 需要额外权限时优先使用 `request_permissions`，申请最小范围并等待结果。
- 用户要求验证审批时，由 Agent 自行申请允许范围之外的最小权限；普通临时文件写入不能冒充审批测试。
- 旧版工具列表缺少 `request_permissions` 时，使用原生命令审批通道，不要求用户代写命令。
- `never` 策略下不申请或反复重试；已有所需权限时如实说明无需额外授权。
- 检查实际授予范围后执行和验证；拒绝、取消或未授予权限时停止对应受限操作。

宿主指令负责选择申请通道，不能替代执行沙箱。现有沙箱模式、临时目录语义、审批回传协议和回合级授予范围均沿用原实现。

## 验证

新增 `tests/cli-adapters-codex-permissions.spec.ts`，在内存运行完整插件链路：

```text
llm/stream → Feature → Registry → Codex 驱动 → 消息投影 → 原生审批桥接 → DSH 决定 → Codex 应答
```

模拟运行时仅在启动参数启用原生权限工具时发送请求。修复前，测试明确失败于“插件回合在触发 DSH 审批之前结束，原生权限工具未接入”；修复后通过。

新增 8 项检查覆盖普通和分段回合：

- 等待审批时，回合没有结束、没有应答、没有执行受限操作。
- 允许后回传请求的权限画像，且模拟操作成功。
- 拒绝和取消后回传空权限画像，且模拟操作没有执行。
- DSH 审批服务缺失时不给予额外权限。

同时更新启动参数回归断言，并确认恢复已有线程也收到权限交互指令。
