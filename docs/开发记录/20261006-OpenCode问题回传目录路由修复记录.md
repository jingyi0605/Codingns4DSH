# OpenCode 问题回传目录路由修复记录

## 问题现象

OpenCode 适配器能够收到 `question.asked` 事件并弹出 DSH 原生问题对话框，但提交答案时报错：

```text
OpenCode 问题回复失败（HTTP 404）：Question request not found: que_...
```

会话压缩包中的失败请求 ID 是 OpenCode 原生生成的 `que_...`，说明问题发生在服务端定位待回答请求阶段，而不是答案格式转换阶段。

## 根因

OpenCode 的会话、SSE 和交互请求按工作目录实例隔离。适配器发送消息和订阅事件时已经使用 `?directory=<cwd>`，但 `permission` 与 `question` 回传仍使用无目录的全局 URL：

```text
POST /question/:requestID/reply
```

当 DSH 会话的工作目录不是 OpenCode server 的默认目录时，回传请求会落到另一个实例，该实例没有对应的 `que_...`，于是返回 404。

## 修复内容

- `interactionTargets` 同时保存 server 地址和产生交互请求的工作目录。
- 权限批准与问题回答统一复用 `withOpenCodeDirectory()`，保证回传命中产生请求的目录实例。
- `dispose()` 清理交互目标，避免驱动复用已失效的目录上下文。
- 新增带中文工作目录的回归测试，验证权限和问题回传 URL 都携带正确的 `directory` 查询参数。

## 问题工具调用审计信息补强

第二次回放确认回答已经成功传给 OpenCode，但原生历史中的 `tool/call` 仍显示空对象 `{}`。原因是 `question.asked` 事件单独携带了问题内容和工具 `callID`，而初始 `message.part.updated` 的工具输入快照可能还是空对象。

现已在公共问题事件中保留 OpenCode 原生 `callID`，并在同一个工具调用上追加：

- 输入：`requestId` 与完整 `questions`（问题、选项、单选/多选信息）。
- 输出：DSH 回答对象 `answers` 与实际发给 OpenCode 的 `providerAnswers` 二维数组。

因此工具历史可以直接核对“问了什么”和“向 Provider 发送了什么答案”。
