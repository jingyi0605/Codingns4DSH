# DSH 0.2.1-rc.3 升级与插件兼容适配记录

日期：2026-10-24
关联调查：`docs/调查报告/20261024-DSH-0.2.1-rc.3接口与调用变化.md`

## 背景与结论

用户要求三件事：① 把 dsh-stage0 升级到 `0.2.1-rc.3`；② 把插件版本升到 `0.2.1-rc.3`；③ 完成 DSH `0.2.1-rc.3` 的兼容。

rc.3 与 rc.2 的差异只有新增（三个 root 级 list 槽位、`pluginNavigation.openList()`、`whenDraftExists`、`DraftInitializationOptions` 扩展、`/models` 列举），宿主运行时包逐字节一致。因此兼容工作不是改接口适配，而是：放宽版本声明 + 同步能力矩阵上界 + 修正依赖旧上界的测试 + 升级 Stage0 运行时。

## 决策

1. **沿用「-021 路由 + 放宽上界」的做法，不新增 -022 路由。**
   十一条上界为 `<=0.2.1-rc.2` 的路由，其探测点全部是结构判断（`Session Controller` 的 `create/resolveAgent/agents.selectionFor`、`systemPrompt.assemble`、`slots.inject/register/registerFactory`、`connection.admit/createPeer/browserPeer`、`agentTeams` 的八个方法、`sessions.scope`/`conversation.input.for`/`uiWorkspace.openSession`）。rc.3 上这些结构逐字节未变，新增一条重复路由只会让矩阵膨胀、并在 `capability:check` 里多一条未来要退休的路线。AGENTS.md 中「新增 DSH 版本 → 在 matrix/routes 增加新老路由」针对的是**结构变化**，本次没有结构变化。
   与 rc.2 升级的处理方式保持一致（那次也是把 alpha.3 路由的上界从 alpha.3 延到 rc.2）。
2. **能力矩阵上界必须与 manifest 同步放宽。**
   只改 `DSH_COMPATIBILITY` 会出现「插件启用但十一条能力悬空」的静默降级（Team 标记版本不支持、译文气泡不渲染、终端分享入口消失、外部 Agent 模型选择失效）。两者本次一起改。
3. **Stage0 使用独立版本目录 `~/.local/share/codingns/deepseek-harness/0.2.1-rc.3`**，保留 rc.2 目录以便回退；不触碰 Desktop、其他 profile 与 `--from-default-profile`。

## 需要特别注意的地方

- **`scripts/set-dsh-version.mjs` 无法覆盖这 11 条路由**：它用 `replaceAll(previousCompatibility, nextCompatibility)`，只会替换完整的 `>=0.2.0-rc.2 <=0.2.1-rc.2` 串；`>=0.2.1-alpha.3 <=0.2.1-rc.2` 这类起点不同的串必须单独处理。本次用针对性的正则替换完成，并在事后用 `grep -c '0\.2\.1-rc\.2'` 确认归零。
- **本仓库嵌套在父工作区 `CodingNS` 下**：`pnpm install` 会向上找到 `/Users/jackson/Code/CodingNS` 的 workspace root，导致 `data/dsh-codingns/pnpm-lock.yaml` 根本不更新（命令报告成功但文件 mtime 不变）。必须加 `--ignore-workspace` 才能更新本仓库锁文件。这是本次排查中踩到并记录的坑。
- **共享检出中的并发编辑**：`src/host/cli-adapters/magpie-management.ts` 在本次操作期间被另一会话反复改写，一度出现语法错误的中间态（`this.remember(after)` 插进 `if` 条件里）。按 AGENTS.md「不修改他人工作」的要求未介入该文件；等并发编辑收敛后再验证（该文件最终由对方修好，`tsc` 0 error）。本次所有改动均限于版本/能力/脚本/测试与文档。

### 关于 `magpie-management.ts` 的修复

该文件在本次操作期间被并发会话反复重写，留下了两处结构损坏（在 HEAD 中已存在）：

1. `updateAccount()`：`this.remember(after)` 被插进了 `if (... !== update.on` 与后续 `||` 之间；
2. `readWebState()`：方法体被整体剪切到 `remember()` 之后，`readWebState` 只剩 `signal?.throwIfAborted()`。

修复方式：第 1 处把 `remember(after)` 移回条件语句之前（与同文件 `updateProvider`/`updateGroup` 的写法一致）；第 2 处从历史提交 `888f5ae` 取回完整方法体原位恢复。修复后 `tsc` 0 error，diff 仅 14 增 14 删，未改任何业务逻辑。此外把被 `pnpm add -D` 误移到 `devDependencies` 的 `@deepseek-ai/dsh-typert-protocol` 移回了 `dependencies`（Host 入口在独立 npm Profile 中运行，不能依赖 devDependencies）。
