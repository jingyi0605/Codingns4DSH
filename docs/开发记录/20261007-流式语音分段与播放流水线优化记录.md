# 流式语音分段与播放流水线优化记录

## 问题与判断

用户反馈助理文字先出现，语音明显滞后，希望识别到标点后就开始转换和播放。

源码确认当前链路没有统一等待整轮 DSH Agent 结束的门槛：

- `AssistantAgentAdapter` 在原生 `text-delta` 事件中立即调用累计文本回调；思考块和工具参数不会进入播报文字。
- `AssistantTextChat` 保存运行中的累计文字，Client 每 250 毫秒读取一次运行状态。
- 原分段队列只消费句末标点和换行，逗号串或没有标点的文本会一直等待句末或最终结算。
- 原 `MossVoiceOutput.speak` 在音频生成、播放都结束后才返回，下一句因此无法在前一句播放时合成。
- Host 工作进程本身已有帧回调和逐块音频下行，并非先生成整个音频文件再发送。

值得优化的是文本分段和生成／播放的等待关系。无需增加模型、并行工作进程或替换语音识别引擎。

## 实现

`StreamingSentenceQueue` 继续消费累计文本快照并保持已提交前缀校验：

1. 句末标点立即提交；逗号、分号、冒号短语达到八个字符后提交，避免单独合成「好，」等过短语气词。
2. 数字分隔符、时间和网址中的英文标点不作为短语边界。
3. 没有标点时，残片达到十二个字符且等待超过 700 毫秒，或达到 64 个字符，就寻找安全位置补切。仅在中文字符或空白后切分，保留尚未完成的英文单词及数字。等待时长由已有轮询检查，实际触发还受轮询和网络时间影响。
4. 最终结算补齐残片，重复快照不重复播报；取消后跳过旧轮排队文本。

`MossVoiceOutput` 增加连续播报的 `append` 和 `finish`：

- `append` 只等待该段音频流生成完毕，保留已经安排的音频节点和播放时间线。
- 下一段在前一段生成完成后即可请求，前段音频仍可继续播放；同一 Host 的 CPU 推理仍保持串行。
- 待播音频超过五秒时暂缓下一次请求或音频调度，随播放释放容量；这是预取阈值，单个音频块的时长可能使待播时长短暂超过阈值。保留异常队列长度保护。
- 段间停顿、变速后的实际时长、音量和选定音色继续生效。
- `finish` 等整轮音频播完后结算；旧轮取消不会清理新轮的请求句柄。
- 单次试听的 `speak` 保留取消旧播报并等待本次播放结束的行为。

Python 工作进程首个音频帧立即送入因果解码器，后续仍每两帧解码，减少首音等待而不过度增加持续解码调用。

## ONNX 能力边界

当前接入和[官方 ONNX 演示实现](https://github.com/OpenMOSS/MOSS-TTS-Nano/blob/main/app_onnx.py)都先编码一段完整文本，再建立推理请求并逐帧生成、解码音频。本次实现是「流式文本增量分段 → 每段音频流 → 连续播放」，没有向已经开始的同一次推理不断追加文本 token。该方案符合本项目轻量 CPU 部署方向，不新增常驻模型实例。

```bash
pnpm run typecheck
```

- TypeScript 回归 89/89、Python 生成控制 5/5、类型检查通过。
- 真实安装的 DSH 核心库在独立内存 Context 中证明 `finish` 和 `whenIdle` 前已转发文字，未加载 Profile 或启动服务器。
- 模拟工作进程证明 Host 在生成完成前返回首块音频；播放器证明续段合成不等待前段播完，最终状态仍等待播放完成。
- 覆盖标点、无标点兜底、前缀去重、数字／网址／英文词、预取限流、段间停顿、失败和新旧轮次取消。

本轮没有真实模型推理或音质测量，不能据此承诺首音耗时、实时率或 1～2 GB 内存预算。工作进程空闲 120 秒释放模型的行为仍保留，冷启动加载及每段预填充耗时需在真实环境单独测量。没有主动构建、启停 Stage0、下载模型或操作 Desktop。
