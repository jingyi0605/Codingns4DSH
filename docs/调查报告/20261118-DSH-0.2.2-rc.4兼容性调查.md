# DSH 0.2.2-rc.4 compatibility investigation

## Fixed upstream evidence

Compared `dsh-v0.2.2-rc.3` (`38a6a5c965aa99ab525161efb7cc5cf1fe62fced`)
with `dsh-v0.2.2-rc.4` (`3f321d32bfe382212a8ed8785c1d47a5a300aa23`).
There are 395 changed files, including 380 manifests containing version-only
changes. Production changes affect three files:

- `packages/llm/llm-deepseek/src/translate.ts`: a streamed refusal emits final
  billed usage and fails with `CONTENT_REFUSED`, preserving its explanation.
- `packages/llm/llm/src/error.ts`: adds the built-in refusal code.
- `packages/experimental/liveshare/src/host/tunnel-worker.ts`: inherits the
  Host's `ELECTRON_RUN_AS_NODE` when launching its own worker.

The final release does not add a `safetyCheck` setting or a default
`safety_check` request field. The old `MALFORMED_RESPONSE` code remains a
protocol failure and must not be relabelled without provider evidence.

## Plugin compatibility

The existing `llm.text`, Session, approval, question, RPC, UI and PeerHost
routes can serve rc.3 and rc.4 through their existing structural probes.
The minimum remains `>=0.2.1-alpha.2`; no new protocol version is required.
The plugin's Node MCP bridge already sets `ELECTRON_RUN_AS_NODE`.

Translation failure classification previously matched diagnostic text before
reading a structured provider refusal. A refusal explanation mentioning a
timeout, rate limit or network error could therefore cause an inappropriate
automatic retry. Prefer the explicit refusal code while preserving caller
cancellation and all existing handling of other failures.

Required regression coverage includes:

- Partial refusal output, terminal failure, exact error preservation, and no
  successful reply or automatic translation retry.
- One failed Webhook event per terminal sequence, with no successful event.
- Actual rc.4 Session, LLM and projection components, including billing and
  cold/checkpoint replay.
- Shared capability routes on old supported hosts, rc.3 and rc.4.
- Stage0 activation/settings, real Codex and Claude lifecycle checks, and
  available PeerHost/Relay checks.

## Verification policy

Keep the public tested version at rc.3 until candidate compatibility checks
pass. Record runtime package identity, startup method, logs, rollback paths,
passed checks and unverified platforms in the implementation record.
Desktop operations, release publication, tags and npm publication are outside
this change.

The upstream refusal migration is documented at
`docs/upgrade-guide/v0.2.2-rc.3/deepseek-refusal-code/guide.md` in the fixed
upstream tag. The local implementation evidence belongs in
`docs/开发记录/20261118-DSH-rc4兼容升级与Stage0验收.md`.

## Resumed blocker investigation

The Codex normal-turn exit regression was reproduced against unmodified
pre-upgrade plugin commit `9dd603ab`: empty and partial turns remained open
until the 3-second cancellation deadline. The driver does not depend on a DSH
runtime for this regression, and the upstream diff does not change it.
This establishes a pre-existing plugin defect. Attaching the existing
process-exit listener now produces `PROVIDER_ERROR` promptly and preserves
earlier completion/cancellation.

Both Grok's absent `view.tokenUsage` and Claude's `remove is not a function`
were reproduced with rc.3 native libraries and the original fixtures. The
projection key remains `tokenUsage` in both releases. Native token accounting
registers its projections in async `TokenMeter[Service.init]`; the fixture
bypassed that lifecycle. Awaited plugin startup plus awaited Claude projection
installation/cleanup fixes both runtimes without field aliases or version
branches. Full billing and cold/hot/checkpoint equality assertions remain.

rc.4 verification is limited to macOS Stage0 Web and installed Codex/Claude
protocol lifecycles with loopback model fixtures. Desktop, Windows/Linux,
public Relay, real model services and the Node 24 boundary remain unverified.
