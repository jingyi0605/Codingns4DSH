# DSH 0.2.2-rc.5 compatibility investigation

Compared upstream `dsh-v0.2.2-rc.4` (`3f321d32bfe382212a8ed8785c1d47a5a300aa23`)
with `dsh-v0.2.2-rc.5` (`9c2670d3bce5275e0d1610272958121af87787bb`).
The tag diff covers 433 files, including 380 version-only package manifests.
The range contains a LiveShare test-clock commit whose test changes are already
present in rc.4. The net source changes are confined to web search and its
tool catalog documentation.
[Upstream tag comparison](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.2-rc.4...dsh-v0.2.2-rc.5)

## Search contract

- The shared base removes its fixed `searchProvider` value. Upstream's settings card presents the unset value as **Automatic**. Explicit values in configuration or `DSH_WEB_SEARCH_PROVIDER` still take precedence. Fetch continues to default to `http`.
- `WebSearchRequest` adds optional `llmProvider`. The native tool passes the current model route, and `WebRuntime.search()` and `searchReady()` use it to prefer the same provider. The `deepseek-official` and `deepseek-account` model routes prefer DeepSeek server-side search. Other routes and calls without a model route prefer `deepseek-search-api`. If the preferred provider is unavailable, the existing single-usable-provider rule applies. An explicit provider selection does not fall back.
- The `searchProvider`, `fetchProvider`, `searchBilling`, and `fetchBilling` fields and the provider registration shape are unchanged. DeepSeek server-side search now prefers an inline result snippet to the citation excerpt when present, while the normalized response shape stays the same.
- Server-side search has no per-search fee and still incurs model-token usage. Its Messages endpoint uses its own Base URL and does not inherit the chat model's gateway. Deployments that require a gateway can configure the Messages Base URL or explicitly select the Search API.

## Plugin impact

The external CLI bridge delegates search and fetch to the Host's `web` service without a DSH model route, so its Automatic search preference remains the Search API. Plugin settings and provider registration do not read the changed default or the upstream billing fields. The plugin's usage display reads model and subscription usage through its existing contracts. The diff requires no compatibility adapter, capability route, or minimum-version change.

Verification is limited to dependency and capability checks, type checking, and targeted fixture tests. Live provider billing, gateway behavior, and runtime deployment are outside this verification.
