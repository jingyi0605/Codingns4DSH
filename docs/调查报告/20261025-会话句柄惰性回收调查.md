# DSH Session Handle Idle Eviction Investigation

## Decision

The repository does not directly open JSONL session handles from the assistant-navigation or terminal-sharing adapters. Those adapters call the public DSH UI navigation service, so closing a handle at those call sites would be both unavailable and semantically incorrect.

The fix is therefore installed at the `sessionPersistence.open` boundary as a compatibility safety net. It preserves the upstream handle `close()` implementation and only adds lifecycle tracking, idle/cap selection, and diagnostics. The upstream `@deepseek-ai/dsh-session-persistence-jsonl` package remains unchanged because this repository is not authorized to modify the Desktop profile or packaged application files.

## Opening Call-Site Evidence

| Location | Operation | Direct JSONL handle open | Runtime count | Conclusion |
| --- | --- | ---: | ---: | --- |
| `src/host/index.ts` | `sessionPersistence.open` wrapper | Yes, boundary observation | Not measured in Desktop | The wrapper is the only repository-owned boundary that can observe every upstream open. |
| `src/dsh-capabilities/client/assistant-session-navigation-adapter.ts:93` | `uiWorkspace.openSession(uiSessionId)` | No | Not applicable | UI navigation delegates to DSH; it does not receive a persistence handle. |
| `src/dsh-capabilities/client/terminal-sharing-adapter.ts:137` | `uiWorkspace.openSession(sessionId)` | No | Not applicable | Navigation is followed by scoped draft access; no persistence handle is retained here. |
| `src/host/features/global-voice-rpc.ts:1427` | `query.listSessions()` | No body materialization | Not applicable | Metadata listing remains header-only and is intentionally unchanged. |

The installed boundary sampler honors `DSH_TRACE_SESSION_HANDLES=1` and emits the same one-shot `[handle-trace]` format requested for upstream `JsonlBackendTracker.adopt()`. It samples the stack at the returned handle boundary, which identifies the DSH service that called `sessionPersistence.open` without touching the packaged Desktop code.

## Implementation

- `src/host/session-handle-eviction.ts` tracks handles returned by `sessionPersistence.open`.
- `lastUsedAt` is refreshed by `next`, `read`, `append`, `flush`, write, iterator, and subscription entry points.
- Read handles are evictable only when no operation or iterator/subscriber is active. Write handles additionally require an empty `buffered` queue.
- A wrapped `flushAll()` increments a traversal barrier so a sweep cannot close a handle during the persistence barrier.
- One unref'd `setTimeout` drives the sweep. It is removed when the tracked handle set becomes empty.
- TTL and LRU-cap evictions call the existing handle `close()` and emit `session handle evicted` diagnostics.
- `CodingNsSettingsSchema` exposes the following defaults:

```yaml
sessionHandleEviction:
  enabled: true
  idleTtlMs: 600000
  maxOpenHandles: 32
```

## Reproducible Verification

The local fixture suite is deterministic and does not start a server or operate Desktop:

| Scenario | Verification | Result |
| --- | --- | --- |
| Idle TTL | One read handle at `idleTtlMs` is closed | Pass |
| LRU cap | Three handles with cap `2` close the oldest handle | Pass |
| Buffered write | Non-empty write buffer is skipped | Pass |
| Active read | In-flight read is skipped, then closes after completion | Pass |
| Active iterator | Live iterator is skipped until `return()` | Pass |
| Active subscriber | Subscription disposer prevents eviction until unsubscribe | Pass |
| `flushAll()` barrier | Concurrent sweep does not close during the barrier | Pass |
| Lock release | Closing an evicted writer allows another writer to acquire the same lock | Pass |
| Diagnostics | `{ openHandles, maxOpenHandles, evictedTotal }` and eviction fields are emitted | Pass |

## Before/After Measurement Boundary

The supplied incident evidence reports 609 open handles for 622 sessions before the fix. The following Desktop measurements were not run in this coding session because repository policy forbids starting or modifying the Desktop application and profile:

| Scenario | Before evidence | After repository fixture | After Desktop run |
| --- | ---: | ---: | --- |
| Idle after restart | About 5 handles in the control run | N/A | Not run |
| Browse 200 sessions | 200 additional handles are expected from the leak direction | Cap remains at `32` when handles are evictable | Not run |
| Idle 15 minutes after browsing | Not available | TTL removes idle handles on the next sweep | Not run |
| 24-hour heap peak | 3.6 GB crash signature | Not a heap soak | Not run |

The Desktop acceptance run still needs to be performed in an explicitly authorized environment. It should collect both `session.lock` counts and GC heap values; RSS alone is not a valid leak criterion for the reported swap-heavy machine.

## Upgrade Notes

No pnpm patch was applied to the Desktop profile, so there is no local patch artifact to invalidate on App upgrade. When the upstream JSONL package adds native idle eviction, remove or disable this compatibility wrapper only after verifying that the upstream implementation covers TTL, cap, active subscriptions/iterators, the `flushAll()` barrier, and lock release. Until then, retain this repository-side regression suite and repeat the Desktop handle-count and heap soak checks after each App/package upgrade.
