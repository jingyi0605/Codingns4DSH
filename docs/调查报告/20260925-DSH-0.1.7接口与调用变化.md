# DSH 0.1.7 接口与调用变化

## 结论

本报告对比本插件当前验证基线 `@deepseek-ai/dsh-* 0.1.6-alpha.2` 与公开可用的 DSH 0.1.7 线路最新版本 `0.1.7-rc.2`。截至 2026-09-25，npm 没有稳定版 `0.1.7`；GitHub 最新对应 tag 为 `dsh-v0.1.7-rc.2`，提交为 `477b4f420553e8a52c2fbccc464d7561b239c443`。

当前插件已升级到 `0.1.1`，现已允许安装到 DSH 0.1.7；实际验证基线仍为 `0.1.6-alpha.2`：

```text
>=0.1.5-rc.3 <0.1.8-0
```

这是正确的保守结论。0.1.7 不是一次可通过改依赖版本完成的补丁升级，至少涉及设置系统迁移、连接 RPC 对等端语义、UI 图标导出重命名和多个客户端运行时类型变化。直接把依赖切到 0.1.7 会同时触发编译错误和运行时契约风险。

## 对比范围

| 项目 | 当前插件 | 对比目标 |
| --- | --- | --- |
| 插件版本 | `dsh-codingns 0.1.1` | 本次已升级 |
| DSH 测试基线 | `0.1.6-alpha.2` | 保持不变 |
| DSH 0.1.7 可用版本 | 无稳定版 | `0.1.7-rc.2` |
| DSH 版本约束 | `>=0.1.5-rc.3 <0.1.8-0` | 已放宽，0.1.7 进入实机测试 |
| 直接依赖 | 所有 `@deepseek-ai/dsh-*` 锁定 `0.1.6-alpha.2` | 未切换 |

下文的“删除”表示相对于 0.1.6 的公开类型或调用面不再存在；“新增”表示 0.1.7 增加的公开能力，不代表本插件必须全部使用。

## 1. 设置系统：最大破坏性变化

### 1.1 Host 设置 API

0.1.6 的核心模型是 `SettingsProvider` 加 `SettingsScope`：

```ts
import type { SettingsProvider, SettingsScope } from '@deepseek-ai/dsh-settings'

settings.register(namespace, schema, options)
settings.get(namespace)
settings.describe()
settings.mutate(namespace, ops, revision)
```

0.1.7 的变化如下：

- `SettingsProvider` 改名为 `SettingsForms`。
- `ctx.settings` 仍然存在，但不再提供旧的 `register` 入口。
- 公开写入/描述接口为 `describe`、`update`、`replace`、`mutate`；0.1.7 的 `SettingsForms` 声明没有独立的 `get(namespace)`，当前值应从 `describe()` 返回的 descriptor 读取。
- 新增 `configure({ auto }, owner?)`，支持自动生成配置表单。
- `SettingsDescriptor` 增加 `autoGenerate`。
- namespace 不再只是普通字符串，改为带品牌标记的 `SettingsNamespace`。
- 配置 schema 引入 `Config` 与 volatile 字段模型，配置生命周期和持久化语义随之调整。

本插件直接受影响的文件：

- `src/host/settings.ts`
- `src/host/rpc.ts`
- `src/host/features/types.ts`
- `src/host/cli-adapters/session-store.ts`
- `src/host/cli-adapters/registry.ts`
- `src/host/lan-access-dsh.ts`
- `src/host/terminal/startup.ts`

这些文件当前显式导入 `SettingsProvider` 或 `SettingsScope`，不能仅替换 package.json 版本后继续编译。

### 1.2 Client 设置 API

0.1.6 的 Client 通过 `ctx.settingsScope` 和 `SettingsScopeBinder.bind({ namespace })` 使用设置：

```ts
ctx.settingsScope
SettingsScopeBinder.bind({ namespace })
SettingsScope
SettingsScopeSnapshot
```

0.1.7 删除上述 scope 模型，改为配置表单模型：

```ts
ctx.configForms
ctx.configForms.get(entryId)
ctx.configForms.describe()
ctx.configForms.whileServed(...)
ConfigForm
ConfigFormSnapshot
```

此外，`ConfigForm.mutate`、`set`、`unset` 的返回值从 `Promise<void>` 变为 `Promise<boolean>`，调用方需要重新处理成功/未变更结果。

本插件直接受影响的文件：

- `src/client/index.ts`
- `src/client/settings-bridge.ts`
- `src/client/settings-section.ts`
- `src/client/features/types.ts`
- `src/client/account-bar.ts`
- `src/client/terminal/xterm-view.ts`
- `src/client/terminal/ui.ts`

### 1.3 迁移判断

这不是类型别名兼容问题，而是设置的拥有者、注册方式、快照来源和更新返回值都发生变化。必须先重新设计本插件 Host/Client 的设置边界，再迁移调用点；否则最容易出现“类型修到能编译，但运行时没有注册表单或配置更新丢失”的假兼容。

## 2. UI Primitives：图标导出重命名

0.1.6 导出固定尺寸名称：

```ts
IconPlusOutline16
IconChevronDownOutline14
```

0.1.7 改为按字重/规格命名：

```ts
IconPlusOutlineRegular
IconPlusOutlineMedium
IconChevronDownOutlineRegular
IconChevronDownOutlineMedium
```

同类图标整体从 `...14`、`...16` 等固定尺寸导出迁移到 `Regular`/`Medium` 风格导出。旧名称不再是兼容导出。

本插件调用点：

- `src/client/terminal/xterm-view.ts` 使用 `IconPlusOutline16`，需要选择新的 `IconPlusOutlineRegular` 或 `IconPlusOutlineMedium`。
- `src/client/terminal/ui.ts` 使用 `IconChevronDownOutline14`，需要选择新的 `IconChevronDownOutlineRegular` 或 `IconChevronDownOutlineMedium`。

其他相关变化：

- `Button` 仍存在，0.1.7 改为 `forwardRef` 组件，普通 props 基本兼容。
- `Menu.items`、`children`、`onSelect` 改为可选。
- `Menu` 新增 `listClassName`。
- `MenuEntry` 新增可选 `shortcut`。

## 3. Client Connection：RPC 增加 Peer 语义

0.1.6 的 handler：

```ts
type ConnectionRpcHandler = (
  endpoint,
  payload,
  signal,
) => Promise<ConnectionRpcResult<unknown>>
```

0.1.7 的 handler：

```ts
type ConnectionRpcHandler = (
  endpoint,
  payload,
  signal,
  peer: PeerScope,
) => Promise<ConnectionRpcHandlerResult>
```

新增公开类型和能力：

- `PeerId`
- `PeerScope`
- `RemoteInvocation`
- `PeerAdmission`
- `ConnectionRpcAttachment`
- `ConnectionRpcHandlerResult`
- `HostConnectionHandle.operator`
- `HostConnectionHandle.admit(request)`
- `OperatorPeer`

调用参数变化：

- `ClientConnectionRpc.open` 增加可选 `uplink?: AsyncIterable<unknown>`。
- `RpcStreamOpen` 增加可选 `uplink?: AsyncIterable<unknown>`。
- RPC 结果可以携带 attachment，调用协议不再只面向 JSON 返回值。

本插件的 `src/host/rpc.ts` handler 目前只声明前三个参数。TypeScript 通常允许函数忽略新增的第四个参数，因而不一定立刻报错；但完整适配必须显式接收 `peer`，并决定每个端点是否校验 peer 身份和 admission。当前自定义 JSON RPC 没有二进制 attachment，结果结构通常仍可兼容。

## 4. Typert 协议：远程调用增加上下文和双向流

0.1.6 已有：

- `RemoteResult`
- `Remote`
- `RemoteError`
- `TypertRemoteService`
- `remoteMethods`

0.1.7 新增：

- `PeerId`
- `PeerScope`
- `RemoteInvocation`
- `RemoteStream<Out, In = never>`
- `RemoteStreamHandle<Out, In>`
- `isRemoteJsonValue`
- `isRemoteUplinkItem`
- invocation descriptor 中的 uplink 定义
- Client 到 Host 的 remote stream uplink
- Gateway 上的 `ctx.invocation` 当前调用上下文

本插件的 `RemoteResult`、`@Remote`、`TypertRemoteService` 仍然存在，基础远程服务代码不属于立即删除项。但以下文件明确写有 0.1.6-alpha.2 兼容假设，升级时必须重新生成或检查 Typert artifact：

- `src/host/terminal/terminal-controller.ts`
- `src/typert.host.ts`
- `src/client/terminal/model.ts`

如果终端流要使用 Client -> Host 的上行输入，不能继续把旧的单向 stream 当成完整契约。

## 5. Conversation：匹配模型放宽、工具调用拆分

0.1.7 的变化：

- `ConversationStartMatch` 从 `SessionEvent<'start'>` 放宽为 `SessionEventLike`。
- `ConversationMatch` 的事件类型随之扩大。
- `ConversationViewSnapshotStore.grouped(...)` 新增。
- `ConversationNodeDefinition` 新增可选 `groupInput?()`、`publish?()`、`toolCallFocus?()`。
- `RunningToolCall` 拆为 `PreparingToolCall` 和 `StartedToolCall`。
- 原有 `match`、`start`、`update`、`buildViewNode` 仍保留。

本插件 `src/client/external-tool-stream.ts` 使用 `ConversationNodeDefinition`、`ConversationLocation`、`ConversationMatch`、`ConversationStartMatch`。当前实现没有依赖新增方法，理论上可以保持；但 `ConversationStartMatch` 变宽后必须重新 typecheck，尤其要检查事件收窄逻辑。

## 7. Locale：设置表单化，应用变为异步

0.1.6 的 `LocaleRuntime` 构造参数使用：

```ts
SettingsScope<LocaleSettings>
```

0.1.7 改为：

```ts
ConfigForm<LocaleSettings>
```

并新增：

- 可选 `LocaleBootstrap`
- `resolveText(text)`

`apply(ctx)` 返回值从 `void` 改为 `Promise<void>`。

本插件的 `CodingNsLocale` 只调用 `bind`、`getSnapshot`、`subscribe`、`register`，这些方法仍在；但构造注入类型和 `apply` 的异步调用链需要同步检查。直接受影响文件是 `src/client/locale.ts`。

## 8. Theme：Host apply 增加配置参数

0.1.7 的变化：

- `ThemeRuntime` Host 构造参数从 `SettingsScope<ThemeSettings>` 改为 `ConfigForm<ThemeSettings>`。
- Host `apply(ctx, config)` 增加 `config` 参数。
- `getTheme()`、`setTheme()` 仍保留。

本插件主要读取 `ctx.theme.getTheme().revision` 并监听 `theme/change`，这些调用没有明显破坏；真正迁移点在运行时构造和 Host apply 的实现约定。

## 11. 插件加载与兼容性策略

0.1.7 的 `app-boot` 对插件兼容性做了更明确的检查：

- 根据 plugin/package 的 `peerDependencies` 检查 `@deepseek-ai/dsh` 和 `@deepseek-ai/dsh-*` 是否与运行时版本兼容。
- 引入更明确的 plugin compatibility、profile compatibility 和 compatibility exemption 机制。
- 兼容性拒绝发生在 DSH 自己掌握的 profile composition boundary；被拒绝插件不会导入模块。
- `engines.dsh` 仍是安装期约束，但运行时重点检查 peerDependencies。

本轮已将 manifest 的 `engines.dsh` 和 peer dependency 临时放宽到 `<0.1.8-0`，允许用户在 DSH 0.1.7 上安装实机测试。当前 `version.json` 的 tested version 仍为 `0.1.6-alpha.2`，因此这不是正式兼容认证；正式发布前仍需在真实 0.1.7 依赖和 Profile 上完成完整回放。

## 13. 建议的 0.1.7 迁移顺序

1. 先把 Host/Client 设置数据结构迁移到 `SettingsForms`、`ConfigForm` 和新的 namespace/config 模型。
2. 替换图标导出，保证 UI 包先恢复编译。
3. 迁移 Connection RPC 的 `PeerScope`、admission 和 attachment 返回模型。
4. 重新生成并检查 Typert 终端 stream artifact。
5. 处理 Locale、Theme、Conversation 的异步和类型变化。
6. 在 DSH 0.1.7 依赖上运行 typecheck、构建、单元测试和实际 profile 加载测试。
7. 本轮已先更新 manifest 的 peer/engines 上限以支持实机测试；真实 0.1.7 回放通过后，再更新 `version.json` 的 tested version 和所有 DSH 包版本。

## 15. 阻塞点解决方案

### 15.1 发布策略：保留旧线，新增 0.1.7 适配线

当前 `0.1.1` 已临时允许同时安装到 0.1.6 和 0.1.7，但这只是实机测试通道。设置 API 和图标导出已经发生删除式变化，正式兼容声明仍必须以真实 0.1.7 依赖回放为准，不能把安装成功误认为运行时兼容已经认证。

建议维护两条清晰的插件线：

| 插件线 | DSH 范围 | 责任 |
| --- | --- | --- |
| `dsh-codingns 0.1.x` | `>=0.1.5-rc.3 <0.1.8-0` | 允许安装 0.1.7，当前由用户进行实机验证 |
| 后续正式适配线 | `>=0.1.7-rc.2 <0.1.8-0` | 完成真实 0.1.7 依赖、Profile 和运行时回放后再发布正式兼容声明 |

公共业务逻辑抽到 DSH 无关的内部接口，只有 Host/Client 装配层按 DSH 版本分线。这样不会让每个功能模块都携带版本判断。

### 15.2 设置系统迁移：从自建 Scope 改成原生 Config

这是必须先做的主线任务。

1. 在包根入口增加 DSH 0.1.7 需要的 `Config` 导出，把当前 `CodingNsSettingsSchema` 作为基础，但把真正需要由设置页编辑的字段标记为 `.volatile()`。
2. 将 `CodingNsSettings` 拆成两层：`CodingNsConfig`（DSH Loader 管理的用户配置）和 `CodingNsRuntimeState`（`cliSessions` 等 Host-only 动态状态，不进入 Config 和浏览器表单）。
3. Host 的 `apply(ctx, config)` 直接消费解析后的 `config`，功能模块通过内部 `CodingNsSettingsStore` 读取，而不是依赖 `SettingsScope.get()`。
4. Host 设置读写改为 `ctx.settings.describe({ redactSecrets: true })` 和 `ctx.settings.mutate(namespace, ops, expectedRevision)`。0.1.7 没有独立的 `settings.get(namespace)`，当前值从 descriptor 的 `value` 读取。
5. 监听 `settings/document-updated`，收到配置变化后更新内部 store；不要再通过 `SettingsProvider.register` 建立第二份权威状态。
6. Client 删除 `settingsScope` 注入和 `CodingNsSettingsBridge`，改为 `ctx.configForms.get('dsh-codingns')`，把返回的 `ConfigForm<CodingNsConfig>` 作为插件服务传给设置页和功能模块。
7. `ConfigForm.set/unset/mutate` 的返回值是 `Promise<boolean>`。设置页必须区分 `false`（被拒绝、跳过或恢复读取）与异常（传输失败），不能继续假定所有完成都是成功写入。
8. 自定义 `settings/get`、`settings/set` RPC 只在旧 DSH 适配线保留；0.1.7 线直接使用 DSH 的 settings mirror，避免双写和 revision 不一致。

建议的内部接口形状：

```ts
interface CodingNsSettingsStore<T> {
  getSnapshot(): { value: T | undefined; revision: number | undefined; writable: boolean }
  subscribe(listener: () => void): () => void
  mutate(ops: readonly SettingsPathOp[], expectedRevision?: number): Promise<boolean>
}
```

这个接口让 `FeatureRegistry`、终端和设置页不再知道 DSH 是 `SettingsScope` 还是 `ConfigForm`。

### 15.3 图标导出：直接替换，不做动态探测

在 0.1.7 适配线直接替换：

```text
IconPlusOutline16        -> IconPlusOutlineRegular（或 Medium）
IconChevronDownOutline14 -> IconChevronDownOutlineRegular（或 Medium）
```

不要用 `try/catch import` 或运行时字符串查找掩盖类型错误。图标是静态依赖，应该在构建期失败；根据现有视觉尺寸优先选择 `Regular`，并补一条渲染快照或 DOM 存在性测试。

### 15.4 Connection RPC：把 peer 变成请求上下文

把当前 `CodingNsRpcTable` 的 handler 从 `(action, payload)` 扩展为带上下文的形式：

```ts
interface CodingNsRpcContext {
  readonly peer?: PeerScope
}
type CodingNsRpcHandler = (action: string, payload: unknown, context: CodingNsRpcContext) => unknown | Promise<unknown>
```

`createCodingNsRpcHandler` 显式接收第四个 `peer` 参数并传入 context。所有手写 HTTP 入口与 DSH Connection 入口共用同一个 `dispatch` 函数，避免一条路径忘记 peer 约束。

安全规则：

- `peer` 只作为授权上下文，不能接受客户端 payload 中自报的 peer id。
- 需要对等端身份的端点必须拒绝 `peer === undefined`。
- 手写 `/codingns` HTTP 兼容入口继续经过 `connection.requestRejection`，但不能把它伪装成 `OperatorPeer`。
- 当前 JSON RPC 没有 attachment，先返回普通 `ConnectionRpcHandlerResult`；只有真实需要二进制传输时才引入 attachment/uplink。

### 15.5 Typert：先保持单向终端协议

本插件终端已有明确的 `follow`、`write`、`resize` RPC，当前没有必须使用 Client -> Host uplink 的场景。因此先在 0.1.7 依赖下重新生成或校验 Typert artifact，保持现有终端 wire manifest 和 `RemoteResult` 形状；只有要把终端输入改成双向流时，才迁移到 `RemoteStream<Out, In>`。

同时为 stream 增加取消、断线、旧 generation 隔离测试，防止 artifact 编译成功但生命周期语义改变。

### 15.6 Locale、Theme、Conversation、Sidebar

- Locale：当前 `CodingNsLocale` 只是能力子集类型，不要复制 DSH runtime；继续使用 `bind/getSnapshot/subscribe/register`，只在自有持久化偏好时改为 `ConfigForm`。
- Theme：当前只读 `getTheme()` 和监听 `theme/change`，不需要主动迁移；若后续写主题偏好，统一走 `ConfigForm`。
- Conversation：把 `ConversationStartMatch` 和 `ConversationMatch` 的事件参数显式收窄到 `readMarker` 能接受的 `unknown`，新增 `PreparingToolCall`/`StartedToolCall` 不要映射回旧的单一 `RunningToolCall`。
- Sidebar：保留现有 `openTabIn/register` 调用，暂不接入焦点、分屏和快捷键新增 API，先完成图标替换和运行时回归。
- Slots：当前未使用已知重命名 slot；升级测试中检查 `conversation.header.leading`，不要依赖旧 `conversation.session.header.leading` 别名。

### 15.7 实施与验收顺序

1. 新建 DSH 0.1.7 适配分支和内部 SettingsStore 接口。
2. 增加根入口 `Config`，拆出 Config 与 Host-only runtime state。
3. 迁移 Host 配置读取、revision 更新和 feature registry watcher。
4. 迁移 Client `configForms` 和设置 UI，删除旧 bridge。
5. 替换两个图标导出，补 UI 构建检查。
6. 接入 `PeerScope`，为 RPC 表增加上下文和拒绝策略。

8. 使用真实 profile 做加载、设置修改、重连和插件拒绝回放；全部通过后再把 `version.json` 的 tested version 更新为 0.1.7，并发布正式兼容声明。
