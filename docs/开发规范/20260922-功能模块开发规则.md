# 功能模块开发规则

## 目的

这份规则约束 `dsh-codingns` 里功能模块的写法。

要解决的问题只有一个：**新增一个模块时，只写模块自己的文件，不去改设置页、入口或 RPC 分发代码。**

改造前不是这样。加一个模块要改六处（类型联合、设置页清单、渲染分支、设置接口、设置 schema、RPC 的 `switch`），其中三处是条件分支。现在这些地方都由注册表驱动，只有一份清单需要登记。

## 模块长什么样

一个功能模块就是普通对象，包含三部分：

```ts
interface FeatureModule<S> {
  descriptor: FeatureDescriptor             // 它是谁
  start(context): void | FeatureDisposer    // 启用时做什么
  drain?(context): void | Promise<void>     // 可选：先停止接收新工作，保留状态
  dispose?(context): void | Promise<void>   // 可选：模块自己的收尾
}
```

`descriptor` 描述身份和界面：

| 字段 | 含义 | 注意 |
| --- | --- | --- |
| `name` | 模块名 | 同时是依赖引用名和设置里的启用键，发布后不要改 |
| `version` | 模块版本 | |
| `enabledByDefault` | 用户没表态时是否启用 | |
| `dependencies` | 依赖的同侧模块名 | 必须写全，注册表按它排序启停 |
| `runtime` | `host` / `client` / `both` | 决定模块归哪一端；设置页只显示非 `host` 的模块 |
| `ui` | 界面描述，可选 | 不写就不出现在设置页 |

`ui` 里可以写 `label`（标题）、`description`（说明）、`order`（排序）、`defaultOpen`（默认展开）、`alwaysEnabled`（不可关闭）。

`context` 是模块能碰到的全部东西：

```ts
interface FeatureContext<S> {
  readonly descriptor: FeatureDescriptor     // 自己的描述符
  readonly resources: FeatureResourceScope   // 登记清理函数
  readonly services: S                       // 宿主注入的能力
}
```

## 两个承载端

模块不会同时在两端运行。Host 侧和 Client 侧各有一个注册表，各自维护一份清单：

| | Host 侧 | Client 侧 |
| --- | --- | --- |
| 清单 | `HOST_FEATURES`（`src/host/features/index.ts`） | `CLIENT_FEATURES`（`src/client/features/index.ts`） |
| 服务 | `CodingNsHostServices`（目前只有 `rpc`） | `CodingNsClientServices`（`settings`、`rpc`） |
| 能做什么 | 子进程、文件、网络、PTY | 界面、设置表单、调用 Host RPC |
| 跑在哪 | DSH Host 进程（Node） | 浏览器 |

同一个功能需要两端配合时，在两侧各写一个模块，`runtime` 都写 `both`。两端模块名可以不同（Host 侧按能力取名，Client 侧按界面取名），同名更省事。

Host 模块默认不出现在设置页。它的配置界面应该由一个 Client 模块承载——例如认证能力在 Host 侧是 `auth` 模块，配置表单挂在 Client 侧的「中转访问服务」卡片里。Host 模块因此通常只靠 `enabledByDefault` 决定是否启用，或者由依赖它的模块带着启动。

## 新增一个 Host 侧模块

以终端为例。第一步，新建 `src/host/features/terminal.ts`：

```ts
import type { FeatureModule } from '../../shared/contracts/feature.js'
import { CodingNsRpcError } from '../rpc-table.js'
import type { CodingNsHostServices } from './types.js'

export function createTerminalFeature(): FeatureModule<CodingNsHostServices> {
  return {
    descriptor: {
      name: 'terminal',
      version: '0.1.0',
      enabledByDefault: false,
      dependencies: ['auth'],
      runtime: 'host',
      // 不写 ui：这个模块的配置由 Client 侧的卡片承载
    },
    start(context) {
      // 模块自己的动作表，键就是浏览器看到的动作名
      const actions: Record<string, (payload: unknown) => unknown> = {
        // list: () => [...],
        // open: (payload) => ...,
      }

      // 1. 需要浏览器调用的能力，按「命名空间/动作」登记
      context.resources.add(context.services.rpc.register('terminal', (action, payload) => {
        const handler = actions[action]
        if (handler === undefined) {
          throw new CodingNsRpcError('CODINGNS_RPC_NOT_FOUND', `未知动作: ${action}`)
        }
        return handler(payload)
      }))

      // 2. 自己创建的进程、监听器、定时器也登记进来，停用时按逆序释放
      context.resources.add(() => {
        // 关闭全部会话
      })
    },
  }
}
```

第二步，在 `src/host/features/index.ts` 的 `HOST_FEATURES` 里加一行：

```ts
export const HOST_FEATURES: readonly FeatureModule<CodingNsHostServices>[] = [
  createAuthFeature(),
  createTerminalFeature(),
]
```

## 新增一个 Client 侧模块

第一步，新建 `src/client/features/terminal.ts`：

```ts
import type { CodingNsClientFeatureModule } from './types.js'
import { TerminalPanel } from './terminal-panel.js'

export const terminalFeature: CodingNsClientFeatureModule = {
  descriptor: {
    name: 'terminal',
    version: '0.1.0',
    enabledByDefault: false,
    dependencies: [],
    runtime: 'client',
    ui: {
      label: '终端',
      description: '在浏览器里连接 Host 上的终端会话。',
      order: 30,
    },
  },
  start(context) {
    // 长期存在的订阅、连接、定时器都要登记，停用时注册表会调用它们
    const unsubscribe = subscribeSessions(context.services.rpc)
    context.resources.add(unsubscribe)
  },
  settingsPanel: TerminalPanel,
}
```

第二步，在 `src/client/features/index.ts` 的 `CLIENT_FEATURES` 里加一行。

第三步，如果模块有配置表单，按 [20260922-设置选项与表单开发规则](20260922-设置选项与表单开发规则.md) 写 `settingsPanel`：单列纵向布局、标题栏右侧 Switch、未启用时灰显且不可操作。

## 硬性约定

1. **模块名发布后不要改。** 它同时是设置里的键，改名等于丢掉用户已经保存的开关。

2. **资源必须登记到 `context.resources`。** 注册表在停用时按登记的逆序调用这些函数。不要自己安排清理时序，也不要在 `dispose` 里重复清理已经登记过的资源。

3. **只通过 `context.services` 取能力。** 模块不要 import 另一个模块的内部实现，也不要自己创建全局单例——设置句柄和 RPC 调用器都由宿主注入。

4. **RPC 走命名空间。** 用 `context.services.rpc.register('<命名空间>', handler)` 登记；命名空间重复会直接抛错。浏览器看到的端点是 `<命名空间>/<动作>`，主分发只解析一次前缀，不关心有哪些模块。

5. **依赖写全。** `dependencies` 里的模块会先启动，停用时反过来先停依赖方。缺依赖在 `validate()` 阶段抛 `FEATURE_DEPENDENCY_MISSING`，循环依赖抛 `FEATURE_DEPENDENCY_CYCLE`。

6. **常驻模块声明 `alwaysEnabled: true`。** 这类模块在设置页只展示状态、不给开关，`reconcile` 也不会停用它。只用在"启动即生效且无法撤销"的场景，比如局域网访问的 `crypto.randomUUID` 兼容。

7. **需要别的模块的能力时，先写依赖，再从 services 取。** 不要在模块里重新实现一遍已经存在的连接、凭据或作用域逻辑。

## 启用与停用的判定顺序

一个模块当前是否启用，按这个顺序判断（实现在 `isFeatureEnabled`）：

1. `ui.alwaysEnabled === true` → 启用，忽略设置。
2. 设置里 `modules[模块名]` 有值 → 用这个值。
3. 都没有 → 用模块自己的 `enabledByDefault`。

设置变化后宿主调用 `FeatureRegistry.reconcile(期望启用的模块名)`：期望启用但没启用的启动，已启用但不在期望集合里的停用。期望集合会自动补上这些模块的依赖，所以不会出现"子模块要启用、它依赖的模块却被停用"的互相拆台。

模块状态有五种：`disabled`、`enabling`、`enabled`、`draining`、`failed`。启动失败会进入 `failed` 并释放已经登记的资源，改好原因后可以再次启动。

## 不要做的事

- 不要在设置页、入口或 RPC 分发里加"如果是某个模块就……"的分支。这些地方应该是遍历和查表。
- 不要绕过 `context.resources` 自己管理清理时序。
- 不要让模块之间直接 import 内部实现；顺序用 `dependencies`，能力用 `services`。
- 不要把密码、refresh token 放进模块状态、日志、快照或界面文案。refresh token 只能待在 Host 凭据存储里。
- 不要留下未清理的进程、监听器、定时器和连接。

## 提交前检查清单

- [ ] 模块名是否稳定，是否与其他模块重名。
- [ ] `dependencies` 是否写全。
- [ ] 创建的每个资源是否都通过 `context.resources.add` 登记。
- [ ] 新增的 RPC 命名空间是否唯一，动作名是否稳定。
- [ ] 需要界面时，是否只改了模块自己的文件和清单里的一行。
- [ ] 是否补了测试（模块启停、资源释放、RPC 分发至少各覆盖一条）。
- [ ] 是否执行 `pnpm exec tsc --noEmit` 和相关定向测试。
