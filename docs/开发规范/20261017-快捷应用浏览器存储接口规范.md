# Quick Apps browser-storage integration contract

Date: 2026-10-17. This document defines the supported storage interfaces for HTML applications opened in the default sandbox viewer.

## Isolation and ownership

The default sandboxed Host preview now supports browser-local storage without additional domains, certificates, ports or workspace permissions. The trusted viewer owns browser LocalStorage and SessionStorage. The HTML receives a restricted message channel and cannot access DSH's storage object, cookies or parent DOM.

The browser origin and browser profile supply the outer storage boundary. A namespace is derived from the saved shortcut's owning Host, workspace, ID, document root and entry path. Renaming, reordering and ordinary revision changes preserve it. Changing the source selects another namespace; removing and recreating a shortcut creates another ID. This is browser-local data, not account synchronization or Host-side persistence. Clearing browser site data clears application data. Shortcut removal does not automatically purge the old namespace.

## Recommended asynchronous API

For the current sandbox viewer, the plugin installs `window.appStorage` before the original HTML scripts run. No SDK script or application-selected namespace is required.

```js
const saved = await appStorage.getItem('settings'); // string or null
const settings = JSON.parse(saved || '{}');

try {
  await appStorage.setItem('settings', JSON.stringify(settings));
  // The trusted browser store accepted the write.
} catch (error) {
  // Keep the edited state available for retry or export.
  console.error(error);
}

const keys = await appStorage.keys();
await appStorage.removeItem('settings');
await appStorage.clear(); // This application's local namespace only.

await appStorage.session.setItem('draft', 'temporary');
const draft = await appStorage.session.getItem('draft');
await appStorage.session.clear();
```

All values are strings. Non-string arguments use string conversion; symbols fail. Local data survives viewer reload/reopen in the same browser origin/profile. Session data follows the parent browser tab, survives viewer reload/reopen in that tab, and is independent in a separate tab. Normal browser session-restore behavior still applies. Promise success acknowledges a browser storage operation; it is not a disk-fsync or backup guarantee.

## LocalStorage and SessionStorage compatibility

Existing applications can use the supported core methods, `length`, `key(index)`, named properties, deletion and key enumeration:

```js
localStorage.setItem('settings', JSON.stringify(settings));
const restored = JSON.parse(localStorage.getItem('settings') || '{}');
sessionStorage.draft = 'temporary';

// Wait for preceding queued local writes and report earlier write failures.
await appStorage.flush();
await appStorage.session.flush();

window.addEventListener('appstorageerror', event => {
  console.error(event.detail.area, event.detail.name, event.detail.message);
});
```

The initial snapshot is loaded before application scripts run. Compatibility writes update an optimistic in-memory mirror immediately and are sent to the trusted viewer. A failed write is rolled back in the mirror, reported to the viewer and through `appstorageerror`, and remains observable through the next `flush()`. Applications requiring a reliable save acknowledgement should use the asynchronous API directly. Synchronous validation/quota errors throw immediately.

The compatibility objects are not native `Storage` instances. Native branding, `storage` events, live cross-window mirror synchronization and every Web IDL edge case are not promised. Explicit asynchronous reads fetch the current browser value; reload also refreshes the mirror. IndexedDB is deliberately not implemented. Cache API, OPFS, workers and file-picker APIs are not enabled by this feature.

Only the viewer's direct application document receives a storage channel. Nested HTML documents remain subject to the existing `frame-ancestors` and sandbox restrictions; no nested-document compatibility is added. Dedicated-origin providers keep native browser storage and do not receive this sandbox-specific API. Older Hosts/viewers keep the earlier preview behavior; update both sides to obtain the adapter.

## Protocol, limits and cleanup

New HTML clients opt into browser storage at launch. The Host generates a fresh handshake token. Only HTML navigation responses on those sandbox launches use a small bootstrap document. Ordinary fetches, binary resources and older launches keep their original bytes. The bootstrap fetches the original HTML, obtains browser storage snapshots, installs the API, and parses the HTML at its original URL. Source files are not edited. Existing relative resource URLs and the opaque-origin response CSP remain in effect.

The parent validates the exact iframe window, opaque origin, launch token and per-document ID, then transfers a MessagePort. The Host derives the namespace from its authoritative launch snapshot; the viewer does not use possibly stale sidebar metadata. PeerHost controllers bind it to their saved shortcut identity. Requests contain only a correlation ID, storage area, allowlisted operation and optional string key/value. Extra namespace/identity fields are rejected. Replacement, viewer disposal and expiry close channels. Host revocation without a viewer lifecycle change has no browser push notification; expiry still bounds the broker lifetime. Already downloaded snapshots cannot be recalled.

Each local/session area has a maximum of 1024 keys and 2 MiB of serialized UTF-16 JSON. The runtime allows at most 64 pending operations with a 10-second acknowledgement timeout. The browser's actual per-origin quota can fail earlier because DSH and other applications share the underlying browser quota. Denied storage, corruption and quota failures never silently become successful memory-only saves. Independent tabs do not provide cross-tab transactions for this adapter.
